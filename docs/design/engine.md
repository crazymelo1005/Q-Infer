# 引擎规格

本文定义引擎各子系统的实现规格。需求与验收条件见 [requirements.md](../requirements.md)，模块边界见 [overview.md](../overview.md)，接口契约见 [interfaces.md](interfaces.md)，必须先测的假设见 [gates.md](gates.md)，风险见 [risks.md](risks.md)。

硬件约束以环境 2 口径为准（[hardware.md](../hardware.md)）：单卡 16 GB 显存、448 GB/s 带宽、约 70 GB/s 主机内存带宽、PCIe 5.0 x8 约 31.5 GB/s、NVMe 顺序读约 7 GB/s、CPU 仅有 AVX2。单卡是本设计的硬下限，双卡为扩展形态（见第 14 节）。

## 2. 设计原则

1. 容量优先于速度。任何优化先问它是否增加了常驻需求。
2. 预测优先于反应。能在上一步算出来的东西，不要等到需要时按需加载。
3. 并行优先于串行。未命中专家与命中专家并行计算，预取与计算重叠。
4. 能确定的就不用猜，猜的部分单独标注。表行索引由已生成 token 确定性算出；路由共现只是概率性先验。两者置信度不同级，确定性请求按必需分配预算，概率性请求按剩余额度分配。
5. 质量不妥协。加速手段要么可证明不改变输出分布，要么误差有界且可测。
6. 可标定。性能相关的常量由自动标定确定，不硬编码。

## 3. 三层存储与流调度

职责：把所有逻辑块映射到介质，并保证计算所需的数据在需要之前就位。

### 3.1 统一页表

每个逻辑块维护所在层、物理偏移、引用计数、世代号、热度与预取状态。所有子系统通过页表申请与归还，不直接持有指针。字段与操作见 [interfaces.md](interfaces.md) 第 2 节。

驱逐前引用计数必须归零；预取一旦发出即锁定到消费完成，防止中途被驱逐。

### 3.2 字节预算仲裁

每步 decode 有一个固定的 PCIe 字节预算 `B_step`，由标定得到。全部过 PCIe 的搬运竞争同一预算，优先级自高到低为：本步必需 KV、本步必需表行、预测性专家。

预算不足时，预测性请求被主动放弃并计入迟到数，绝不为它插入额外的同步点。三类流量的范围见 [overview.md](../overview.md) 第 5 节。

实现见 `src/scheduling/budget_arbiter`：必需项按类别优先（KV 先于表行）一律准入、超出预算的部分记 overspend；预测性项按收益 ÷ 字节降序贪心，放不下就弃并继续尝试后面的。仲裁之上的两件事在 `src/scheduling/step_budget`：每步预算由机器画像推导（`pcie_h2d × 步长 × io_share`，环境2 得 186.8 MiB，字段与换算口径见 [S-52]）；计划层每步的四类需求（[interfaces.md](interfaces.md) 第 4 节）里过 PCIe 的三类转成请求送仲裁，仲裁结果再折成每步观测（interfaces 第 7 节）——观测里的预算用量、超支、迟到三笔账分开记，是引用性能数字的唯一取数口径。

### 3.3 介质层级与零拷贝

- 热数据在显存，温数据在主机 pinned 内存，冷数据在 NVMe。
- 冷数据用 `mmap` 直接映射，不经主机内存中转；异步预取使用 `io_uring` 与内存建议接口。
- 权重在传输通道上保持压缩态，只在计算前一刻解压，避免解压后的高精度副本再走一遍内存带宽。
- 热专家常驻页锁定内存，避免换页抖动。这是对上游做法的改变，不是复述上游：参考引擎自报常驻区 `arena_mib 17,395`（约 17 GB），但实测其常驻区在共享内存里且可被换出（进程 VmRSS 31.25 GiB、换出 2.61 GiB、系统 swap 已用 91%，见 [`../research/01-strata-engine.md`](../research/01-strata-engine.md) §10.1）。代价是 pinned 页不可换出，会加剧内存不足时的整体压力。

### 3.4 主机内存预算

约束：主机内存标称 64 GB，可见 61.0 GiB；参考引擎实测已用 73%（44.6 / 61 GiB），另一时点约 90%，可支配余量仅 6 至 16 GiB。

本设计需要的常驻对象与外挂表同量级且方向相反，因此内存预算是硬门禁（G-11）。

| 项 | 目标上限 | 超预算时的处理顺序 |
|----|---------|------------------|
| 记忆表行缓存 | 默认 1,048,576 行（IQ4_NL 约 90 MB） | 1，减小缓存行数至 0（关闭） |
| 共现图 | 需给出稀疏密度上限 | 2，降维或退化为会话级 top-K |
| 记忆表中频行内存层 | 4-bit 表 28.8 GB 中的中频部分 | 3，中频行并入 NVMe 层，只保显存热行 |
| 专家 pinned 区 | 由命中率目标反推 | 4，缩小常驻区，未命中比例上升后退守第 5 节 |
| KV 池（主机侧） | 见第 7 节 | 5，仅涉及正确性与长文能力时最后处理 |
| 机器画像 | 小于 1 MiB | 不降级 |
| 视觉编码器主机张量 | 约 1.4 GB | 按需载入载出，不常驻 |

降级顺序固定为自上而下。理由：先牺牲预测性与概率性收益，再牺牲分层深度，最后才动涉及正确性的部分。

## 4. 记忆表读取

问题：外挂表远超显存。一个 token 要读 16 行（每行 90 字节的 IQ4_NL 行，共 1,440 字节），行索引由该 token 及其前两个 token 经 n-gram 哈希唯一决定，因而是确定性的。

本节曾按「提前一步的显式预取加双缓冲」设计。该设计已被门禁 G-04 否定：表行访问在去重后既无顺序性也无局部性——16 个头把表切成 16 个互不相邻的约 20,000,000 行区间，一个 token 的 16 行必然异区间异页，顺序性在结构上为零；行级重复虽随上下文增长到约 0.59，但属长距离复现，复用距离中位数达上万次请求。据此退守按需读加有界行缓存，决策见 [ADR-007](adr/ADR-007-ngram-table-on-demand-read.md)，实测见 [`../research/02-qwen3.8-flash-next.md`](../research/02-qwen3.8-flash-next.md) §3.2。

### 4.1 解码期

1. 按需读。token 一经确定即算出其 16 个行索引并发起读，读回后参与该层 embedding 相加。不做提前一步的预取：G-04 显示下一步的行与刚读过的行几乎不复用（16 请求窗口内的重复只占 0.14%），提前一步得不到命中。
2. 重叠窗口。发起时刻取在 token 已知时，收集时刻取在该层消费之前，使读取与 embedding 落位重叠。这是上游已有的做法，本设计沿用，不承诺更多提前量。
3. 有界行缓存。按「8 路组相联、按行号哈希定组、组内轮转替换」保留最近读过的行，默认 1,048,576 行（IQ4_NL 约 90 MB）。它吃下长距离复现：G-04 实测该容量在 4K / 32K / 262K 档的命中率为 0.28 / 0.42 / 0.58。缓存容量计入内存预算（§3.4）。实现见 `src/storage/row_cache`。
4. 不允许近似。表行是精确输入，缓存未命中必须阻塞等待，其能否藏进一个步长由 G-10 判定。G-10 已实测（环境2）：16 页随机读 + H2D 的往返 P50 1.48 ms、P99 2.10 ms，而 decode 步长 P50 12.74 ms——约 6 倍余量，紧张内存 lane 下同样成立，故按需读成立（见 [`../research/02-qwen3.8-flash-next.md`](../research/02-qwen3.8-flash-next.md) §3.3）。

行反量化的实现与回归见 `src/kernels/iq4nl`：IQ4_NL、一行 90 字节、分裂式半字节序（按交错读会得到一组可信但错误的值）；其正确性用模型真实字节与手算样例两路钉住。整条装配（token → ngram 哈希 → 预算仲裁 → 命中行缓存或读表 → 反量化 → 按 head-slowest 拼 2560）在 `src/ple/row_path`，表行来源可注入（真模型上是 `artifact::GgufTable`）；行号越出表范围即失败，不静默读别的行。真表上已跑通：分片2 的 `per_layer_token_embd.weight`（320,001,536 行 × 90 字节），5 个 token 全冷读 80 行、行号全部在范围内，且第 0 个 token 的 16 个行号在独立的 Python 实现（`measure/ple_row_oracle.py`）上复算，逐头的 L1 一致。预算按每个 token 一轮累计：必需的表行即使超预算也全部准入（记 overspend），一条都不丢。

### 4.2 预填期

1. 与分块对齐。按每块不超过 8,192 token 切分，逐块算出该块的全部表行索引。索引合并只用于去重与排序，不能合并为顺序大块读：G-04 显示一个 token 的 16 行落在 16 个相距约 1.8 GB 的区间，跨 token 亦然，不存在可合并的相邻性。
2. 块内去重。块内不同位置的键存在重复（G-04 全序列重复率 0.28 至 0.59），先按行 id 去重再取，减少 IO 次数。此处减少次数优先于减少字节。
3. 首块没有重叠窗口。第 1 块无前序 token，只能阻塞读取。因此冷启动改善的上界就是首块的表行读取时间，不承诺更多。
4. 本路径受 G-04 已给出的结论约束（去重后为近似随机访问），故不做顺序化改造，只做去重与批量化。

## 5. 专家缓存与共现感知替换

问题：参考引擎的专家缓存是固定槽位加持续学习，没有自适应淘汰策略，且命中率会随工作集切换波动（环境2 实测单请求 0.935 至 0.975，长提示下可低至 0.794）。

命中率的上界由路由集中度决定，不由缓存策略决定。策略只能逼近上界，因此本子系统受门禁 G-09 约束。

G-09 已实测该曲线（环境2，解码路径，164.6 万次查表）：top-5,000 对覆盖 0.680、部署配置的 8,106 个槽位覆盖 0.835，且饱和很慢（99% 需 16,674 对，占全表 68%）。因此「上界」是一条收益递减的慢曲线，而非硬天花板：共现与会话亲和改变的是哪些对常驻，抬不高曲线本身。口径提醒：引擎会话内自报的 94% 至 97% 含自适应换入与跨请求前缀复用，与本口径不可混用（[S-34]、[`../research/01-strata-engine.md`](../research/01-strata-engine.md) §4.1）。

G-05 给出槽位的实测量级：部署配置（双卡、`--batch 4`、`--kv-resident 32768`）下两卡合计 11,967 个槽位（主卡 6,529，8,816 MiB），`--batch 4` 的槽位会话另占主卡 2.05 GiB——并发是用槽位换来的。G-06 给出命中率到吞吐的斜率：同一提示内约 +1.4 tok/s 每 +1 点命中率，且跨提示不可比（[`../research/01-strata-engine.md`](../research/01-strata-engine.md) §4.2）。两条合起来说明：本子系统能动的杠杆是「把哪些对放进那不到一万二千个槽位」，而不是抬高曲线本身。

设计：

1. 共现图。维护专家对在同一 token 或同一会话内被一起激活的统计，作为替换策略的输入。
2. 会话亲和。会话开始时按任务类型预载对应专家簇，而不是使用全局热榜。
3. 替换策略可插拔，在线评估，每次替换时用近期命中率做比较。
4. 槽位弹性。槽位数在 KV 常驻窗口与专家数量之间动态配平，见第 7 节。

实现与实测。槽位与替换策略见 `src/storage/expert_cache`：组相联，键是 (层, 专家)，策略可插拔（`FifoPolicy` 复刻参考引擎与本仓库行缓存那种组内轮转、`LruPolicy`、`CooccurrenceAwarePolicy`）。本类只管谁占槽位，不管槽位里的字节——字节按同一个键登记进 `storage/page_table`，故驱逐前那两条不变量（引用计数归零、预取不在途）由调用方给的 evictable 回调守住：组内全都不可驱逐时返回 `kMissBlocked`，不硬换。读取路径把三者接起来在 `src/experts/expert_source`：一个专家的三矩阵从表里读出来后就地组装进常驻区（三矩阵在文件里不连续，故按各自的逐专家步长分别读），驱逐时同时退掉常驻区与页表条目（`PageTable::remove` 也守那两条不变量，引用计数不为零或预取在途时拒绝）。两条退化语义是刻意的：字节预算用尽后不再准入、改走临时缓冲（缓存装不下该退化，不让正确性受影响）；组内全不可驱逐时这次不准入而不是硬换。`pin`/`unpin` 走页表的引用计数，被 pin 的专家在期间不会被换出。共现图见 `src/storage/cooccurrence`：容量是显式参数（engine §3.4 要求给出稀疏密度上限），规则是「每 2^20 次观察把全表计数减半、归零的条目退场」加「衰减后仍满则拒收新对」——这两条都是 O(1)，替代了最初那版「满时全表扫描找最弱的一对」（后者在 28,080 条记录的真轨迹上把一次重放从十几毫秒拖到 14 分钟）。

离线重放在 `measure/expert_cache_replay.cpp`（读参考引擎 `--dump-routing` 的轨迹，格式见 [S-34]）与编排脚本 `measure/expert_cache_sweep.py`，记录 `measure/results/20261010T184146-expertcache-环境1.json`。四条结论，口径是**单条轨迹内部**的自适应命中率（与 G-09 的全局静态覆盖不是一个口径，不可混用；重放是确定性纯计算，写在环境1 或环境2 不改变结果，轨迹来自环境2）：

1. LRU 高于组内轮转。部署槽位口径（8,106 / 11,967、8 路）下三条轨迹分别高 3.0 / 2.4 / 1.9 与 2.2 / 1.9 / 2.4 个百分点——参考引擎那种固定槽位加持续学习确实留了约两个点在这里。
2. 相联度是与容量独立的旋钮，且更划算：8,106 槽位下 1 路 0.7097、8 路 0.8525、64 路 0.8705（trace-p0）；11,967 槽位 2 路（0.8468）仍低于 8,106 槽位 8 路（0.8525）。
3. 共现感知策略与 LRU 的差在 ±0.01 个百分点内、方向还不一致，即共现图作**替换输入**这一形式本轮不支持。
4. 换形式再测一轮（把共现用在「哪些对放进槽位」：留出法下用去一半的轨迹统计排序、预载后评另一半）仍然没有增益：中心度排序与频次排序**逐位相同**，且这是结构性的——固定 top-k 时一次激活恰好带来 (k−1) 个伙伴对，故 `中心度 == (k−1) × 边缘频次`，共现图作排序输入不含超出边缘频次的信息（这条不变量有测试钉住，见 `tests/test_expert_cache`）。**但预载本身是真收益**：与冷启动比，预载（不论用哪种排序）在 11,967 / 8,106 槽位下高 3.9 至 5.5 个百分点——engine §5 第 2 条「按簇预载而不是用全局热榜」的**预载**这一半成立，**「按簇」这一半不成立**（簇排序退化为频次排序）。要让共现图真正产生增量，需要用到条件结构（同一个键在不同场合搭配不同伙伴）而边际频次抓不到的形式，那要单独设计并单独测；在此之前不把 §5 第 1 条当作已获收益的设计。

读取路径已在真模型上核过：`src/experts/expert_source` 接进 `experts/moe_layer`（`cache_slots > 0` 才启用；`cache_ways`、`cache_byte_budget`、`cache_policy` 同层可配）。部署那份的层 0 与层 12 各跑 32 个 token，缓存路径与直读路径的逐元素差为 0；常驻 10 个专家占 14.404 MiB，即 1.44 MiB/专家，与画像由 `cache_mib ÷ cache_slots_total` 反推的 1.35 MiB/专家相合（两条独立路线）。口径：手工入口只对激活做小扰动，路由其实没换专家，故它给的是接线与逐位一致的证据，不是命中率结论——命中率问题由下面的离线重放回答。

命中率不作为优化目标，只作为观测量。任何引用命中率的结论必须同时给出 PCIe 侧占比与空闲显存，否则不成立。

## 6. 异构执行

职责：让命中专家、未命中专家、KV 搬运与表行读取在同一时刻都在推进。

显存侧执行稠密部分（注意力、门控残差、路由器、共享专家、输出头、MTP 层）与命中专家，全部走融合内核。解码步的稠密部分用图捕获消除启动开销。

CPU 侧执行未命中专家，用 AVX2 量化内核：

1. 量化直接参与计算。码本解码融进 GEMM，避免先反量化到高精度再计算，否则内存带宽消耗放大约四倍。
2. 线程池按核心类型分配。本平台为 8 个性能核加 16 个能效核。G-03 实测单核：P 核 2.81 GMAC/s、E 核 2.29（4 位档码本内核），P/E 仅 1.23 倍，且 16 个 E 核的合计（33.4 GMAC/s）高于 8 个 P 核（21.1）。故「两类核不混用」是策略选择（避免长尾由慢核决定），不是达到合计算力的必要条件。
3. 归并。CPU 与 GPU 的结果在同一缓冲区按专家槽位累加合并，避免额外的同步。
4. 同步点最小化。每步只有一次显存与主机之间的汇合。

设备侧已开工，四块内核合起来覆盖了部署那份**一个专家的全部三档**：Q2_0（down 全 48 层）、IQ2_S（gate/up 的 34 层）、IQ2_XXS（gate/up 的 11 层）、IQ1_M（gate/up 的 3 层），分别在 `src/kernels/cuda/q2_0_gemv.cu`、`iq2s_gemv.cu`、`iq_gemv.cu`（后两档同处一个 TU：配对物同为 Q8_K、脚手架相同）；语义都照本仓库主机那份写（`src/kernels/` 的同名档），并在真模型字节上逐行对照（`tests/test_q2_0_cuda`、`test_iq2s_cuda`、`test_iq_gemv_cuda`，只在 `-DQINFER_ENABLE_CUDA=ON` 时构建）。为什么不复用上游的 CUDA 实现：ggml 那两条（`ggml/src/ggml-cuda/mmvq.cu` 与 `vecdotq.cuh` 的 Q2_0 与 IQ2_S 分支）都把权重配的是 Q8_1 激活——带 d 与 s 两个尺度、整数累加时要四舍五入——而本仓库的激活搭档是 Q8_0 与 Q8_K，配对物不同，抄过来就是另一套数值行为。

环境2（sm_120，CUDA 13.2）上的读数：把真模型字节 tile 成 2560 行 × 每行 10 块（正是部署那份 down 的几何）后，设备与主机逐位相同（2560/2560 行，L1 相对差 0），对独立双精度参考 5.2e-08；两条错读法——漏掉码的 −1 偏移、字节内位序取反——分别偏离 0.846 与 0.494，即这两处一旦读错必被抓住。同几何下一次调用的耗时：主机 550.5 µs（约 3.0 GMAC/s，与 G-03 的单核量级相合）、设备 98.9 µs，设备侧约 5.6 倍——但这个入口每次都要把权重搬上去，故那是含搬运的下界，不是常驻后的数字。变异测试 5 条里 4 条致死；存活的那条是行越界守卫，当前夹具的 n_rows 恰是块大小的整数倍，越界写落在同一段显存里、主机侧观测不到，故该守卫按一般的 n_rows 保留。IQ2_S 那块同法核过：真字节 tile 成 640 行 × 每行 10 块（gate/up 的几何）后设备与主机逐位相同（640/640 行，L1 相对差 0），对反量化双精度参考 7.77e-08；计时主机 522.7 µs、设备 188.3 µs（含搬运，约 2.8 倍）；它的变异 4 条全致死（尺度漏掉乘 2、qh 的两位从低位取、丢掉最后的 0.125、丢掉块的 fp16 尺度），即这四处一旦读错必被抓住。IQ2_XXS 与 IQ1_M 两块同法核过：真字节 tile 成 640 行 × 每行 10 块后设备与主机也都逐位相同（各 640/640 行，L1 相对差 0），对反量化双精度参考 7.37e-08 与 3.02e-08；计时 IQ2_XXS 主机 473.1 µs 对设备 141.1 µs、IQ1_M 462.5 对 204.7 µs（含搬运）；两块各 5 条变异全致死（尺度漏掉加 1、符号索引反序、qh 高位取错端、忽略 delta 符号、丢掉 delta 项）。

block_out·2·sigmoid(inject_c/hc)`——`2·sigmoid` 把门心定在 1，零注入即普通残差相加。这六处都是一读就过、错值却可信的地方（还有「按流平均还是求和」「激活要不要按 bf16 舍入」），故实现与测试都按上游 parity 测试的做法：每处错读法先按错的算一遍、要求与对的读法有明显差别，再比实现。实现见 ## 7. KV 管理

主案例有两种 KV，必须分开记账。

| 缓存 | 所在层 | 随什么增长 |
|------|-------|-----------|
| GDN 循环状态 | 36 层线性注意力 | 并发序列数，与长度无关 |
| QSA KV 与索引器 KV | 12 层稀疏注意力 | 上下文长度乘以并发 |

设计：

1. 两个独立池，独立配额、限额与驱逐。并发升高时两条一起涨，调度器必须同时观察两个余量。
2. 常驻热窗。QSA 只常驻最近一段 token，其余分块流式读，块粒度与注意力块对齐。
3. 索引器 KV 有独立精度旋钮。它对质量敏感但体积小，可以比主 KV 更激进。
4. 精度档默认 FP8，长上下文或高并发时降到 4-bit，3-bit 作为实验档，需融合内核与标定后才启用。
5. 分页方案与稀疏注意力的块粒度对齐，避免一次注意力跨越过多物理块。

长上下文下每 token 的 KV 读字节已测（G-12）：256K 原生上下文下 KV 块读的显存命中率 90.1%，一个 256K 请求的内存侧 KV 读合计 213.3 MiB，约 1.7 MiB/token（且大部分在预填期），远低于「索引器稠密扫描」的推算——引擎只读索引器选中的块。因此第 15 节「瓶颈不在带宽」不再受这一条阻塞（见 [`../research/01-strata-engine.md`](../research/01-strata-engine.md) §7.2）。

两个池的记账与准入已实现（[interfaces.md](interfaces.md) 第 5 节的实现说明）：`src/kv/kv_pool`，两类驱逐语义不同（QSA 只清常驻窗口、序列还在；GDN 全有或全无）。第 5 节第 4 条「槽位弹性」——槽位数在 KV 常驻窗口与专家数量之间动态配平——现在**机制已就位**（第 6 节的 `src/dense/kv_window`：字节配额 + LRU 驱逐 + 钉住，接在 QSA 的搬入路径上），故可以据此定配平规则；**配平本身仍是待定的设计决定**：目前槽位数与常驻窗口是两个独立的配置项，二者的换算与优先级还没定，等这条规则定了再改本节。

## 8. 投机解码

1. 基线用模型自带的 MTP 头，起草长度默认 3，按显存与接受率在线自适应；接受率低于阈值时收缩。
2. 提示查询起草从上下文已有文本中抄取，最多 5 个 token，仅在实测有收益时启用。
3. 验证即证据。主模型一次前向验证全部草稿，输出分布不变。
4. 被拒绝的草稿仍会被验证窗口读入其表行与专家，造成 IO 放大。G-13 实测（环境2，接受率 0.786 至 0.940）：接受率取倒数为 1.064 至 1.272 倍，按轨迹直接数出的「每生成 token 的位置数」为 1.047 至 1.250 倍（中位 1.133）。该放大按位置计，同时作用于专家读与表行读，不改变第 4 节的按需读路径。

## 9. 精度策略

| 旋钮 | 默认 | 备选 |
|------|------|------|
| 权重 | NVFP4（本平台原生）或 IQ2_XS / IQ3_XXS | IQ4_XS、三值 |
| 主 KV | FP8 | 4-bit，再到 3-bit |
| 索引器 KV | FP8 | 4-bit |
| 累加 | FP32 | BF16 |

所有低精度路径都必须把反量化融进内核。多旋钮同时降档会产生复合误差，允许的组合与禁止的叠加见第 16 节。

## 10. 自动标定

标定产出机器画像，四项输入与五项推导参数：

1. 显存可用量与带宽。本项用 device STREAM（copy/triad）而不是规格里写的小 GEMM 扫描：画像要的是「每 token 权重字节 ÷ 显存带宽」这个上限，而 fp32 小 GEMM 在消费级卡上先撞算力，会把带宽量低。GPU 侧的纯算力下限另有参考引擎的 `--gpu-only-full`。
2. PCIe 实际档位与有效单向带宽（大块拷贝）。这一步同时回答空闲降档是否只是假象。
3. 按核心类型区分的量化内核吞吐。
4. 主机内存有效带宽。

据此推导：每步字节预算、专家槽位数、KV 常驻窗口、并发分池方案、起草长度上限。每步字节预算的公式为 `pcie_h2d × 步长 × io_share`，其中 io_share（一个步里允许 IO 占用的时间份额）是设计输入，不是测出来的——本设计取 0.5。全部参数落盘，可复用、可对比，字段见 [interfaces.md](interfaces.md) 第 6 节。

环境2 上这四项已测、推导已实现：工具 `measure/calibrate.py`（组合器，输入即各测点的原始记录），产物 `measure/results/*-calibrate-环境2.json`，逐项数字与读数见 [`../research/01-strata-engine.md`](../research/01-strata-engine.md) §10.2。三条可直接使用的结论：槽位 = 缓存字节 ÷ 专家块字节（复现实测到 1.6%）；每步 PCIe 预算对「本步必需的未命中专家」有 1.75 倍余量（静态命中 0.835）；用实测显存带宽（398 GB/s，标称的 88.9%）算，§15 的上限是 IQ2_XS 216 tok/s、FP8 64.8 tok/s。

本能力不具备差异化价值：参考引擎已有对应的启动标定开关。

## 11. 代码与数据布局

| 维度 | 做法 |
|------|------|
| 数据布局 | 专家按 id 主序存为连续块，量化块边界与传输粒度对齐，一次传输取回一个完整专家 |
| 零拷贝 | 冷数据直接映射文件；权重在通道上保持压缩态，只在计算前一刻解压 |
| 内核融合 | 反量化融进矩阵乘；路由的归一化、取前 k、聚集融合；门控残差的四分支门控融合 |
| 零分配 | 全部缓冲区启动时一次性分配，解码步内不分配 |
| 图捕获 | 解码步的稠密部分用图捕获，消除小批量下的启动开销 |
| 主机内核 | AVX2 加码本查表；按核心类型分池；专家槽位按缓存行对齐以避免伪共享 |
| 同步 | 每步一次汇合；预取完成用事件通知，不用轮询 |
| 语言与构建 | C++20 + CMake（≥3.28），依赖面为零；主机侧不依赖 CUDA，使 CI 能在无 GPU 的 runner 上守住不变量。CUDA 侧由 `-DQINFER_ENABLE_CUDA=ON` 单独打开（默认关），见 [ADR-008](adr/ADR-008-implementation-stack-and-kernel-reuse.md) |
| 内核来源 | 第三方量化内核以裁剪子集入库，而不是外部依赖：本设计要插桩的位置正是内核边界，需要冻结的数值行为（[ADR-008](adr/ADR-008-implementation-stack-and-kernel-reuse.md)） |

## 12. 服务与调度

- 提供 OpenAI 兼容的 HTTP 接口。
- 批调度目标是并发不超过 8，不追求服务端式吞吐。环境2 上批量转矩阵乘的收益有限。
- 前缀缓存用基数树。多轮对话共享系统提示时，重复预填接近归零。
- 会话亲和：会话到专家簇的画像，作为第 5 节的输入。
- 多模态：视觉编码器约 1.4 GB，按需载入载出；图像特征缓存复用，避免多轮引用同一图像时重复计算。

## 13. 核显与 NPU

动机：未命中专家路径是当前最大的可控瓶颈。核显与 CPU 共享同一条内存总线（约 70 GB/s），因此不增加带宽；只有在算子属于计算密集而非带宽密集时，多一组计算单元才有价值。

判断准则由 G-07 给出：

| 未命中专家路径的性质 | 现象 | 结论 |
|---------------------|------|------|
| 带宽瓶颈 | 读字节速度封顶，CPU 在等数据 | 核显无用，只能提高命中率 |
| 算力瓶颈 | 数据已就位但低比特码本解码算不过来 | 核显可分担，与 CPU 并行 |

G-07 已实测为**算力瓶颈**（环境2）：纯流式读 8 线程即饱和在 58.5 GB/s、24 线程 67.5 GB/s；4 位码本反量化+FMA 臂 24 线程仅 30.8 GB/s（0.456× 天花板）、16 线程 20.6 GB/s，且随线程数上升未触顶。故本节的启用前提满足：核显可作为第二组算力参与未命中专家路径，与 CPU 并行；在引擎专家池的实际规模（16 线程附近）算力臂只用掉总线的一半左右，带宽尚有可分配的余量（见 [`../research/01-strata-engine.md`](../research/01-strata-engine.md) §5.1）。

不依赖 G-07、可直接采用的三处：视觉编码器移到核显（直接省 1.4 GB 显存，约等于一千个专家槽位，并省去一次主机到显存的拷贝）；表行的聚集与加权聚合；图像与视频预处理。

边界：核显与 CPU 总吞吐共同受总线带宽约束，只在算力瓶颈场景启用并限制其占比，把它当作第二个工人而不是独立的带宽来源。NPU 擅长整数卷积，不适合低成本码本矩阵乘，不参与专家计算。

核显现状与总线争用已实测（工具 `measure/igpu_probe.c`，记录 `measure/results/20261010T195533-igpuprobe-环境2.json`；零新增依赖，只用发行版自带的 Mesa Vulkan / ANV）：

1. 设备可见：Intel Arrow Lake-S Graphics（vendor 0x8086、device 0x7d67、集成型），绑在 i915，渲染节点 `/dev/dri/renderD130` 对当前用户可开（有显式 ACL）。
2. 运行时现状：核显没有任何计算运行时——无 Level Zero（无 loader、无头文件），OpenCL 只注册了 `nvidia.icd`（核显不在其中）。Vulkan 加载器与 ANV 驱动（Mesa 26.0.8）在。故两条路线的依赖代价不同：Vulkan 路线运行时零新增，只需编译期的 `libvulkan-dev` 与一个 SPIR-V 编译器（或按 [ADR-008](adr/ADR-008-implementation-stack-and-kernel-reuse.md) 的惯例把预编译 SPIR-V 连同生成来源入库）；Level Zero 路线需要在环境2 加装 `intel-level-zero-gpu` 与 `level-zero-devel`。上游那套 Arc 端口是 SYCL，同样依赖 Intel 计算运行时，故「复用上游内核」并不因此更省依赖。
3. 该设备在 192 项扩展里没有 `VK_KHR_shader_integer_dot_product`，故 Vulkan 路线上 DP4a 等效指令不可用，码本矩阵乘只能手写整数乘加——这与 ADR-005「内核走 DP4a（若可用则 XMX）」之间有一处待决的口径差。
4. 总线争用（带宽型对带宽型）：核显 `vkCmdCopyBuffer` 搬 256 MiB 最好 26.9 GB/s（对总线约 53.7 GB/s，拷贝按读一遍写一遍计）；与 8 线程 CPU 流式读同跑时 CPU 从 56 至 61 GB/s 掉到约 25 GB/s（保留 41% 至 46%），两侧合计 59 至 62 GB/s，只有 CPU 单独的 0.98 至 1.10 倍。即带宽型工作下核显是争用者、不是增量来源。
5. 口径边界（要紧）：上面两条只回答带宽型工作。未命中专家路径是算力型（G-07：4 位码本臂在 16 线程只用 20.6 GB/s 总线），故「算力型工作能否叠加」还没有答案，它需要一个真正跑在核显上的计算内核——而那需要上一条的 SPIR-V 工具链。CPU 臂与 `measure/cpu_expert_bench.c` 同形（按线程切互不重叠区段、屏障齐发、固定遍数），本机上 8 线程得 56 至 61 GB/s，与 G-07 的 58.5 同量级，可作为方法互校。

专家分担这条缝的接口形式已定在 [interfaces.md](interfaces.md) 第 8 节：后端以计算组为单位（设备、队列、内存池、能力表，见 [ADR-011](adr/ADR-011-compute-group-abstraction.md)），提交面是工作单元与工人，PCIe 与 DDR 两套资源分开限制，另有同步与归约、降级与正确性口径。核显是其中一组，它的能力表按本节实测填（没有计算运行时、没有整数点积指令）。本节的三处无条件用途不经过那条接口。

共享内存总线上同类方案的公开实测为负收益（−19%），这一风险不因 G-07 的结论消失；G-07 只回答「值不值得试」（算力瓶颈成立），占比如何限制仍须实测，见 R-08。

## 14. 单卡与双卡

统一原则：代码与数据格式只有一套。卡数只改变机器画像与分配策略，不改变代码路径。目标是单卡能跑、加卡更好，而不是两套引擎。

双卡的收益：显存合计翻倍，命中率随之提高；两卡的 PCIe 通道可并行搬运；算力翻倍。

消费级双卡的三条硬限制：

1. 第二条槽位常为 x4 或走芯片组，第二卡带宽可能只有第一卡的四分之一。
2. 无跨卡直连，通信只能走 PCIe。
3. 第二卡显存不是更大的空间，而是更热的专家缓存，模型逻辑仍是同一份。

| 策略 | 做法 | 适用 |
|------|------|------|
| 按层切分 | 层在两卡间粗粒度切开，各卡独立运行自己的层与专家缓存 | 单会话、低延迟优先 |
| 专家并行 | 两卡各持约一半专家的常驻副本，未命中的从共享主机内存专家池取 | 单会话、命中率优先 |
| 双实例数据并行 | 两卡各跑一个独立实例，共享主机内存中的专家池与记忆表 | 多会话、吞吐优先 |
| 禁止 | 每层同步的张量并行 | 会把慢链路放进每层关键路径 |

共享主存专家池是关键设计：双卡与双实例不各自复制专家与表，主机内存是共享资源，由统一页表管理并共享引用计数。

具体选择依据 G-08 的实测结果。

## 15. 瓶颈模型

理论上限：每秒解码 token 数约等于有效带宽除以每 token 字节量。

粗算，假设激活参数 6B 且全部命中：

| 权重精度 | 每 token 权重字节 | 显存带宽上限 |
|---------|-----------------|-------------|
| FP8 | 约 6 GB | 约 75 tok/s |
| IQ2_XS | 约 1.8 GB | 约 250 tok/s |
| NVFP4 | 约 3.3 GB | 约 135 tok/s |

参考引擎实测（双卡 77.2 至 86.3，单卡期 57.9 至 81.7 tok/s）远低于权重口径的上限，说明瓶颈不在显存带宽，而在三处：未命中专家走 CPU 的慢路径、PCIe 与同步开销、记忆表 IO（冷启动尤其明显）。

其中 CPU 侧已可量化：G-03 给出每 1% 的路由量落到 CPU 就多约 0.7 ms/token（本内核口径），G-09 的覆盖曲线意味着部署槽位下约 16.5% 要走这条路，即约 11.6 ms/token——与引擎自报的专家池 `pool 11.4 ms/round` 同量级（口径不同，不作等号）。这解释了参考引擎为何需要 8,106 个专家槽位加自适应换入。

该结论原有一个未闭合的缺口：上表只算了权重，未算 KV；262K 下 12 层稀疏注意力的索引器若要扫描全量 KV，这部分读取可能与权重同数量级。**该缺口已由 G-12 关闭**：引擎只读索引器选中的块，256K 原生上下文下 KV 块读 90.1% 命中显存、整个请求的内存侧 KV 读仅 213.3 MiB（约 1.7 MiB/token），远低于权重读。故本节结论不再受 KV 侧阻塞（对应风险 R-06 未发生）。

更细的步时间模型：

```
T_step ≈ max( T_gpu_compute, T_cpu_experts, T_pcie_budget × IO_amplify / B_eff ) + T_sync

T_gpu_compute ∝ 命中专家字节 / 显存带宽
T_cpu_experts ∝ (1 − h) × 专家字节 / 主机内存带宽
IO_amplify    = 1 / 接受率
```

推论：

- 命中率升高直接降低 CPU 侧耗时。
- 表行按需读的等待（上游实测 16 行串行约 2.10 至 2.61 ms/token）由「token 已知即发起」的重叠窗口与有界行缓存吸收；G-04 已排除提前一步的预取（见第 4 节）。
- 字节预算化避免某一步抢爆 PCIe 造成长尾。
- 接受率下降会按比例放大 PCIe 预算消耗与表行 IO 次数，验证窗口越长放大越大；G-13 实测该系数为 1.05 至 1.27 倍（接受率 0.786 至 0.940）。

## 16. 质量保障

端到端闸门（G-14）：

| 门槛 | 口径 |
|------|------|
| 困惑度 | 默认档相对参考档劣化不超过 1%（建议值；本平台尚未测——原生 pack 下取不到 logits 通路，见下） |
| 任务集 | pass@1 与工具调用成功率不低于参考档（需外部评测 harness） |
| 长文 | 长上下文评测不低于参考档（同上） |
| 贪婪解码 | 只适用于不改变数值表示的开关（归约顺序、图捕获等）。对 KV 精度档不适用：G-14 实测 KV 降档会改变贪心轨迹——int8 与 q4_0 在第 40 个 token、k8v4 在第 57 个首次分歧，序列一致率只有 0.078 至 0.111（见 [`../research/02-qwen3.8-flash-next.md`](../research/02-qwen3.8-flash-next.md) §4.1）。KV 档的验收改用困惑度与任务级判据 |

G-14 已经测得：四档 KV 的 decode 吞吐几乎相同（±2%），即该旋钮买的是显存而非速度；且这台机器上该引擎的逐位复现口径是 `--adapt-every 0 --pcie-frac 0`（只关自适应换入不够）。阈值里的困惑度、任务集、长文三条仍待补。

复合误差白名单以位宽组合为粒度，单旋钮降档与多旋钮同时降档是两种风险：

| 组合 | 权重 | 主 KV | 索引器 KV | 表行 | 备注 |
|------|------|-------|-----------|------|------|
| D1 默认 | IQ2_XS 或 NVFP4 | FP8 | FP8 | 4-bit | 须实测复合后仍过闸门 |
| D2 | IQ3_XXS | FP8 | 4-bit | 4-bit | 先降位置敏感的索引器 |
| E1 实验 | 三值或 2-bit | 4-bit | 4-bit | 低比特 | 禁止进入默认档 |

禁止权重与表行同时降到 2-bit 以下，两者都是每 token 必用的路径。

复合误差的上界只由实测决定，不允许由各项误差上界线性相加推出。

归约顺序与可复现性：结果由显存、CPU、核显三路累加归并，归约顺序不固定就无法逐位复现。本设计定为**按专家 id 全序**（升序）归并，落到两处实现：逐专家路径在 `src/experts/moe_layer`，一层一批的批量路径在 `src/experts/layer_dispatch`。两条路径的「取字节、算、累加」三步都按 id 升序做，路由给出的排名序只决定取哪 k 个、各占多少权重，不参与归并顺序。选它而不是排名序的理由：它不依赖路由并列的打破方式，三路各自算完直接按 id 并入即可，核显那一批的边界（哪几个专家落在核显上）也不必进入求和顺序。测试用结构判据钉住（两条路径的排序排列都在 scratch 的 `order` 字段里），因为合成夹具的值域太规整，换顺序求和仍逐位相同，靠浮点差别判会在夹具上变成空转。

## 附录 A 数据交换优化清单

把每一次数据搬动归入五类，逐类找漏。

别搬（消除搬运）

1. 权重保持压缩态在通道上，只在计算前一刻解压，禁止先解压到高精度再计算。
2. 冷数据直接映射文件，不经主机内存中转。
3. 未命中专家就地计算，不搬回显存。
4. 共享前缀在基数树中只存一份。

提前搬（预取与重叠）

5. 表行在 token 确定时即发起读，与 embedding 落位重叠（不做提前一步的预取，见 §4.1）。
6. 专家提前一至两步按出现概率预取。
7. KV 按块提前于消费点取入。
8. 全部预取与当前步计算重叠，不在关键路径上阻塞。

一次搬够（批量化与对齐）

9. 同一步内的取专家请求聚合为连续大块读；表行请求只能按行 id 去重，不能合并为连续读（见 §4.2）。
10. 传输粒度与专家块、页大小对齐，避免跨块散射。
11. 减少 IO 次数优先于减少字节数。

搬的时候顺便算（融合与就地处理）

12. 反量化融进矩阵乘与注意力核。
13. 路由的归一化、取前 k 与聚集融合。
14. 门控残差的四分支门控融合。
15. 累加归并在同一缓冲区完成，不额外同步。

元开销（最容易漏）

16. 同步点每步只有一次。
17. 解码步的稠密部分用图捕获。
18. 启动时一次性分配，解码步内不分配。
19. 专家槽位按缓存行对齐，避免伪共享。
20. 线程按核心类型分池，不混用。
