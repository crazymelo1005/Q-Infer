# 引擎规格

本文定义引擎各子系统的实现规格。需求与验收条件见 [requirements.md](../requirements.md)，模块边界见 [overview.md](../overview.md)，接口契约见 [interfaces.md](interfaces.md)，必须先测的假设见 [gates.md](gates.md)，风险见 [risks.md](risks.md)。

硬件约束以环境 2 口径为准（[hardware.md](../hardware.md)）：单卡 16 GB 显存、448 GB/s 带宽、约 70 GB/s 主机内存带宽、PCIe 5.0 x8 约 31.5 GB/s、NVMe 顺序读约 7 GB/s、CPU 仅有 AVX2。单卡是本设计的硬下限，双卡为扩展形态（见第 14 节）。

## 2. 设计原则

1. 容量优先于速度。任何优化先问它是否增加了常驻需求。
2. 预测优先于反应。能在上一步算出来的东西，不要等到需要时按需加载。
3. 并行优先于串行。未命中专家与命中专家并行计算，预取与计算重叠。
4. 能确定的就不用猜，猜的部分单独标注。表行索引由已生成 token 确定性算出；路由共现只是概率性先验。两者置信度不同级，确定性请求按必需分配预算，概率性请求按剩余额度分配。
5. 质量不妥协。加速手段要么可证明不改变输出分布，要么误差有界且可测。
6. 可标定。性能相关的常量由自动标定确定，不硬编码。

## 3. 三层存储与流调度

职责：把所有逻辑块映射到介质，并保证计算所需的数据在需要之前就位。

### 3.1 统一页表

每个逻辑块维护所在层、物理偏移、引用计数、世代号、热度与预取状态。所有子系统通过页表申请与归还，不直接持有指针。字段与操作见 [interfaces.md](interfaces.md) 第 2 节。

驱逐前引用计数必须归零；预取一旦发出即锁定到消费完成，防止中途被驱逐。

### 3.2 字节预算仲裁

每步 decode 有一个固定的 PCIe 字节预算 `B_step`，由标定得到。全部过 PCIe 的搬运竞争同一预算，优先级自高到低为：本步必需 KV、本步必需表行、预测性专家。

预算不足时，预测性请求被主动放弃并计入迟到数，绝不为它插入额外的同步点。三类流量的范围见 [overview.md](../overview.md) 第 5 节。

实现见 `src/scheduling/budget_arbiter`：必需项按类别优先（KV 先于表行）一律准入、超出预算的部分记 overspend；预测性项按收益 ÷ 字节降序贪心，放不下就弃并继续尝试后面的。仲裁之上的两件事在 `src/scheduling/step_budget`：每步预算由机器画像推导（`pcie_h2d × 步长 × io_share`，环境2 得 186.8 MiB，字段与换算口径见 [S-52]）；计划层每步的四类需求（[interfaces.md](interfaces.md) 第 4 节）里过 PCIe 的三类转成请求送仲裁，仲裁结果再折成每步观测（interfaces 第 7 节）——观测里的预算用量、超支、迟到三笔账分开记，是引用性能数字的唯一取数口径。

### 3.3 介质层级与零拷贝

- 热数据在显存，温数据在主机 pinned 内存，冷数据在 NVMe。
- 冷数据用 `mmap` 直接映射，不经主机内存中转；异步预取使用 `io_uring` 与内存建议接口。
- 权重在传输通道上保持压缩态，只在计算前一刻解压，避免解压后的高精度副本再走一遍内存带宽。
- 热专家常驻页锁定内存，避免换页抖动。这是对上游做法的改变，不是复述上游：参考引擎自报常驻区 `arena_mib 17,395`（约 17 GB），但实测其常驻区在共享内存里且可被换出（进程 VmRSS 31.25 GiB、换出 2.61 GiB、系统 swap 已用 91%，见 [`../research/01-strata-engine.md`](../research/01-strata-engine.md) §10.1）。代价是 pinned 页不可换出，会加剧内存不足时的整体压力。

### 3.4 主机内存预算

约束：主机内存标称 64 GB，可见 61.0 GiB；参考引擎实测已用 73%（44.6 / 61 GiB），另一时点约 90%，可支配余量仅 6 至 16 GiB。

本设计需要的常驻对象与外挂表同量级且方向相反，因此内存预算是硬门禁（G-11）。

| 项 | 目标上限 | 超预算时的处理顺序 |
|----|---------|------------------|
| 记忆表行缓存 | 默认 1,048,576 行（IQ4_NL 约 90 MB） | 1，减小缓存行数至 0（关闭） |
| 共现图 | 需给出稀疏密度上限 | 2，降维或退化为会话级 top-K |
| 记忆表中频行内存层 | 4-bit 表 28.8 GB 中的中频部分 | 3，中频行并入 NVMe 层，只保显存热行 |
| 专家 pinned 区 | 由命中率目标反推 | 4，缩小常驻区，未命中比例上升后退守第 5 节 |
| KV 池（主机侧） | 见第 7 节 | 5，仅涉及正确性与长文能力时最后处理 |
| 机器画像 | 小于 1 MiB | 不降级 |
| 视觉编码器主机张量 | 约 1.4 GB | 按需载入载出，不常驻 |

降级顺序固定为自上而下。理由：先牺牲预测性与概率性收益，再牺牲分层深度，最后才动涉及正确性的部分。

按真几何把这张表算出来（`tests/test_memory_plan --g11`，纯算术）：行缓存 90 MiB、画像 0.2 MiB，而表内存层与专家 pinned 两项都是 0——前者被 [ADR-007](adr/ADR-007-ngram-table-on-demand-read.md) 砍掉、后者本设计不 pin 而是 mmap 直读走页缓存（§6），这两条正是本设计主机占用远小于参考引擎（44.6 GiB RSS）的原因。唯一随规模增长的是 KV 的权威副本（`src/dense/kv_store`，上下文 × 1056 B × 12 层 × 并发）：4096 / 1 是 0.14 GiB、32768 / 8 与 262144 / 1 都是 3.18 GiB（与画像的 `kv_full_mib 3168` 独立对上）、262144 / 8 是 24.84 GiB。故 262K 单序列与 32K 八并发都在 6 至 16 GiB 余量内，262K 八并发超——那一档的杠杆不是降级常驻窗而是**拒绝新序列**（§5：调度器必须同时观察两个池的余量，任一不足即拒绝），因为权威副本的大小由上下文与并发定，与常驻窗口无关。G-11 据此判为通过：表已填齐，超限的边界与处置明确。

槽位数在专家与 KV 常驻窗之间的配平规则也已落地（`src/scheduling/memory_plan`，纯函数，interfaces §8 那条待定项）：KV 那一侧的硬地板由几何算出来——一次 decode 步要同时装下本步刚写的页与本步要读的页，即 `1 + ceil(选择宽度 / 页大小)` 页（真模型选择宽度 2051 个 cell → 514 页 = 2056 cell；`kv_window` 的合成夹具里 4 个槽位正好等于这个数、再少一页就报错，规则算出来的正是那条边界）。分法是固定的：先削专家（降到 0 即退守 CPU 路径，§8.5），还不够才削 KV 常驻窗（以地板为限），连地板都装不下就明确拒绝而不是静默配一个装不下的数。池固定 2 GiB、单序列时它给出的弹性：上下文 1024 / 4096 / 32768 / 262144 分别留 28 / 27 / 22 / 0 个专家槽位——上下文越长，KV 越挤占专家。4 条变异全致死（顺序破、不查地板、地板公式少一页、削 KV 不按池限制）。运行中按计划动态重配属于设备侧那一半。

## 4. 记忆表读取

问题：外挂表远超显存。一个 token 要读 16 行（每行 90 字节的 IQ4_NL 行，共 1,440 字节），行索引由该 token 及其前两个 token 经 n-gram 哈希唯一决定，因而是确定性的。

本节曾按「提前一步的显式预取加双缓冲」设计。该设计已被门禁 G-04 否定：表行访问在去重后既无顺序性也无局部性——16 个头把表切成 16 个互不相邻的约 20,000,000 行区间，一个 token 的 16 行必然异区间异页，顺序性在结构上为零；行级重复虽随上下文增长到约 0.59，但属长距离复现，复用距离中位数达上万次请求。据此退守按需读加有界行缓存，决策见 [ADR-007](adr/ADR-007-ngram-table-on-demand-read.md)，实测见 [`../research/02-qwen3.8-flash-next.md`](../research/02-qwen3.8-flash-next.md) §3.2。

### 4.1 解码期

1. 按需读。token 一经确定即算出其 16 个行索引并发起读，读回后参与该层 embedding 相加。不做提前一步的预取：G-04 显示下一步的行与刚读过的行几乎不复用（16 请求窗口内的重复只占 0.14%），提前一步得不到命中。
2. 重叠窗口。发起时刻取在 token 已知时，收集时刻取在该层消费之前，使读取与 embedding 落位重叠。这是上游已有的做法，本设计沿用，不承诺更多提前量。
3. 有界行缓存。按「8 路组相联、按行号哈希定组、组内轮转替换」保留最近读过的行，默认 1,048,576 行（IQ4_NL 约 90 MB）。它吃下长距离复现：G-04 实测该容量在 4K / 32K / 262K 档的命中率为 0.28 / 0.42 / 0.58。缓存容量计入内存预算（§3.4）。实现见 `src/storage/row_cache`。
4. 不允许近似。表行是精确输入，缓存未命中必须阻塞等待，其能否藏进一个步长由 G-10 判定。G-10 已实测（环境2）：16 页随机读 + H2D 的往返 P50 1.48 ms、P99 2.10 ms，而 decode 步长 P50 12.74 ms——约 6 倍余量，紧张内存 lane 下同样成立，故按需读成立（见 [`../research/02-qwen3.8-flash-next.md`](../research/02-qwen3.8-flash-next.md) §3.3）。

行反量化的实现与回归见 `src/kernels/iq4nl`：IQ4_NL、一行 90 字节、分裂式半字节序（按交错读会得到一组可信但错误的值）；其正确性用模型真实字节与手算样例两路钉住。整条装配（token → ngram 哈希 → 预算仲裁 → 命中行缓存或读表 → 反量化 → 按 head-slowest 拼 2560）在 `src/ple/row_path`，表行来源可注入（真模型上是 `artifact::GgufTable`）；行号越出表范围即失败，不静默读别的行。真表上已跑通：分片2 的 `per_layer_token_embd.weight`（320,001,536 行 × 90 字节），5 个 token 全冷读 80 行、行号全部在范围内，且第 0 个 token 的 16 个行号在独立的 Python 实现（`measure/ple_row_oracle.py`）上复算，逐头的 L1 一致。预算按每个 token 一轮累计：必需的表行即使超预算也全部准入（记 overspend），一条都不丢。

表行的下游是并入残差栈的那一块（第 1 层专属，见 [S-63]）：`src/ple/block` 收 `emb`（表行拼出的 2560）、`hidden`（hc 条流的残差栈）与 9 行历史，出 `out = hidden + gated + silu(conv)`——`key/query` 两个投影各过一条逐流 RMS 归一，逐流点积得到 4 个带符号平方根门，`value` 在流上广播之后再过一次归一，最后是 4 抽头膨胀卷积（tap 0 读最远那行、tap 3 读当前这条归一）。引擎把三处「写错了也长得对」的地方单列过注释，本实现的夹具就按它们各算一遍错读法：卷积的输入必须是 `normalized` 而不是 `gated`（相对偏离 0.093）、`ple_conv1d` 是 ggml 原生的 `k + 4·c` 而不是转置（1.52）、历史是 row-fastest 而不是通道慢（0.814）；另加两条本地的（门不带符号的平方根 0.051、结果不套 silu 0.747）。两处与 `dense/norm.hpp` 的 `rms_norm_rows` 不能复用：平方和要「乘积先按 f32 舍再放宽」（不是先放宽再相乘）、尺度要 f32 的 `1/sqrtf(mean+eps)`。历史推进按引擎的形状留在调用方（块是它输入的纯函数），逐通道错位拷贝——夹具里把「整块 memmove」那条错法也照出来（144 个位置差 15 个）。

表行那条路径的下游是并入残差栈的那一块，它现在也接进了步循环。接线按引擎 `block_layer_pre` 的形状（[S-63]）：配置（六张张力的登记与常驻权重 + 表行来源）由调用方建、以指针挂进 `StepConfig`，`prepare_step_scratch` 只把它挂到它自己那一层（于是「挂错层」不可能悄悄发生），那一层跑之前就地写 `R`、跑完推进历史；别的层与「没配」一律一步都不跑。表行向量分两半，与引擎一致：`run_token_step` 负责按当前 token 与它前面两个取表行（前驱存在会话状态里，跑完才推进一格），调用方也可以自己把 `emb` 填好再跑（引擎那侧的 `ple_issue_token`/`ple_finish_token` 在驱动侧、图里只有 `ple_block`，就是这么分的）；配了 PLE 却没喂 token 会明确报错，不静默跳过——静默跳过等于在算另一个模型。表行向量固定 2560 宽（16 头 × 160），故自动取表行那条要求 `n_embd == 2560`（真模型正是），不相等就明确失败，不截断不补零。合成夹具上的判据：带张力与不带张力两份模型逐位一致（有张力但没配，等于没跑）、配上后 logits 相对偏离 0.033、历史每步「左移一格并追加」、同一组 emb 两次独立跑逐位一致、挂到第 0 层偏离 1.4、两条明确报错各被触发；4 条变异全致死（不推进历史 / 不在第一段之前跑 / 没喂 token 也照样跑 / prev 写错格）。真权重（部署那份、3 个 token、真表行）：含 PLE 的 logits |值| 合计 372679（不含 177087）、argmax 由 69906 变 66214、表行 48 行 48 命中；逐 token 取的表行向量与「整段重算」逐位相同 7680/7680——这条把前驱的顺序与推进时机钉在行号这一级（合成夹具照不到：它的 n_embd 与向量宽不一致走不了自动取表行那条），prev 写错格那条变异就是在这条上被杀掉的（变异体 2560/7680）。

真权重上对块本身的核验走逐段对照而不是只看最终值：`measure/ple_block_oracle.py` 自读两份 GGUF 的六个张力（key/value 是 BF16、三条 gamma 是 F32、卷积核是 F16），按 numpy 的写法重算一遍并把输入与逐段期望值写成夹具，`tests/test_ple_block --model … --oracle …` 逐段比相对 L1。部署那份的分片1 上七段落在 1.0e-08 至 5.1e-07（纯求和顺序差；结构性错读是 O(1)，两者隔五六个数量级）。这个做法第一次跑就抓到了 oracle 自己的两处错：漏了「激活也按 bf16 舍入」这条契约（key/value/gated/normalized 齐刷刷差 1.5e-03），以及 `ple_conv1d` 按 (4, 10240) 行主序重塑等于转置读（conv 那一段差 11 倍——修好后 |conv| 从 83161 掉到 8132，这个量级变化本身就是判据）。引擎自己那份 parity 的逐段数搬不过来：它的权重来自自带的 pack（key 是 S2、value 是 F32），与这两份 GGUF 的 BF16/F16 不是同一份；它把 ggml 图捕获成的夹具也不在盘上。故这一段的口径是「同一公式的第二种写法 + 逐段 + 1e-4」，写在 [S-63] 与 oracle 的文档串里，不假装成更强的口径。

### 4.2 预填期

1. 与分块对齐。按每块不超过 8,192 token 切分，逐块算出该块的全部表行索引。索引合并只用于去重与排序，不能合并为顺序大块读：G-04 显示一个 token 的 16 行落在 16 个相距约 1.8 GB 的区间，跨 token 亦然，不存在可合并的相邻性。
2. 块内去重。块内不同位置的键存在重复（G-04 全序列重复率 0.28 至 0.59），先按行 id 去重再取，减少 IO 次数。此处减少次数优先于减少字节。
3. 首块没有重叠窗口。第 1 块无前序 token，只能阻塞读取。因此冷启动改善的上界就是首块的表行读取时间，不承诺更多。
4. 本路径受 G-04 已给出的结论约束（去重后为近似随机访问），故不做顺序化改造，只做去重与批量化。

## 5. 专家缓存与共现感知替换

问题：参考引擎的专家缓存是固定槽位加持续学习，没有自适应淘汰策略，且命中率会随工作集切换波动（环境2 实测单请求 0.935 至 0.975，长提示下可低至 0.794）。

命中率的上界由路由集中度决定，不由缓存策略决定。策略只能逼近上界，因此本子系统受门禁 G-09 约束。

G-09 已实测该曲线（环境2，解码路径，164.6 万次查表）：top-5,000 对覆盖 0.680、部署配置的 8,106 个槽位覆盖 0.835，且饱和很慢（99% 需 16,674 对，占全表 68%）。因此「上界」是一条收益递减的慢曲线，而非硬天花板：共现与会话亲和改变的是哪些对常驻，抬不高曲线本身。口径提醒：引擎会话内自报的 94% 至 97% 含自适应换入与跨请求前缀复用，与本口径不可混用（[S-34]、[`../research/01-strata-engine.md`](../research/01-strata-engine.md) §4.1）。

G-05 给出槽位的实测量级：部署配置（双卡、`--batch 4`、`--kv-resident 32768`）下两卡合计 11,967 个槽位（主卡 6,529，8,816 MiB），`--batch 4` 的槽位会话另占主卡 2.05 GiB——并发是用槽位换来的。G-06 给出命中率到吞吐的斜率：同一提示内约 +1.4 tok/s 每 +1 点命中率，且跨提示不可比（[`../research/01-strata-engine.md`](../research/01-strata-engine.md) §4.2）。两条合起来说明：本子系统能动的杠杆是「把哪些对放进那不到一万二千个槽位」，而不是抬高曲线本身。

设计：

1. 共现图。维护专家对在同一 token 或同一会话内被一起激活的统计，作为替换策略的输入。
2. 会话亲和。会话开始时按任务类型预载对应专家簇，而不是使用全局热榜。
3. 替换策略可插拔，在线评估，每次替换时用近期命中率做比较。
4. 槽位弹性。槽位数在 KV 常驻窗口与专家数量之间动态配平，见第 7 节。

实现与实测。槽位与替换策略见 `src/storage/expert_cache`：组相联，键是 (层, 专家)，策略可插拔（`FifoPolicy` 复刻参考引擎与本仓库行缓存那种组内轮转、`LruPolicy`、`CooccurrenceAwarePolicy`）。本类只管谁占槽位，不管槽位里的字节——字节按同一个键登记进 `storage/page_table`，故驱逐前那两条不变量（引用计数归零、预取不在途）由调用方给的 evictable 回调守住：组内全都不可驱逐时返回 `kMissBlocked`，不硬换。读取路径把三者接起来在 `src/experts/expert_source`：一个专家的三矩阵从表里读出来后就地组装进常驻区（三矩阵在文件里不连续，故按各自的逐专家步长分别读），驱逐时同时退掉常驻区与页表条目（`PageTable::remove` 也守那两条不变量，引用计数不为零或预取在途时拒绝）。两条退化语义是刻意的：字节预算用尽后不再准入、改走临时缓冲（缓存装不下该退化，不让正确性受影响）；组内全不可驱逐时这次不准入而不是硬换。`pin`/`unpin` 走页表的引用计数，被 pin 的专家在期间不会被换出。共现图见 `src/storage/cooccurrence`：容量是显式参数（engine §3.4 要求给出稀疏密度上限），规则是「每 2^20 次观察把全表计数减半、归零的条目退场」加「衰减后仍满则拒收新对」——这两条都是 O(1)，替代了最初那版「满时全表扫描找最弱的一对」（后者在 28,080 条记录的真轨迹上把一次重放从十几毫秒拖到 14 分钟）。

离线重放在 `measure/expert_cache_replay.cpp`（读参考引擎 `--dump-routing` 的轨迹，格式见 [S-34]）与编排脚本 `measure/expert_cache_sweep.py`，记录 `measure/results/20261010T184146-expertcache-环境1.json`。四条结论，口径是**单条轨迹内部**的自适应命中率（与 G-09 的全局静态覆盖不是一个口径，不可混用；重放是确定性纯计算，写在环境1 或环境2 不改变结果，轨迹来自环境2）：

1. LRU 高于组内轮转。部署槽位口径（8,106 / 11,967、8 路）下三条轨迹分别高 3.0 / 2.4 / 1.9 与 2.2 / 1.9 / 2.4 个百分点——参考引擎那种固定槽位加持续学习确实留了约两个点在这里。
2. 相联度是与容量独立的旋钮，且更划算：8,106 槽位下 1 路 0.7097、8 路 0.8525、64 路 0.8705（trace-p0）；11,967 槽位 2 路（0.8468）仍低于 8,106 槽位 8 路（0.8525）。
3. 共现感知策略与 LRU 的差在 ±0.01 个百分点内、方向还不一致，即共现图作**替换输入**这一形式本轮不支持。
4. 换形式再测一轮（把共现用在「哪些对放进槽位」：留出法下用去一半的轨迹统计排序、预载后评另一半）仍然没有增益：中心度排序与频次排序**逐位相同**，且这是结构性的——固定 top-k 时一次激活恰好带来 (k−1) 个伙伴对，故 `中心度 == (k−1) × 边缘频次`，共现图作排序输入不含超出边缘频次的信息（这条不变量有测试钉住，见 `tests/test_expert_cache`）。**但预载本身是真收益**：与冷启动比，预载（不论用哪种排序）在 11,967 / 8,106 槽位下高 3.9 至 5.5 个百分点——engine §5 第 2 条「按簇预载而不是用全局热榜」的**预载**这一半成立，**「按簇」这一半不成立**（簇排序退化为频次排序）。要让共现图真正产生增量，需要用到条件结构（同一个键在不同场合搭配不同伙伴）而边际频次抓不到的形式，那要单独设计并单独测；在此之前不把 §5 第 1 条当作已获收益的设计。

读取路径已在真模型上核过：`src/experts/expert_source` 接进 `experts/moe_layer`（`cache_slots > 0` 才启用；`cache_ways`、`cache_byte_budget`、`cache_policy` 同层可配）。部署那份的层 0 与层 12 各跑 32 个 token，缓存路径与直读路径的逐元素差为 0；常驻 10 个专家占 14.404 MiB，即 1.44 MiB/专家，与画像由 `cache_mib ÷ cache_slots_total` 反推的 1.35 MiB/专家相合（两条独立路线）。口径：手工入口只对激活做小扰动，路由其实没换专家，故它给的是接线与逐位一致的证据，不是命中率结论——命中率问题由下面的离线重放回答。

主机侧的专家缓存不是提速手段（环境2 实测，48 层、同一份 x 连跑 3 步，唯一变量是把主机参考路径的 `cache_slots` 从 0 改成正数，诊断入口 `--cache-slots N`）：给到 128 槽/层时这一步观测到驱逐 0 次、命中率 0.594（同一条 x 连跑时 MoE 的输入逐层在变，故每步仍会碰上新专家），20 线程下 MoE 那一段却从 495 至 551 ms 变成 603 至 626 ms，稳态步从 892 至 936 ms 变成 1016 至 1043 ms；给到 32 槽那种口径也一样慢（603 ms、驱逐 37 次）。即主机上那约 600 MB/步的专家字节本来就躺在页缓存里、直读已经够快，进了缓存反而多出页表登记、钉住与（未常驻时）拷进批内缓冲这笔账。故这套子系统的价值在容量记账与设备/主机之间的搬运与预取，不在主机侧的速度；要把主机这条 MoE 弄快只能动它的计算路径（见第 6 节）。两边的 logits 开与不开逐位一致（248320/248320），即缓存对数值透明这一条在整步上也成立。

命中率不作为优化目标，只作为观测量。任何引用命中率的结论必须同时给出 PCIe 侧占比与空闲显存，否则不成立。

## 6. 异构执行

职责：让命中专家、未命中专家、KV 搬运与表行读取在同一时刻都在推进。

显存侧执行稠密部分（注意力、门控残差、路由器、共享专家、输出头、MTP 层）与命中专家，全部走融合内核。解码步的稠密部分用图捕获消除启动开销。

CPU 侧执行未命中专家，用 AVX2 量化内核：

1. 量化直接参与计算。码本解码融进 GEMM，避免先反量化到高精度再计算，否则内存带宽消耗放大约四倍。
2. 线程池按核心类型分配。本平台为 8 个性能核加 16 个能效核。G-03 实测单核：P 核 2.81 GMAC/s、E 核 2.29（4 位档码本内核），P/E 仅 1.23 倍，且 16 个 E 核的合计（33.4 GMAC/s）高于 8 个 P 核（21.1）。故「两类核不混用」是策略选择（避免长尾由慢核决定），不是达到合计算力的必要条件。
3. 归并。CPU 与 GPU 的结果在同一缓冲区按专家槽位累加合并，避免额外的同步。
4. 同步点最小化。每步只有一次显存与主机之间的汇合。

主机侧的按行并行已落地（`src/scheduling/thread_pool`）：十一个量化档与注意力那几处投影都从 `experts/ffn` 的 `run_gemv` 这一个分派点走，故只在这一处按行切块就覆盖了两边；它只切行、不切归约维，所以并行版与单线程逐位相同（`tests/test_thread_pool` 钉住：同一份真模型字节与激活，单线程对 8 线程位相同 2560/2560）。池子是进程级单例、默认关（`set_pool_threads`），故既有测试与 CI 仍在单线程下跑。环境2 上的读数（部署那份，48 层、同一份 x 连跑）：稳态单线程 2610 / 2617 ms 对 20 线程 1476 / 1470 ms，约 1.8 倍，而每一步的 logits 都逐位相同；8 线程与 20 线程差别不大（0.55 倍对 0.56 倍，P 核先够用）。

设备侧已开工，四块内核合起来覆盖了部署那份**一个专家的全部三档**：Q2_0（down 全 48 层）、IQ2_S（gate/up 的 34 层）、IQ2_XXS（gate/up 的 11 层）、IQ1_M（gate/up 的 3 层），分别在 `src/kernels/cuda/q2_0_gemv.cu`、`iq2s_gemv.cu`、`iq_gemv.cu`（后两档同处一个 TU：配对物同为 Q8_K、脚手架相同）；语义都照本仓库主机那份写（`src/kernels/` 的同名档），并在真模型字节上逐行对照（`tests/test_q2_0_cuda`、`test_iq2s_cuda`、`test_iq_gemv_cuda`，只在 `-DQINFER_ENABLE_CUDA=ON` 时构建）。为什么不复用上游的 CUDA 实现：ggml 那两条（`ggml/src/ggml-cuda/mmvq.cu` 与 `vecdotq.cuh` 的 Q2_0 与 IQ2_S 分支）都把权重配的是 Q8_1 激活——带 d 与 s 两个尺度、整数累加时要四舍五入——而本仓库的激活搭档是 Q8_0 与 Q8_K，配对物不同，抄过来就是另一套数值行为。

环境2（sm_120，CUDA 13.2）上的读数：把真模型字节 tile 成 2560 行 × 每行 10 块（正是部署那份 down 的几何）后，设备与主机逐位相同（2560/2560 行，L1 相对差 0），对独立双精度参考 5.2e-08；两条错读法——漏掉码的 −1 偏移、字节内位序取反——分别偏离 0.846 与 0.494，即这两处一旦读错必被抓住。同几何下一次调用的耗时：主机 550.5 µs（约 3.0 GMAC/s，与 G-03 的单核量级相合）、设备 98.9 µs，设备侧约 5.6 倍——但这个入口每次都要把权重搬上去，故那是含搬运的下界，不是常驻后的数字。变异测试 5 条里 4 条致死；存活的那条是行越界守卫，当前夹具的 n_rows 恰是块大小的整数倍，越界写落在同一段显存里、主机侧观测不到，故该守卫按一般的 n_rows 保留。IQ2_S 那块同法核过：真字节 tile 成 640 行 × 每行 10 块（gate/up 的几何）后设备与主机逐位相同（640/640 行，L1 相对差 0），对反量化双精度参考 7.77e-08；计时主机 522.7 µs、设备 188.3 µs（含搬运，约 2.8 倍）；它的变异 4 条全致死（尺度漏掉乘 2、qh 的两位从低位取、丢掉最后的 0.125、丢掉块的 fp16 尺度），即这四处一旦读错必被抓住。IQ2_XXS 与 IQ1_M 两块同法核过：真字节 tile 成 640 行 × 每行 10 块后设备与主机也都逐位相同（各 640/640 行，L1 相对差 0），对反量化双精度参考 7.37e-08 与 3.02e-08；计时 IQ2_XXS 主机 473.1 µs 对设备 141.1 µs、IQ1_M 462.5 对 204.7 µs（含搬运）；两块各 5 条变异全致死（尺度漏掉加 1、符号索引反序、qh 高位取错端、忽略 delta 符号、丢掉 delta 项）。

再往上一层，设备侧已经能算完一层的一批专家：`src/experts/cuda/expert_ffn_cuda`（`ExpertFfnDevice`）在设备上给一层开一个权重常驻区（槽位数由调用方给，`upload` 一个专家只搬一次），`run` 把 gate GEMV → up GEMV → silu·up 并就地量化成 Q8_0 → down GEMV 串在同一个流上，中间不与主机同步（interfaces §8.4 那条约束）；激活在主机侧量化（复用 `quantize_input`，不另写一份算术），h 的量化在设备上做、照主机 `kernels/q8_0` 的量化器逐句对应。支持范围是明确的，不满足就在 init 里失败而不是猜：三矩阵的档都要有设备内核，且 down 的激活搭档必须是 Q8_0——这正好是部署那份模型的形状（down 全 Q2_0、gate/up 是那三档）。环境2 上的读数：一份合成但真字节的夹具（ffn 64 / hidden 256，gate/up 用 IQ2_S、down 用 Q2_0，字节取自两份真模型 oracle）上，两个专家各一次前馈与主机 `expert_ffn` 逐元素位相同（512/512，L1 相对差 0），常驻的观测量 `uploaded_bytes` 在第二次 run 后不再增长；5 条变异全致死（丢掉 silu、h 的量化漏掉尺度、down 用错激活、槽位偏移没乘、常驻记账不记）。再往上一层就是组：`src/experts/cuda/cuda_worker` 把上面那个常驻区包成工人（一块卡一个实例、一层一片常驻区、`submit` 只在该专家还没常驻时搬它），`cuda_group()` 给出它的能力表（四块内核覆盖的档）。按卡分工见同一处的 `cuda_owner_of` 与 `CudaGroupFleet`：前者按 [ADR-004](adr/ADR-004-consumer-dual-gpu-no-tensor-parallel.md) 的层切分把层**连续地**分给各卡（层间只传残差栈，切口越少越好），后者每张卡起一个工人与一个组、每层给出「本卡的组在前、CPU 兜底组在后」的候选表；数据格式与代码路径仍只有一套，卡数只改变分配。环境2（两张 5060 Ti）上的读数：夹具里两张卡各算一个专家都与主机逐位一致；整模型一步按 24/24 切开后，logits 仍与主机逐位一致（248320/248320、L1 相对差 0），两张卡各 24 批 / 240 个专家。定位时还抓到一处同类的静默错：常量内存是逐设备的，而「表已上传」的标志当时是逐进程的——卡 0 传过之后卡 1 永远不再传，于是卡 1 的内核读空表、算出来全是垃圾；改成按设备记账后消失（教训：状态的作用域要与它真正的作用域一致）。

一步各段的实测（环境2，部署那份，48 层、20 线程的池子、最后一步）：把一组 hc_* 解成 F32 的 load 约 0 ms、gr_read 348 ms、注意力 516 ms、MoE 552 ms、gr_write 约 0 ms，其余约 0.4 s 是 embedding、输出头与分派。与设备侧同口径对照（稠密都开 20 线程，只差谁算这批专家）：48 层稳态主机 1433 / 1464 ms 对设备 1497 / 1466 ms——设备与 20 个核的池子打平，不再更快（单线程分母下看着快，是因为那一轮的稠密部分是单线程跑的）。由此两条：一是设备侧今天的价值不是速度，而是把主机核让给稠密部分；要有净收益，得让它的活与主机的活重叠（步内只有一个汇合点，那就要跨层流水），或者把内核做得更快（批式、常驻、融合）。二是最大的单段是注意力（约 36%）。把它再拆开（48 层、单线程）：GDN 的三个投影（含每步重新读这些权重）685 ms、其余（前段/递推/收尾，含 QSA 的 205 ms）415 ms。685 ms 与 G-03 的单核吞吐正好对得上：该层三个投影合计 2.06 GMACs，按实测的 2.81 GMAC/s 每核算是 735 ms——当时据此认为主机这条路卡在**码本 GEMV 的算术**上，读被页缓存吃掉、与计算重叠（下一条的 A/B 表明那些读并不免费）。由此第三件事：**按行并行只给出约 1.8 倍**（20 个核），远不到线性，而这一步里可并行的部分（注意力 1100 + MoE 984）占了绝大头——这个倍数是眼下最大的一个杠杆，先弄清为什么上不去（分派的固定开销、块粒度、还是访存带宽在 20 路并发下实际只有 30 GB/s 量级），比继续搬算子更能说明问题。设备侧那四块内核在这样的小尺寸下与 20 个核打平（见上文），所以把稠密部分搬过去也不会凭尺寸就赢。

三条嫌疑分开量过（工具 `measure/thread_pool_bench.cpp`，环境2、24 线程）：纯流式读 1 线程 18.3 一路到 16 线程 58.0 GB/s 见顶；一次 `run_rows` 的固定开销约 20 µs（一步约一千二百次提交，合 24 ms）；真实的逐行 GEMV（Q2_0、10240×2560、7.4 MiB 权重）1 线程 3.19 GMAC/s 到 24 线程 33.3（10.4 倍）、9.36 GB/s，离带宽天花板很远。故池子与内核的伸缩都是好的——整步只快 1.8 倍、那 685 ms 的投影段，都不是这两者的问题。把两组数对起来只剩一个解释：那三段投影里的读——每一层每一步都把 attn_qkv / attn_gate / ssm_out 重新从文件读一遍（36 层约 1.16 GB/步），它不随线程数缩小。按流式读的 58 GB/s 算这只要 20 ms，而实测那一段是 685 ms 减去 GEMV 该有的约 54 ms——即读的实际速率在 2 GB/s 量级，走的是 NVMe 而不是页缓存（20 GB 权重加 35 GB 专家的常驻工作集，在这台 61 GiB 的机器上装不下，页缓存被反复挤掉）。

让这批权重常驻已落地：GDN 的三个投影、QSA 的四个投影与四个 norm、GR 的两组各三个投影都按层号缓存在该层的 scratch 里，同一层只在第一次调用时读，换层则重读。记账的是层号而不是「缓冲空不空」——同一份 scratch 跨层复用时，按空不空记账会把上一层的大权重当成这一层的；生产路径每层各持一份 scratch 恰好掩盖了这个错，故 `tests/test_gdn_layer` 与 `tests/test_qsa_layer` 各用「两层共用一份 scratch」的用例把它钉住（变异测试里把守卫改成「永不重读」或「缓冲空不空」都被抓住；改成「每次都重读」存活，那只是性能退步，不违反不变量）。环境2 上的读数（48 层、同一份 x 连跑 3 步，唯一变量是这两句守卫）：20 线程下 gr_read 349 / 注意力 517 / MoE 517 ms 对 346 / 301 / 495 ms，稳态步 1433 / 1492 ms 对 1203 / 1218 ms（约 16% 到 18%）；单线程下 GDN 三个投影 687 对 545 ms、QSA 209 对 163 ms，稳态步 2633 / 2637 对 2433 / 2437 ms（约 7.6%）。省下的远超按页缓存速率估的二十毫秒，印证这些读走在 NVMe 上；20 线程省得更多，与「并发读与算争同一条访存路径」相符。MoE 那段作为对照没动（984 对 985 ms），整步 logits 仍与主机逐位一致（3 步内 248320/248320、L1 相对差 0）。相位图因此变成 20 线程下 load 0 / gr_read 346 / 注意力 301 / MoE 495 ms：最大单段换成 MoE，注意力退到第二。

紧接着的一块是门控残差：它的两个投影（down / up）与 inject 一直是手写的标量循环（double 累加、逐元素按声明精度取值），没接池子，而每层会被调两次（attn 前与 ffn 前），在 20 线程的步长里占了约四分之一。现按输出行并行：切法与 `experts/ffn` 的 `run_gemv` 同一口径——一行一个独立点积、行间无依赖，故并行版与单线程逐位相同；`tests/test_gated_residual` 用真模型几何（N 2560 / hc 4 / lr 320）钉住这一点，并先断言这个几何下切块确实多于一块（N 8 / lr 5 那种规模切不出第二块，用例会空转）。环境2 上的读数（48 层、同一份 x 连跑 3 步，唯一变量是这两处是否进池子）：20 线程下 gr_read 361 ms → 69 ms、稳态步 1215 / 1288 ms → 927 / 898 ms（约 27%），按行并行的整体倍数也从 1.8 倍提到约 2.6 倍；单线程那条作为对照没动（339 对 347 ms，串行路径一字未改，故这个差就是池子带来的）。整步 logits 仍与主机逐位一致（3 步内 248320/248320、L1 相对差 0）。相位图再变一次：20 线程下 load 0 / gr_read 69 / 注意力 290 / MoE 493 ms——MoE 已是最大的单段（约一半），注意力第二，两段合计占了这一步的九成以上。

MoE 那一段是算出来的、不是读出来的。上一段的相位图里它最大，故先问「这 493 ms 里有多少是每步重读专家字节」——把主机参考路径的专家缓存打开（第 5 节那条实测）反而更慢，答案是不到一成，剩余全是计算。把它按调用数摊开看：48 层 × 10 个专家 × 3 个矩阵 = 每步 1440 次按档 GEMV，合计约 2.36 GMAC，即 493 ms 里跑出的是 4.8 GMAC/s；而同一份池子在 24 线程上跑一块 10240×2560 的 Q2_0（`measure/thread_pool_bench.cpp`）能到 33 GMAC/s。差别不在池子也不在内核本身，而在**调用粒度**：这 1440 次里每一次只有 1.64 MMAC（gate/up 640×2560、down 2560×640），20 个线程按行切一两次就到底了，分派与每行的固定开销盖过了算术；此外 gate 与 up 共用同一组激活，而激活量化现在按矩阵各做一遍。故这块的下一步是把粒度做大（同一层的十个专家并成一次按档 GEMV：算上它们共用的激活，一次量化、一块缓冲、一次分派），而不是继续动内核里的乘加。

上面那条建议下笔前先拆了一次，结论要改：把 MoE 按「取数」与「算」两半计时（`MoePhases`，`run_moe_layer` 里两处时间戳，两半互斥且穷尽）后，20 线程下是取数 93 ms、算 402 ms（单线程 79 / 902）。取数那一半由第 5 节那组实验定了性；而「算」那一半比同形状的微基准慢得多——同样的十次 640×2560（IQ2_S）加十次 2560×640（Q2_0），微基准在环境2 24 线程上给每层 2.20 ms → 48 层 105 ms，实测的算却有 402 至 448 ms。逐层摊开它是均匀的（均 18.8 ms/层、最慢六层 19.4 至 20.1 ms、与档无关），故不是某几层的格式问题。同一份微基准的第 5 节给出机制：十次提交背靠背时净算术 0.52 ms，每次提交之间夹 1 ms 串行工作后净算术涨到 2.86 ms——每次提交多付约 200 µs 的挂起再唤醒，而这笔钱记在了 GEMV 的窗口里（`run_rows` 要等所有参与方报完才返回，晚醒的工人把调度延迟也算了进去）。真实路径正是一步 1440 次提交、之间夹着几十微秒的取数与量化，于是「一步约 1200 次提交 ≈ 24 ms」这个早先的估算（同样是背靠背量出来的）低估了一个数量级。修法取第一条并已落地：`thread_pool` 的工作线程先有界自旋（200 µs）再挂起，提交落在窗口内的就不必付挂起/唤醒的钱。环境2 上 20 线程的 MoE 由 495 降到 322 ms（其中算 402 至 448 → 231 ms、取数 90 ms），gr_read 69 → 56 ms，稳态步 898 / 927 → 712 / 759 ms；单线程那条作对照一点没动（980 / 901 对 980 / 903 ms）——自旋只在真有工人时才有意义。整步 logits 仍逐位一致（248320/248320）。第 5 节改后重跑（24 线程）：间隔 50 µs 的净算术 0.610 → 0.500 ms（窗口把它全吃掉了）、200 µs 1.476 → 1.079 ms（窗口边缘，吃掉一半以上）、1 ms 时两者都回到 3 ms 量级（窗口之外自旋不负责）；真实路径的提交间隔约 65 µs，故正落在被吃掉的那一段。

第一版自旋是死锁的（`thread_pool` 与 `gated_residual` 两套用例 240 s 超时），根因值得记下来：工作线程的「已见 epoch」若写成构造时读一次当前值，而工作线程可能起得晚——第一个作业已经提交、epoch 已是 1 时它才被调度上 CPU，于是它把那个还没做的作业当成做过了，转身去等下一个；调用方却在等它报工，双方互等（实测两个线程都停在 `futex_wait`）。原来那句 `seen = 0` 是有承重的：它保证晚起的工人也会去领第一个作业。现在有一条用例专咬这个（建池子立刻提交、200 轮 × 64 行），它在改前必挂、改后必过。

窗口取多大是量出来的，不是拍的。`set_pool_spin_us` 把它做成可设，于是同一份二进制能把拐点扫出来（`thread_pool_bench` 第 6 节 + `test_expert_ffn_cuda --spin-us`）。环境2 上同一会话内交替跑（消掉会话间的漂移）：窗口 200 → 2000 µs 时 MoE 的「算」三轮分别是 247 / 231 / 274 → 178 / 172 / 184 ms（一致约 −28%），而同一次提交里的取数与注意力那两段不动；再放大到 4000 / 8000 不再降（180 / 169 ms）。故默认取 2000 µs。这个数对应的是「一步里提交之间的串行工作有多长」：取一份专家的字节约 65 µs、一层把十个专家取齐约 2 ms，都落在窗口内。代价是池子真闲下来时白烧 CPU——19 个工作线程各多烧 2 ms，相对这一步的总算力可忽略，但「越大越好」不成立。

注意力那一段也该拆，因为相位图里它与 MoE 量级相当，而这两段里只有「投影」走按行并行的池子。办法与 MoE 一样：加 `AttnPhases`（`dense/attn_phases.hpp`，七个互斥且穷尽的子步），两层各自填自己有的那几项。环境2 上的读数（48 层、末步、单线程）：投影 707 / 前段 5 / 递推 206 / 收尾 1 / KV 0 / 索引器 9 / attend+门 2 ms。这张表白纸黑字地说明了两件事：一是 20 线程下 attn 由 295 降到 106 时，掉下去的全在投影那 707 上（它走池子），递推那 206 一点没动——70+206+16 与实测的 295 对得上；二是 QSA 一侧几乎没有手写标量的开销（KV 0、索引器 9、attend+门 2），因为这份夹具只跑 3 个 token：`qsa_index` 的逐 cell 打分随 n_kv 增长，长上下文下它才是大的，本夹具量不到。

于是靶子就是递推。它慢的原因不在算术（每层 2.36 M 次乘加）而在访存：状态是 (S, h_v, S) 且 j 最快，而原实现按「固定 (h,j)、内层走 i」遍历——每一步跨 h_v·S 个 float（真模型 24 KB）取一个元素，三条内层循环全是这种步长。改法是两条，都不动任何元素的归约顺序：把 j 放到最内层（连续），以及按 h 并行（每一头的状态片互相独立；归约维是 i，一律不切）。环境2 上：单线程的递推 206 → 19 ms（10.8×，这一段没有并行，纯粹是访存换来的），20 线程下 17 ms；attn 295 → 106 ms，整步相位和 645 → 462 ms，三步的 logits 仍与主机逐位一致（248320/248320）。新相位图（20 线程）：load 0 / gr_read 59 / 投影 72 / 前段 5 / 递推 17 / 收尾 1 / 索引器 10 / attend+门 2 / MoE 297 ms——MoE 现在是最大单段，注意力这半边已经只剩「投影」还占地方。逐位相同这条由 `tests/test_gdn_recurrence` 钉住（真几何 S 128 / h_k 16 / h_v 48；变异测试里「每块都算成该块的首头」与两条「暂存不按头切开」都被抓住——注意后两条要用固定串做 sed，否则 `*` 与 `(` 会被当正则元字符而静默不生效，那次的 SURVIVED 就是这么来的）。

动手拆那一段的过程里撞出一处正确性问题：递推状态此前每步都被清零。`GdnState::resize` 用的是 `data.assign(..., 0.0f)`，而 `run_gdn_layer` 每个 token 都会调它——于是线性注意力唯一的记忆（那个 (S, h_v, S) 的状态）在每个 token 开始前归零，这一层实际上没有跨 token 记忆。这与契约冲突（`gdn_recurrence.hpp` 写的是「状态原地更新」，`gdn_layer.hpp` 写的是「state 与 conv 跨 token 存活」），而当时的测试抓不到：`test_gdn_layer` 里那句「状态在动」是卷积状态在动，`test_gdn_recurrence` 只看单步，主机与设备两条路又共用同一份代码，故位一致也不受影响。定位它用的是一条能把卷积状态干扰控住的判别：同一条输入跑两遍，一份在两次调用之间手工把递推状态清零、一份不清——若层内部每步清零，两份末态逐位相同；实测正是 0/1024 全同，证据才落地。修法是把 `assign` 换成 `std::vector::resize`（同尺寸时是 no-op，只有首次或换几何才零初始化），并加一条用例钉住「跨 token 存活」。后果要说清：修之前记下的那些绝对量都作废（同一份输入 3 个 token 的 |logits| 合计由 217067 变成 177087，单层 GDN 的 |out| 合计由 2191.92 变成 1979.62），它们是在无记忆的递推上量的；而相对性质的结论不受影响（有限、可复现、主机与设备逐位一致 248320/248320、各子步耗时的量级）。ctest 54/54（开 CUDA 58/58），没有别的测试把旧语义写死。

MoE 那一项的账也要按四项来看（20 线程）：取数 104 / 路由 26 / 逐专家 128 / 共享 37 ms。两张单子立刻能兑现：路由矩阵与稠密权重是同一个毛病——每步每层重读 2.6 MB（48 层合 126 MB/步），故按层缓存（层号记账，同前）；路由那 512 个专家的点积是单线程，故按行并行（与 `run_gemv` 同一个池子，`experts/ffn` 的 `run_bf16_gemv`，QSA 索引器那两个 BF16 投影也改走它）。环境2 上：取数 104 → 76、路由 26 → 5 至 6 ms，MoE 合计 295 → 244 至 251 ms（单线程的取数 96 → 62 也印证常驻那一半）；单线程的路由 27 → 28 没动——这条是诚实的更正：激活的 bf16 舍入「提出来只做一遍」并不提速（编译器本来就把那个纯粹计算提到循环外了），拆开只为「按行并行要切行」服务，21 ms 全部来自并行。整步 logits 仍逐位一致。

接着动的是取数那一项，而修法是不读：给 `GgufFile` 加了 `view_at`——把数据区的一段直接映射成只读内存、**不拷贝**，MoE 的专家矩阵改用它（`ExpertWeights` 本来就是裸指针，故映射之后内核直接读页缓存）。此前那条路是「读进缓冲、再让内核读缓冲」，同一批字节摸两遍，还带每块一次 syscall 与一次流定位；映射把这三样一起去掉。环境2 上：取数 76 → 0 ms（只剩指针算术），逐专家那项也顺带降了（128 → 104 至 109 ms，少了对同一批字节的重复触碰），MoE 244 → 144 至 152 ms、稳态步约 445 → 约 345 ms；整步 logits 仍逐位一致（177087、248320/248320），ctest 54/54（开 CUDA 58/58）。新相位图（20 线程）：load 0 / gr_read 63 / 注意力 88 / MoE 144 ms。两处口径要记：一是平台——`view_at` 用 mmap，故是 POSIX，本仓库的目标平台只有环境1 的 WSL 与环境2 的原生 Linux；映射不起来或越界一律返回 nullptr，调用方退回原来的 `read_at`，所以它不是硬依赖，测试里另有一条「两条路必须给出同样字节」的用例（映射不到时明确跳过），免得退路变成没人看的死代码。二是本条也把「读得慢」这个说法钉死了：8 至 11 GB/s 与带宽无关（同一台机流式读 58 GB/s），是「摸两遍 + 按块 syscall」的代价——换成映射后同一批字节只摸一遍，那一段就消失了。

共享专家那 37 ms 里也是同一个毛病（它的三张矩阵每层每步 `read_at` 一遍，72 MB/步），改用 `view_at` 后降到 9 ms。这里顺带挖出并修掉一处真错：共享专家的标量门无论声明哪种档都只读「隐藏维×2」字节，于是 F32 档只填了一半、后半留零，门的点积跟着错——部署那份是 BF16 故没暴露，F32 门出现在社区那份 MTP pack 上。夹具里让门的上半段非零就能看见：改前「读回与张力相同 128/256、门 0.297 对正确的 0.395」，改后 256/256、两者一致。这条与递推状态那条是同族：读得不够、或把状态清零，都不会报错，只给出可信的错值。MoE 的四项于是变成取数 0 / 路由 5 / 逐专家 103 至 109 / 共享 9 ms。

gr_read 那一段（此前从没拆过）拆开后没有意外：20 线程下 lo 24 至 29 与 mixed 24 至 28 两个投影，加上逐流归一与舍入 1、inject 投影 2 ms——就是两个按行并行的投影、放大倍数约 6（单线程 173 / 156 ms）。它的累加在 double 上（与参考实现同口径，换成 float 更快但会改数值），故不动。

设备侧那一批也按三段拆开（`DispatchPhases`：取数 / 工人 / 归并，20 线程、同一份输入）：**取数 107 / 工人（设备内核与同步）309 / 归并 0 ms**，而主机同口径的逐专家是 103 加共享 11 ms。两处都是真账。取数那一项是「读到缓冲再 H2D」——给主机侧取消掉的那道拷贝，设备侧还在付，而且它必须先把字节取齐才能 H2D。修法是给 `ExpertSource` 加一个直接映射模式（`from_mapping`：`get` 把三张矩阵各指进 GGUF 的映射、既不拷贝也不登记页表，`pin`/`unpin` 因此是空操作，`resident` 仍记为真＝「本次使用期间有效」）：取数 107 → 0 ms，设备整步由 730 至 780 降到 619 至 647 ms（对主机约 300 ms，差距从 2.4 倍收到 2.1 倍），整步 logits 仍逐位一致。剩下的差距全在工人那 312 ms 里，即设备内核本身：1440 次按档 GEMV 在这台卡上跑出的是约 7.6 GMAC/s，而 20 核主机池子约 20 GMAC/s——同一个几何的单次调用，微基准（含搬运）是 98.9 至 204.7 µs，正是这个量级，所以不是「搬运拖累」而是内核本身在标量地解 2/4 位码本；要它划算得重写内核（按行协作、共享内存里的码本、向量化取字节），那是独立的一片。

这一段慢的真正病因是占用，不是访存也不是指令数：一个线程算一个输出行时，gate/up 只有 ffn 即 640 行，也就是 5 个 128 线程的块，而这张卡有 36 个 SM——大半 SM 空着，每个线程那串长依赖链没人替它藏延迟。定位它之前先按顺序试了三个别的猜想，全都在环境2 上量了、端到端都没有收益，于是都撤掉（树里不留没有收益的复杂度）：合并访存（块内先搬进共享内存再解）、每个子块用 4 个整数累加器（整数精确，只缩短依赖链）、每线程两行做 ILP（这个反而把网格减半，与第一条互相抵消）。教训：改指令级之前先看网格——旁证其实早就在同一份记录里：同样 1.64 MMAC 的两次调用，2560 行（20 块）98.9 µs、640 行（5 块）188.3 µs。

修法是按批收集加一次启动：一次提交里先把本批用到的专家的 gate/up 从常驻区 D2D 拷成连续的两段（每层约 10 MB、几毫秒），再对整段各启动一次——行数乘 n、网格乘 n，而激活本来就是共用的那一份。环境2 上：工人 309 → 90 ms（等价于 7.6 → 26 GMAC/s），设备整步 619 至 647 → 335 ms，对主机池子（约 300 ms）从 2.1 倍收到 1.1 倍；整步 logits 仍逐位一致，ctest 54/54（开 CUDA 58/58）。down 那一路的激活是各专家自己的 h、共用不了，故第三片给内核加出「每行的权重基址与激活基址都由专家号决定」这一维（`q2_0_gemv_q8_0_cuda_batch`：权重 = 常驻区起点 + 槽号×槽距 + 行号×行距，激活 = 该专家那段 h，后者给 0 就是各专家共用），h 随之按专家分片（`d_h_` 开 slots 段）、槽号表也搬上设备，于是 down 也成了一次启动——一次提交里三条矩阵各一次，同步次数与本批专家数无关。同一会话内旧新交替读数：工人 90/91/91/90 → 84/84/83/83 ms，取数仍 0、归并仍 0，整步落在噪声内（约 325 ms）、logits 仍逐位一致。夹具补了一条结构判据：槽号按三元轮换分配时，错位那一批的第 e 位必须与恒等那一批「它要的那个槽」那位逐位相同——它在「激活按槽号取」这条错读法上必挂，而既有的同槽用例抓不到它（对换的逆就是它自己，会碰巧对上）。至此这一步的账是：MoE 110 至 124 / 注意力 85 至 91 / gr_read 52 至 60 ms，其余约 45 ms 是 embedding、输出头与分派；本会话累计 20 线程稳态 1476/1470 → 约 300 ms（约 4.9×）。

一条必须先看的测量（环境2，部署那份，48 层、同一份 x 连跑 3 步，逐步计时）：主机 4585 / 2585 / 2622 ms，设备 4614 / 2553 / 2542 ms——设备侧只快 1% 到 3%，等于没快，而每一步的 logits 都与主机逐位相同。两件事由此定下来：① 主机参考路径的一步约 2.6 s（稳态），其中专家那批按单内核实测推算只有约 0.7 s，其余是稠密部分（门控残差、两种注意力、路由、共享专家、输出头，又是单线程标量实现）——所以下一步该动的是稠密部分，不是把专家搬来搬去；② 设备侧的常驻区给 12 槽时，第 1 步之后 92/144 批因「装不下」被退回 CPU（§8.5 的降级照设计生效），量出来的自然不是设备路径——真答案是专家缓存那套淘汰与配额（§5、G-11），不是把槽位硬调大。选组因此能真挑中它：档齐的层走设备侧，角色不对或没有卡时按 §8.5 改派给 CPU 组。环境2 上的读数：同一份真字节夹具上，工人提交的一批（两个专家）与主机逐元素位相同（512/512），第二次提交同样的一批不再搬权重（`uploaded_bytes` 不变），换一个没见过的 id 会真搬；4 条变异全致死（每次提交都重搬、按位置认常驻、所有位置都用 0 号槽、不记映射）。

一层 MoE 于是有了「交出去」的接缝（`MoeOffload`）：给了候选组与字节来源就改走批量分派，不给还是逐专家的主机路径——两条路的归并顺序相同，故逐位可比。真权重上的读数（部署那份的层 0，top-10、含共享专家）：两条路逐位一致（2560/2560），选组 `routed=1 rerouted=0`（真是选中的组做的，不是被静默改派），工人算完 10 个专家、常驻 46.1 MiB；那条「从不交出去」的变异被这个大可致死的判据抓住。步循环也给了「交出表」（`StepConfig.offload_layers`，每层一份字节来源与候选组，`prepare_step_scratch` 逐层挂到该层的 scratch 上；CUDA 侧默认关，故 CI 不受影响）。

整模型一步（48 层逐层交出）与主机路径的 logits 逐位一致（248320/248320、L1 相对差 0），`routed=48 rerouted=0`、480 个专家都算完。

定位它的过程值得记下：一开始按 48 层跑，L1 相对差 0.309、位相同 0/248320；按层数二分发现 1 层逐位一致、2 层起全不同；再把夹具扩到 gate/up 的三档，就看见 IQ2_XXS 那档的 L1 相对差是 1（等于全错）、而 IQ2_S 逐位一致。根因：`iq_gemv.cu` 的常量表上传只放在自包含入口的检查里，没放进「设备指针」那条 `_ddd`——而常驻路径走的正是 `_ddd`。于是内核读的是未初始化的常量内存（全零），点积算出来看着像样、其实是垃圾。两块内核各自的单测都是过的：它们走自包含入口，`_ddd` 从没被碰过。教训是「生产实际走的那条入口必须就是被测的那条」，夹具因此改成三档都过一遍。多卡（一组一张卡由 `layer-split` 分成多个实例）、批式前向、图捕获，以及共享专家那四个档（IQ3_S / IQ4_XS / Q6_K / Q8_0）的设备内核都还没做。

目标负载的专家权重是逐层换档的：gate/up 为 IQ2_S / IQ2_XXS / IQ1_M，down 全 48 层为 Q2_0（专家字节合计 35.45 GB、等效约 2.35 bpw；逐层清单见 [S-36] 与 [`../research/02-qwen3.8-flash-next.md`](../research/02-qwen3.8-flash-next.md) §1）。down 只能用 Q2_0 这类每块 64 个值的档，因为 640（`expert_feed_forward_length`）不是 256 的整数倍。所以解码侧按「层 × 张量」分派格式。这张映射是逐文件的数据、不是固定表：环境2 上现有两档（部署的 IQ2 档与另一份 IQ3_XXS 档）的逐层映射互不相同，同名档位覆盖的层数也不同（[S-36]、[S-38]），故分派表在加载时从 GGUF 的逐张量类型读出——实现见 `src/experts/expert_formats`，它按层组装 gate/up/down 三个矩阵的档与块几何，并把「缺张力 / 类型码不认识 / 几何不成立 / 无内核」分别记进 problems 而不是静默跳过。按实测，部署那份 48 层已全部可用（gate/up 逐层为 IQ2_S 34 层 / IQ2_XXS 11 层 / IQ1_M 3 层，down 全为 Q2_0）；另一档的 48 层也已全部可用（gate/up 里 IQ3_XXS 6 层补上内核后不再有缺口）。

三矩阵的组装在 `src/experts/ffn`：gate/up 的输入是 hidden、输出是 ffn，down 反过来；激活按每个矩阵自己的档选（256 值块的档配 Q8_K，32/64 值块的档配 Q8_0——见 [S-42] 的块几何与 S-37 / S-40 / S-41 的配对；激活量化器的尺度以 fp16 存，见 [S-43]），门控用 SwiGLU（引擎的 MoE 路径就是 swiglu，见其 `src/core/layer.cpp`），路由权重由调用方给出、按专家累加。gate 与 up 共用同一组激活，故两者的激活档必须一致；不一致直接失败而不是各算各的。真权重上已与双精度参考实现对过（三层 × 三个专家），不可用的层明确报错。

路由门控在 `src/experts/router`，口径取自参考引擎自身的主机参考实现（[S-44]）：`ffn_gate_inp` 的 BF16 投影（激活也必须按 bf16 舍入，引擎自注改用 fp16 会引入 8.1e-03 误差并翻掉选择）→ 全专家 softmax（双精度、减最大值）→ 稳定降序取前 10（同值取小索引）→ 按前 10 之和归一化（分母下限 2^-14，本模型几何下取不到）。真模型上与引擎那份参考逐层对拍过：部署那份的层 0 / 12 / 47，专家 id 完全一致、权重到 9 位有效数字一致。注意该参考是「按同一份规格另写的」，与它一致只说明两边同规格，不推出与上游引擎成品一致。

逐专家加权」的独立参考一致；IQ1_M 补上内核后，原先报错的 8 / 13 / 37 三层也已跑通，部署那份的 48 层全部可用。遇到没有内核的档（另一档共享专家里的 Q4_K / Q5_K，以及 IQ1_S 等本仓库尚未做的档）仍然明确报错。本实现是主机侧参考路径：默认按需读文件不做缓存，开 `cache_slots > 0` 之后读取路径走 `src/experts/expert_source`（专家缓存的策略决策、页表的不变量、读表接在一起，见 §5）。真模型上两条路径的输出逐位一致（部署那份的层 0 与层 12，各 32 个 token）。未命中专家交给工人算的那条**批量**路径在 IQ2_XS 这一档的块反量化与「与 Q8_K 的定点点积」已实现：`src/kernels/iq2xs`（块格式，编码定义登记在 [S-35]，表体在 `kernels/iq2xs_tables`）、`src/kernels/q8k`（激活侧 Q8_K 量化）、`src/kernels/iq2xs_dot`（定点点积与逐行 GEMV）。点积把权重留在整数域：整数侧在 int32 里累加完再乘 d · d_y · 0.125，尺度用 ls = 2s + 1，等价于逐元素反量化后再点乘，但省掉权重侧的浮点展开。IQ2_XS 是 §15 算带宽上限所用的名义档，不是参考实例的专家档。

**服务路径接线（阶段 B：KV 上卡，[ADR-014](adr/ADR-014-gpu-igpu-serve.md)）**：QSA 各层的 KV 页从主机搬进设备——`KvDeviceExec`（`src/dense/kv_device_cache`，函数指针结构）给出 `reserve / append / gather / evict / admit_block / resident / release`，`run_qsa_layer_cuda` 在本层首入时按页缓存的几何惰性 `reserve` 一次设备池（含设备页表；主机侧留镜像表供预检），此后写 cell、按选中 id 聚集、softmax GQA + 门全部在设备上做：`qsa_attend_cuda` 拆出共享启动段并新增 `qsa_attend_cuda_dev`（k/v scratch 已在设备时不打每步 H2D），`kv_gather` 换成设备内核（相同 `[id][kv_head][head_dim]` 布局与相同页内寻址）。池的生存期 = StepScratch（析构里经 `release` 回收；主机建构建指针恒空、零 CUDA 引用）。`--kv-resident N`（反向语义，spec §3）：0（默认）= 全常驻不逐出；N > 0 时 `pos` 越过 N 就逐出最旧逻辑页（设备表 → -1，主机权威副本不动），gather 前对缺席页做准入（从 store `read_block` 整块搬回 + 置表）。判据：设备 gather 对主机 `kv_gather` 字节相同（稠密与稀疏 id 集）、attend 设备版对主机版逐位相同（bit-same 1.000、L1 0）、逐出→缺失报错→准入→再 gather 仍字节相同；8K 上下文夹具（2048 页 / 8192 cell、选择宽度 2048、hd 256、n_head 24）每步 attn 段读数（10 次平均）：主机 4.9 ms 对设备 3.9 ms（约 1.3 倍），输出逐位相同——注意此前记过的「单次 ~100 倍」是冷启动单次计量的假象，稳态差距就是这一档：跨总线读（每层每步约 4 MB 的 k/v）在这段的占比有限，被消掉的主要是主机侧的聚拷贝与 DDR 占用（对同时跑 CPU 池的机器是稀缺资源），真正的收益面在长上下文（本夹具已模拟 8K）与阶段 D 的权重常驻/图捕获（融合路径要求 KV 在设备）。真机端到端（环境2、部署那份、`--gpu auto`）：`--kv-resident 0` 与 `--kv-resident 4` 对同提示同 seed 生成的 token 流完全相同（逐出/准入只改字节在哪、不改字节），qinfer 进程稳态占显存 234 MiB（dense 临时缓冲 + 设备 KV 池）。顺带修掉一个长期可见性问题：启动日志走 stdout，重定向到文件时是全缓冲——不加显式 `fflush` 就一行都看不到（此前 runbook 里「服务不写 stdout」的记录即此），main 现在在启动行后显式 flush。

**服务路径接线（阶段 A：dense 整层上卡，[ADR-014](adr/ADR-014-gpu-igpu-serve.md)）**：稠密这段的服务侧入口已接通——`run_block_layer` 的 GDN/QSA 两个分支在给了设备执行器时走整层 `*_cuda` 入口（`run_gdn_layer_cuda` / `run_qsa_layer_cuda`），否则照旧走主机 `run_gdn_layer` / `run_qsa_layer`。分派不靠编译期符号：`DenseExec` 是函数指针结构（`run_gdn` / `run_qsa`），`StepConfig.dense_exec` 由调用方（facade）在 `--gpu` 时填 CUDA 侧 `dense_exec_cuda()`——只有 `QINFER_ENABLE_CUDA=ON` 的构建编这个符号，主机构建恒空、全主机路径零行为变化（68 测全绿即这条的断言）。`--gpu` 语义：`auto` = 全部可见卡、`0,1` = nvidia-smi 索引列表；无 CUDA 的构建给 `--gpu` 明确拒绝启动（错误体含「CUDA 未启用」），不静默回退。补档一件：合成/测试模型的稠密权重是 Q8_0（真模型的 dense 投影是 IQ4_XS / IQ3_S / Q6_K），而 `gdn_proj_gemv` 的分派表原本没有 Q8_0 权重档——补上 `src/kernels/cuda/q8_0_gemv`（Q8_0 × Q8_0 定点点积，激活搭档同为 32 值块），真字节 oracle（ffn_down_shexp 前 16 块）tile 成 640 行 × 80 块/行后与主机 `run_gemv` 逐位相同（640/640、L1 相对差 0）；4 条变异全致死（权重尺度字节序反 / 激活尺度泄漏 / 整数点积少算一个值 / 块循环漏最后一圈）。集成门禁按构建分野：CUDA 构建下 `--gpu 0` 起服务并发一个请求——层 0 GDN + 层 1 QSA 两条 `*_cuda` 路径都跑到、返回 200 且内容非空（任一设备内核炸都会现形为 400/500/坠）；无 CUDA 构建保留「拒绝启动」断言。

环境2（双 5060 Ti，部署那份真模型，`--gpu auto`）上的实测读数：服务约 5 秒就绪（页缓存暖）；一次 53 prompt + 8 gen 的请求 200、finish=length。用同提示双请求拆分：max_tokens=1 耗时 34.62 s、max_tokens=9 耗时 38.17 s，故 decode ≈ 0.444 s/token（2.25 tok/s）、prefill 53 token ≈ 34.2 s——对 CPU 基线（decode 0.5 tok/s、prefill 约 2.5 分钟）各约 4.5 倍与 4.4 倍（单次采样、方差存在；首请求另有约 7 s 的加载/首接触开销）。`nvidia-smi` 可见 qinfer 进程占显存（稳态 228 MiB、请求期间峰值约 1.2 GiB——监控 `history/gpu_mem_used` 读数），`/props` 报告 `offload_enabled:true`、`gpu_devices:["auto"]`。`history/gpu_pcie_rx_mb` 一趟 1.7–3.5 GB 是 dense 权重的反复上传痕迹，`gpu_util` 峰值 15.5%——即当前形态是「每段各自 H2D/D2H + 同步」：权重在主机侧按层缓存、每 token 重传，真正的提速（权重常驻 + 图捕获 + 每步单汇合）留给阶段 D，届时此读数的提升空间自会兑现。分工求解器与其余阶段（B 的 KV 上卡、C 的核显未命中专家、D 的 head/GR/共享专家 + 裁剪）见 [ADR-014](adr/ADR-014-gpu-igpu-serve.md)，不在本节内。

## 7. KV 管理

主案例有两种 KV，必须分开记账。

| 缓存 | 所在层 | 随什么增长 |
|------|-------|-----------|
| GDN 循环状态 | 36 层线性注意力 | 并发序列数，与长度无关 |
| QSA KV 与索引器 KV | 12 层稀疏注意力 | 上下文长度乘以并发 |

设计：

1. 两个独立池，独立配额、限额与驱逐。并发升高时两条一起涨，调度器必须同时观察两个余量。
2. 常驻热窗。QSA 只常驻最近一段 token，其余分块流式读，块粒度与注意力块对齐。
3. 索引器 KV 有独立精度旋钮。它对质量敏感但体积小，可以比主 KV 更激进。
4. 精度档默认 FP8，长上下文或高并发时降到 4-bit，3-bit 作为实验档，需融合内核与标定后才启用。
5. 分页方案与稀疏注意力的块粒度对齐，避免一次注意力跨越过多物理块。

长上下文下每 token 的 KV 读字节已测（G-12）：256K 原生上下文下 KV 块读的显存命中率 90.1%，一个 256K 请求的内存侧 KV 读合计 213.3 MiB，约 1.7 MiB/token（且大部分在预填期），远低于「索引器稠密扫描」的推算——引擎只读索引器选中的块。因此第 15 节「瓶颈不在带宽」不再受这一条阻塞（见 [`../research/01-strata-engine.md`](../research/01-strata-engine.md) §7.2）。

两个池的记账与准入已实现（[interfaces.md](interfaces.md) 第 5 节的实现说明）：`src/kv/kv_pool`，两类驱逐语义不同（QSA 只清常驻窗口、序列还在；GDN 全有或全无）。第 5 节第 4 条「槽位弹性」——槽位数在 KV 常驻窗口与专家数量之间动态配平——现在**机制已就位**（第 6 节的 `src/dense/kv_window`：字节配额 + LRU 驱逐 + 钉住，接在 QSA 的搬入路径上），故可以据此定配平规则；**配平本身仍是待定的设计决定**：目前槽位数与常驻窗口是两个独立的配置项，二者的换算与优先级还没定，等这条规则定了再改本节。

## 8. 投机解码

1. 基线用模型自带的 MTP 头，起草长度默认 3，按显存与接受率在线自适应；接受率低于阈值时收缩。
2. 提示查询起草从上下文已有文本中抄取，最多 5 个 token，仅在实测有收益时启用。
3. 验证即证据。主模型一次前向验证全部草稿，输出分布不变。
4. 被拒绝的草稿仍会被验证窗口读入其表行与专家，造成 IO 放大。G-13 实测（环境2，接受率 0.786 至 0.940）：接受率取倒数为 1.064 至 1.272 倍，按轨迹直接数出的「每生成 token 的位置数」为 1.047 至 1.250 倍（中位 1.133）。该放大按位置计，同时作用于专家读与表行读，不改变第 4 节的按需读路径。

## 9. 精度策略

| 旋钮 | 默认 | 备选 |
|------|------|------|
| 权重 | NVFP4（本平台原生）或 IQ2_XS / IQ3_XXS | IQ4_XS、三值 |
| 主 KV | FP8 | 4-bit，再到 3-bit |
| 索引器 KV | FP8 | 4-bit |
| 累加 | FP32 | BF16 |

所有低精度路径都必须把反量化融进内核。多旋钮同时降档会产生复合误差，允许的组合与禁止的叠加见第 16 节。

## 10. 自动标定

标定产出机器画像，四项输入与五项推导参数：

1. 显存可用量与带宽。本项用 device STREAM（copy/triad）而不是规格里写的小 GEMM 扫描：画像要的是「每 token 权重字节 ÷ 显存带宽」这个上限，而 fp32 小 GEMM 在消费级卡上先撞算力，会把带宽量低。GPU 侧的纯算力下限另有参考引擎的 `--gpu-only-full`。
2. PCIe 实际档位与有效单向带宽（大块拷贝）。这一步同时回答空闲降档是否只是假象。
3. 按核心类型区分的量化内核吞吐。
4. 主机内存有效带宽。

据此推导：每步字节预算、专家槽位数、KV 常驻窗口、并发分池方案、起草长度上限。每步字节预算的公式为 `pcie_h2d × 步长 × io_share`，其中 io_share（一个步里允许 IO 占用的时间份额）是设计输入，不是测出来的——本设计取 0.5。全部参数落盘，可复用、可对比，字段见 [interfaces.md](interfaces.md) 第 6 节。

环境2 上这四项已测、推导已实现：工具 `measure/calibrate.py`（组合器，输入即各测点的原始记录），产物 `measure/results/*-calibrate-环境2.json`，逐项数字与读数见 [`../research/01-strata-engine.md`](../research/01-strata-engine.md) §10.2。三条可直接使用的结论：槽位 = 缓存字节 ÷ 专家块字节（复现实测到 1.6%）；每步 PCIe 预算对「本步必需的未命中专家」有 1.75 倍余量（静态命中 0.835）；用实测显存带宽（398 GB/s，标称的 88.9%）算，§15 的上限是 IQ2_XS 216 tok/s、FP8 64.8 tok/s。

本能力不具备差异化价值：参考引擎已有对应的启动标定开关。

- 多模态：视觉编码器约 1.4 GB，按需载入载出；图像特征缓存复用，避免多轮引用同一图像时重复计算。

### 12.1 服务层 M1 实现说明（已落地）

实现栈见 `adr/ADR-012-http-transport-and-serving-stack.md`，契约对拍对象是 Strata v0.1.43（`../research/01-strata-engine.md`）。本节记实现事实，改动先改它再改代码的约定照旧。

- 传输：cpp-httplib v0.18.6 单头整份入库（不定义 OpenSSL / ZLIB 宏），线程池 2 × 槽位 + 2；协议解析、SSE、轮询自写。静态页由同一进程在 `/web` 与 `/api-monitor` 提供。
- 协议域：OpenAI（`/v1/chat/completions` 流式与非流式、`/v1/completions`、`/v1/models`）与 Anthropic（`/v1/messages`、`/v1/messages/count_tokens`）同一份调度器与门面；两域同请求在默认参数下产出相同 token 序列。非法参数按两域各自的错误形状 400/401/503。
- 生成循环挂在 `src/serve/facade` 的门面上：请求即全新会话（scratch、KV 窗口、PLE 历史都随调用装配，请求之间无共享状态）；采样器用标准库 `mt19937_64`（温度 0 即贪心、seed -1 随机 = 与需求一致的默认）。SSE 用 httplib chunked provider，连接断开即取消生成并释放槽位。
- 调度：有界队列 + 槽位租约，满则 503；`--reject-after` 仅供集成测试制造确定 503。
- 遥测：NVML `dlopen`（Windows `nvml.dll`）、AMD kfd 拓扑 + hwmon、CPU/RAM 走 `/proc` 差值法、磁盘读解析 `/proc/diskstats`；无任何可读源时字段为 `null`。10 个系列各 60 点历史，`/metrics` 顶层键对齐 Strata。
- 请求记录环：保留 100 条、大字段 256 KiB 截断，`/api/requests` 列表剥大字段、`?id=` 给全量；`/metrics` 的 requests 取最近 12 条。前端四页（三 tab 单页 + `/api-monitor` 检查页）读这些端点，轮询 1 秒（/metrics）与 2 秒（/v1/status、/api/requests）。
- 会话前缀缓存（spec §6 的 conversation_cache 落地）：整串精确匹配的 token 前缀 LRU（`serve/prompt_cache`，`--conversation-cache N` 默认 64、0 即关）。请求 prompt 命中缓存即免 BPE、命中 token 数计入 `totals.reused`；`/metrics` 的 `conversation_cache` 实读 enabled/capacity/hits/misses/entries/tokens。查询在 engine_mu_ 锁外、命中免进锁；未命中才进锁 encode 并回填，generate 照旧在锁内串行。BPE 合并可跨字节边界故不做前缀拆分，只整串精确命中；索引器 KV 侧的前缀复用不在本缓存语义内。
- Prometheus text 端口（M2 监控首刀，契约对照 `ref_repos/strata` 的 `serve/prometheus.py`）：`/metrics` 按内容协商输出——Accept 含 `text/plain`/`openmetrics` 或 `?format=prometheus` → `text/plain; version=0.0.4`，否则保持 JSON（前端与无头 curl 缺省 `*/*` 不破）。指标名取 vLLM 家族（`num_requests_running/waiting`、`kv_cache_usage_perc`、`prompt/generation_tokens_total`、`request_success_total`、`prefix_cache_queries/hits_total`、`ttft/itl/e2e` 三直方图 22 桶、`num_preemptions_total` 恒 0）+ `qinfer:` 前缀家族（`live_state`、`live_*`、`totals_*_seconds_total`、`conversation_cache_*`、`engine_max_context`、`gpu_*`、`ram_*`）；模型名标签转义。渲染只读 `/metrics` 已构建的同一份 Json（单一事实源），null/缺键字段不出样本。`totals.requests`（完成时刻 +1）与直方图数据源都是 record_request 的同一落点。
- 鉴权：可选 `--api-key`；`/web`、`/api-monitor`、`/`、`/health` 可达，页面自带 key 走 `Authorization: Bearer`。

## 13. 核显与 NPU

动机：未命中专家路径是当前最大的可控瓶颈。核显与 CPU 共享同一条内存总线（约 70 GB/s），因此不增加带宽；只有在算子属于计算密集而非带宽密集时，多一组计算单元才有价值。

判断准则由 G-07 给出：

| 未命中专家路径的性质 | 现象 | 结论 |
|---------------------|------|------|
| 带宽瓶颈 | 读字节速度封顶，CPU 在等数据 | 核显无用，只能提高命中率 |
| 算力瓶颈 | 数据已就位但低比特码本解码算不过来 | 核显可分担，与 CPU 并行 |

G-07 已实测为**算力瓶颈**（环境2）：纯流式读 8 线程即饱和在 58.5 GB/s、24 线程 67.5 GB/s；4 位码本反量化+FMA 臂 24 线程仅 30.8 GB/s（0.456× 天花板）、16 线程 20.6 GB/s，且随线程数上升未触顶。故本节的启用前提满足：核显可作为第二组算力参与未命中专家路径，与 CPU 并行；在引擎专家池的实际规模（16 线程附近）算力臂只用掉总线的一半左右，带宽尚有可分配的余量（见 [`../research/01-strata-engine.md`](../research/01-strata-engine.md) §5.1）。

不依赖 G-07、可直接采用的三处：视觉编码器移到核显（直接省 1.4 GB 显存，约等于一千个专家槽位，并省去一次主机到显存的拷贝）；表行的聚集与加权聚合；图像与视频预处理。

边界：核显与 CPU 总吞吐共同受总线带宽约束，只在算力瓶颈场景启用并限制其占比，把它当作第二个工人而不是独立的带宽来源。NPU 擅长整数卷积，不适合低成本码本矩阵乘，不参与专家计算。

核显现状与总线争用已实测（工具 `measure/igpu_probe.c`，记录 `measure/results/20261010T195533-igpuprobe-环境2.json`；零新增依赖，只用发行版自带的 Mesa Vulkan / ANV）：

1. 设备可见：Intel Arrow Lake-S Graphics（vendor 0x8086、device 0x7d67、集成型），绑在 i915，渲染节点 `/dev/dri/renderD130` 对当前用户可开（有显式 ACL）。
2. 运行时现状：核显没有任何计算运行时——无 Level Zero（无 loader、无头文件），OpenCL 只注册了 `nvidia.icd`（核显不在其中）。Vulkan 加载器与 ANV 驱动（Mesa 26.0.8）在。故两条路线的依赖代价不同：Vulkan 路线运行时零新增，只需编译期的 `libvulkan-dev` 与一个 SPIR-V 编译器（或按 [ADR-008](adr/ADR-008-implementation-stack-and-kernel-reuse.md) 的惯例把预编译 SPIR-V 连同生成来源入库）；Level Zero 路线需要在环境2 加装 `intel-level-zero-gpu` 与 `level-zero-devel`。上游那套 Arc 端口是 SYCL，同样依赖 Intel 计算运行时，故「复用上游内核」并不因此更省依赖。
3. 该设备在 192 项扩展里没有 `VK_KHR_shader_integer_dot_product`，故 Vulkan 路线上 DP4a 等效指令不可用，码本矩阵乘只能手写整数乘加——这与 ADR-005「内核走 DP4a（若可用则 XMX）」之间有一处待决的口径差。
4. 总线争用（带宽型对带宽型）：核显 `vkCmdCopyBuffer` 搬 256 MiB 最好 26.9 GB/s（对总线约 53.7 GB/s，拷贝按读一遍写一遍计）；与 8 线程 CPU 流式读同跑时 CPU 从 56 至 61 GB/s 掉到约 25 GB/s（保留 41% 至 46%），两侧合计 59 至 62 GB/s，只有 CPU 单独的 0.98 至 1.10 倍。即带宽型工作下核显是争用者、不是增量来源。
5. 口径边界（要紧）：上面两条只回答带宽型工作。未命中专家路径是算力型（G-07：4 位码本臂在 16 线程只用 20.6 GB/s 总线），故「算力型工作能否叠加」还没有答案，它需要一个真正跑在核显上的计算内核——而那需要上一条的 SPIR-V 工具链。CPU 臂与 `measure/cpu_expert_bench.c` 同形（按线程切互不重叠区段、屏障齐发、固定遍数），本机上 8 线程得 56 至 61 GB/s，与 G-07 的 58.5 同量级，可作为方法互校。

专家分担这条缝的接口形式已定在 [interfaces.md](interfaces.md) 第 8 节：后端以计算组为单位（设备、队列、内存池、能力表，见 [ADR-011](adr/ADR-011-compute-group-abstraction.md)），提交面是工作单元与工人，PCIe 与 DDR 两套资源分开限制，另有同步与归约、降级与正确性口径。核显是其中一组，它的能力表按本节实测填（没有计算运行时、没有整数点积指令）。本节的三处无条件用途不经过那条接口。

共享内存总线上同类方案的公开实测为负收益（−19%），这一风险不因 G-07 的结论消失；G-07 只回答「值不值得试」（算力瓶颈成立），占比如何限制仍须实测，见 R-08。

## 14. 单卡与双卡

统一原则：代码与数据格式只有一套。卡数只改变机器画像与分配策略，不改变代码路径。目标是单卡能跑、加卡更好，而不是两套引擎。

双卡的收益：显存合计翻倍，命中率随之提高；两卡的 PCIe 通道可并行搬运；算力翻倍。

消费级双卡的三条硬限制：

1. 第二条槽位常为 x4 或走芯片组，第二卡带宽可能只有第一卡的四分之一。
2. 无跨卡直连，通信只能走 PCIe。
3. 第二卡显存不是更大的空间，而是更热的专家缓存，模型逻辑仍是同一份。

| 策略 | 做法 | 适用 |
|------|------|------|
| 按层切分 | 层在两卡间粗粒度切开，各卡独立运行自己的层与专家缓存 | 单会话、低延迟优先 |
| 专家并行 | 两卡各持约一半专家的常驻副本，未命中的从共享主机内存专家池取 | 单会话、命中率优先 |
| 双实例数据并行 | 两卡各跑一个独立实例，共享主机内存中的专家池与记忆表 | 多会话、吞吐优先 |
| 禁止 | 每层同步的张量并行 | 会把慢链路放进每层关键路径 |

共享主存专家池是关键设计：双卡与双实例不各自复制专家与表，主机内存是共享资源，由统一页表管理并共享引用计数。

具体选择依据 G-08 的实测结果。

## 15. 瓶颈模型

理论上限：每秒解码 token 数约等于有效带宽除以每 token 字节量。

粗算，假设激活参数 6B 且全部命中：

| 权重精度 | 每 token 权重字节 | 显存带宽上限 |
|---------|-----------------|-------------|
| FP8 | 约 6 GB | 约 75 tok/s |
| IQ2_XS | 约 1.8 GB | 约 250 tok/s |
| NVFP4 | 约 3.3 GB | 约 135 tok/s |

参考引擎实测（双卡 77.2 至 86.3，单卡期 57.9 至 81.7 tok/s）远低于权重口径的上限，说明瓶颈不在显存带宽，而在三处：未命中专家走 CPU 的慢路径、PCIe 与同步开销、记忆表 IO（冷启动尤其明显）。

其中 CPU 侧已可量化：G-03 给出每 1% 的路由量落到 CPU 就多约 0.7 ms/token（本内核口径），G-09 的覆盖曲线意味着部署槽位下约 16.5% 要走这条路，即约 11.6 ms/token——与引擎自报的专家池 `pool 11.4 ms/round` 同量级（口径不同，不作等号）。这解释了参考引擎为何需要 8,106 个专家槽位加自适应换入。

该结论原有一个未闭合的缺口：上表只算了权重，未算 KV；262K 下 12 层稀疏注意力的索引器若要扫描全量 KV，这部分读取可能与权重同数量级。**该缺口已由 G-12 关闭**：引擎只读索引器选中的块，256K 原生上下文下 KV 块读 90.1% 命中显存、整个请求的内存侧 KV 读仅 213.3 MiB（约 1.7 MiB/token），远低于权重读。故本节结论不再受 KV 侧阻塞（对应风险 R-06 未发生）。

更细的步时间模型：

```
T_step ≈ max( T_gpu_compute, T_cpu_experts, T_pcie_budget × IO_amplify / B_eff ) + T_sync

T_gpu_compute ∝ 命中专家字节 / 显存带宽
T_cpu_experts ∝ (1 − h) × 专家字节 / 主机内存带宽
IO_amplify    = 1 / 接受率
```

推论：

- 命中率升高直接降低 CPU 侧耗时。
- 表行按需读的等待（上游实测 16 行串行约 2.10 至 2.61 ms/token）由「token 已知即发起」的重叠窗口与有界行缓存吸收；G-04 已排除提前一步的预取（见第 4 节）。
- 字节预算化避免某一步抢爆 PCIe 造成长尾。
- 接受率下降会按比例放大 PCIe 预算消耗与表行 IO 次数，验证窗口越长放大越大；G-13 实测该系数为 1.05 至 1.27 倍（接受率 0.786 至 0.940）。

## 16. 质量保障

端到端闸门（G-14）：

| 门槛 | 口径 |
|------|------|
| 困惑度 | 默认档相对参考档劣化不超过 1%（建议值；本平台尚未测——原生 pack 下取不到 logits 通路，见下） |
| 任务集 | pass@1 与工具调用成功率不低于参考档（需外部评测 harness） |
| 长文 | 长上下文评测不低于参考档（同上） |
| 贪婪解码 | 只适用于不改变数值表示的开关（归约顺序、图捕获等）。对 KV 精度档不适用：G-14 实测 KV 降档会改变贪心轨迹——int8 与 q4_0 在第 40 个 token、k8v4 在第 57 个首次分歧，序列一致率只有 0.078 至 0.111（见 [`../research/02-qwen3.8-flash-next.md`](../research/02-qwen3.8-flash-next.md) §4.1）。KV 档的验收改用困惑度与任务级判据 |

G-14 已经测得：四档 KV 的 decode 吞吐几乎相同（±2%），即该旋钮买的是显存而非速度；且这台机器上该引擎的逐位复现口径是 `--adapt-every 0 --pcie-frac 0`（只关自适应换入不够）。阈值里的困惑度、任务集、长文三条仍待补。

复合误差白名单以位宽组合为粒度，单旋钮降档与多旋钮同时降档是两种风险：

| 组合 | 权重 | 主 KV | 索引器 KV | 表行 | 备注 |
|------|------|-------|-----------|------|------|
| D1 默认 | IQ2_XS 或 NVFP4 | FP8 | FP8 | 4-bit | 须实测复合后仍过闸门 |
| D2 | IQ3_XXS | FP8 | 4-bit | 4-bit | 先降位置敏感的索引器 |
| E1 实验 | 三值或 2-bit | 4-bit | 4-bit | 低比特 | 禁止进入默认档 |

禁止权重与表行同时降到 2-bit 以下，两者都是每 token 必用的路径。

复合误差的上界只由实测决定，不允许由各项误差上界线性相加推出。

归约顺序与可复现性：结果由显存、CPU、核显三路累加归并，归约顺序不固定就无法逐位复现。本设计定为**按专家 id 全序**（升序）归并，落到两处实现：逐专家路径在 `src/experts/moe_layer`，一层一批的批量路径在 `src/experts/layer_dispatch`。两条路径的「取字节、算、累加」三步都按 id 升序做，路由给出的排名序只决定取哪 k 个、各占多少权重，不参与归并顺序。选它而不是排名序的理由：它不依赖路由并列的打破方式，三路各自算完直接按 id 并入即可，核显那一批的边界（哪几个专家落在核显上）也不必进入求和顺序。测试用结构判据钉住（两条路径的排序排列都在 scratch 的 `order` 字段里），因为合成夹具的值域太规整，换顺序求和仍逐位相同，靠浮点差别判会在夹具上变成空转。

## 附录 A 数据交换优化清单

把每一次数据搬动归入五类，逐类找漏。

别搬（消除搬运）

1. 权重保持压缩态在通道上，只在计算前一刻解压，禁止先解压到高精度再计算。
2. 冷数据直接映射文件，不经主机内存中转。
3. 未命中专家就地计算，不搬回显存。
4. 共享前缀在基数树中只存一份。

提前搬（预取与重叠）

5. 表行在 token 确定时即发起读，与 embedding 落位重叠（不做提前一步的预取，见 §4.1）。
6. 专家提前一至两步按出现概率预取。
7. KV 按块提前于消费点取入。
8. 全部预取与当前步计算重叠，不在关键路径上阻塞。

一次搬够（批量化与对齐）

9. 同一步内的取专家请求聚合为连续大块读；表行请求只能按行 id 去重，不能合并为连续读（见 §4.2）。
10. 传输粒度与专家块、页大小对齐，避免跨块散射。
11. 减少 IO 次数优先于减少字节数。

搬的时候顺便算（融合与就地处理）

12. 反量化融进矩阵乘与注意力核。
13. 路由的归一化、取前 k 与聚集融合。
14. 门控残差的四分支门控融合。
15. 累加归并在同一缓冲区完成，不额外同步。

元开销（最容易漏）

16. 同步点每步只有一次。
17. 解码步的稠密部分用图捕获。
18. 启动时一次性分配，解码步内不分配。
19. 专家槽位按缓存行对齐，避免伪共享。
20. 线程按核心类型分池，不混用。
