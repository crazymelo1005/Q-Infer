# ADR-005：核显 / NPU 作为条件性协处理器，不参与专家主计算

**状态**：Accepted（条件性：专家分担部分依赖 G-07）。G-07 已于 2026-10-09 实测为**算力瓶颈**（见 [research/01-strata-engine.md](../../research/01-strata-engine.md) §5.1），故第二条的启用前提满足；占比如何限制仍待实测（R-08）。
**日期**：2026-10-09

---

## 背景

核显（Intel Arc Xe-LPG，64 EU）提供一组独立于 CPU 的计算单元。能否用它分担未命中专家的计算，取决于未命中路径的瓶颈类型。

关键物理事实：核显与 CPU 共享同一条内存总线（环境2 DDR5-4400 双通道 ≈70GB/s）。因此：

- 核显不增加内存带宽——它和 CPU 争抢的是同一条 70GB/s 的管子。
- 但核显是另一组独立的计算单元——对算力密集而非带宽密集的算子，可以与 CPU 并行工作。

结论取决于「未命中专家路径到底卡在哪」。

台账事实（[research/01-strata-engine.md](../../research/01-strata-engine.md) §13.7 / §13.3）：上游已有 Arc SYCL 端口（PR #423），即「核显作为独立执行设备」不是空白；但上游自己声明集成 Arc 的 shared-memory planning「尚不存在」——「核显与 CPU 共总线时的协同算力规划」确实未被占据。同时共享总线上的实测是负面的：Radeon 780M（共享总线）预取变体 −19%，且内存压力下约 9 次里 7 次出现 GPU 复位（原因未知）。因此本 ADR 的「协同」主张只能靠 G-07 从正面证明，不能靠「无人做过」。

## 决策

分两部分：

### 一、不依赖任何实测、现在就用的三处（无条件采纳）

1. 视觉编码器（ViT ≈1.4GB）跑在核显：独显显存直接省 1.4GB（这笔容量可换成 ~1000 个专家槽位），并省掉一次 H2D 拷贝——图像特征以 host 侧张量交付。
2. 记忆表行的 gather 与加权聚合（[engine.md](../engine.md) §4）：索引算出后，gather/加权求和访存规整、算力需求低，适合核显。
3. 图像/视频预处理：缩放、色彩变换、AV1/HEVC 硬解——核显原生支持，独显完全不参与。

### 二、专家计算分担 —— 门禁 G-07

| 若未命中专家路径是… | 现象 | 决策 |
|---------------------|------|------|
| 带宽瓶颈 | 读字节速度封顶，CPU 在等数据 | 核显无用 → 不做，只能提高命中率 |
| 算力瓶颈 | 数据已就位，但 2–3 bit 码本解码 + GEMM 算不过来 | 核显可分担，与 CPU 并行 |

初判倾向后者（低比特码本解码是整数密集型，核显 DP4a 有优势），但必须先实测 G-07。

## 备选方案

1. 核显完全不用 —— 否决：白丢 ViT 显存节省与预处理卸载这两块无条件收益。
2. 核显承担一半专家计算（无条件） —— 否决：若路径是带宽瓶颈，核显只会加剧总线争抢。
3. 条件性分担（依赖 G-07）+ 无条件三处 —— 采纳。

## 后果

正面
- ViT 移核显 → 无条件省 1.4GB 显存（对 16GB 卡意义重大）。
- 若 G-07 判定为算力瓶颈，核显成为「第二个 CPU 工人」，提高未命中专家吞吐。

负面
- 多一套后端接口（ONE API / SYCL 或 Level Zero），工程复杂度上升。
- 核显与 CPU 共享总线 → 必须限制核显占比，把它当「工人」而非「带宽来源」。
- NPU（Intel AI Boost，≈13 TOPS INT8）强项是 int8 卷积，不适合低成本码本 GEMM → 只用于视觉/小模型侧任务，不参与 MoE 专家计算。

## 接口与边界

- 接口：见 [interfaces.md](../interfaces.md) 第 8 节。该节只覆盖「专家分担」这一条缝；本节第一部分的三处无条件用途是各自独立的管线，不经过它。接口本身不绑定图形 API。
- 边界：核显与 CPU 总吞吐共同受 ≈70GB/s 约束。

接口与运行时的实测现状（2026-10-10，工具 `measure/igpu_probe.c`，记录 `measure/results/20261010T195533-igpuprobe-环境2.json`）：

- 环境2 上核显没有任何计算运行时：无 Level Zero（无 loader、无头文件），OpenCL 只注册了 `nvidia.icd`。Vulkan 加载器与 Mesa 的 ANV 驱动在，故 Vulkan 路线的运行时依赖为零新增，Level Zero 路线则要加装 `intel-level-zero-gpu` 与 `level-zero-devel`。上游那套 Arc 端口是 SYCL，同样依赖 Intel 计算运行时。
- 该设备在 192 项扩展里没有 `VK_KHR_shader_integer_dot_product`，即 Vulkan 路线上取不到 DP4a 等效指令，码本矩阵乘只能手写整数乘加。这与本 ADR 上文「内核走 DP4a（若可用则 XMX）」之间存在口径差：待决项是「改走 Vulkan 并手写整数乘加」还是「加装 Level Zero 以取 DP4a」，两者都要等一个真跑在核显上的码本内核才能比较（工具链前提见上一条）。
- 带宽型争用实测：核显拷贝最好 26.9 GB/s（对总线约 53.7 GB/s）；与 8 线程 CPU 流式读同跑时 CPU 保留 41% 至 46%，两侧合计只有 CPU 单独的 0.98 至 1.10 倍。即带宽型工作下核显是争用者而非增量来源，与本 ADR「把它当第二个工人而不是独立的带宽来源」一致；算力型场景仍待测。

## 门禁（Gate）

P0 标定阶段测 G-07：用一个代表性未命中专家负载，分别测「带宽饱和」与「算力饱和」两种情形，判定主导瓶颈。判为带宽瓶颈 → 本 ADR 第二部分不实施，如实记录负结果。
