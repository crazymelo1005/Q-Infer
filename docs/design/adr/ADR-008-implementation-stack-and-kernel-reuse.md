# ADR-008：实现栈（C++20 + CMake）、内核复用口径与许可

**状态**：Accepted
**日期**：2026-10-10

---

## 背景

实施顺序序 2 要落地第一行引擎代码。仓库此前只有文档与测量工具（Python / 纯 C / CUDA 微基准），没有实现代码，因此有三件事必须先定，否则序 2 无从开始：语言与构建方式、复用外部内核的口径、许可。

已有约束：[engine.md](../engine.md) §17 的来源表把「权重加载与量化内核」标为「已有可调用」；参考引擎与 llama.cpp 都是 C++/CUDA + CMake；本设计的差异在调度与预算（页表、三类流量），不在内核算术。

## 决策

1. 语言 C++20。构建用 CMake（3.28 及以上），不引入包管理器。
2. GPU 侧用 CUDA（nvcc），但骨架的第一片不依赖 CUDA：三层存储与页表是纯主机侧代码，这样 CI 能在没有 GPU 的 runner 上编译并跑测试。CUDA 内核、图捕获等在序 3 之后引入。
3. 内核复用口径：不把 ggml 当外部依赖链接，改为在仓库内维护一份裁剪后的内核子集（vendored subset）。每个这样的文件顶部登记上游路径、提交号与许可；升级等于重新裁剪加复核差异，不做 submodule 指针漂移。理由是本设计要插桩的位置正是内核边界（三类流量的字节预算），而「与上游逐位可比」这条判据需要一个冻结的数值行为。
4. 许可：本仓库 Apache-2.0；vendored 的 ggml / llama.cpp 内核为 MIT，两者兼容。来源与许可登记到 [research/references.md](../../research/references.md)，vendored 文件内保留原始版权头。不复制上游的测试向量：oracle 向量留在测量工具里、由脚本从被测环境读取，不把第三方数据混进仓库。
5. 测试：不引第三方测试框架。`tests/` 下的可执行文件用 `assert`，由 `ctest` 驱动；CI 增加一个构建与测试作业，与文档自检并列。

## 备选方案

1. Rust 或 Go。否决：复用 ggml 内核要走 FFI，而 CUDA 生态在 C++ 一侧，两处都要付跨语言成本。
2. 直接依赖 ggml（submodule 或 FetchContent）。否决为主路径：版本漂移会让「与上游逐位可比」失效，而本设计要插桩的位置正是内核边界。保留为「裁剪成本失控时」的退路。
3. 纯 Python。否决：调度与字节预算是每 token 的热路径。

## 后果

正面：

- 与参考实现同栈，内核可逐位对照；CI 在无 GPU 环境也能守住主机侧的不变量。
- 依赖面为零，不存在版本漂移带来的判据失效。

负面：

- vendored 子集要自己跟上游的量化格式演进（IQ 系列仍在变）。这是把「逐位可比」的代价显式化了，属于本设计愿意付的成本。
- 第一片骨架不含 GPU，因此序 2 的验收只覆盖主机侧；GPU 侧的验收要等序 3。
