# 需求与验收

本文定义引擎要满足什么、按什么口径验收、以及明确不做什么。实现方案见 [design/engine.md](design/engine.md)，必须先测的假设见 [design/gates.md](design/gates.md)。

## 2. 指标与目标值

| 指标 | 目标 | 口径 |
|------|------|------|
| decode 吞吐 | 相对目标基线 ≥1.5× | 同机、同量化档、同任务集、同并发 |
| TTFT 与 prefill 吞吐 | 相对目标基线 ≥1.3× | 同上 |
| 显存占用 | 不劣化 | 不得以增加常驻需求换取速度 |
| 输出质量 | 逐 token 分布不变；量化误差有界且可测 | 投机只做验证；量化误差须有上界与评测 |

命中率不作为优化目标。该指标在参考引擎的定义中不保证与速度同向，仅作观测量记录。

## 3. 目标基线（分母）

全部倍数指标的分母为环境2 上的实测基线，不是任何上游公布的估算值。基线口径与逐项数字见 [research/01-strata-engine.md](research/01-strata-engine.md) §10.3，原始记录 `measure/results/20261009-baseline-*-环境2.json`。口径为：同一份部署配置（`--kv int8`、`--expert-cache auto`、`--batch 4`）、greedy、真实基准文本、单请求、发 256 个 token、同一实例内 5 次。

| 形态 | decode 冷（第 1 次）/ 稳态（中位） | prefill 冷 |
|------|--------------------------------|-----------|
| 单卡（硬下限） | 57.97 / 64.44 tok/s | 1,258 tok/s |
| 双卡（扩展形态，4K 提示） | 75.13 / 85.96 tok/s | 561 tok/s |
| 双卡（32K 提示） | 73.76 / 89.33 tok/s | 1,855 tok/s |

按第 2 节的目标倍数换算出的验收靶子（分母取稳态中位；TTFT 的快 1.3 倍等价于 prefill 吞吐 ≥1.3×）：

| 形态 | decode ≥1.5× | prefill 吞吐 ≥1.3×（等价 TTFT ≤ 基线的 1/1.3） |
|------|-------------|------------------------------------------|
| 单卡 | 96.7 tok/s | 1,636 tok/s |
| 双卡（4K） | 128.9 tok/s | 730 tok/s |
| 双卡（32K） | 134.0 tok/s | 2,412 tok/s |

两处口径提醒：prefill 的稳态值不可用（第 2 次起提示被前缀复用，剩下的是尾段速率，会算出假的高值），TTFT 与 prefill 一律以冷启动为分母；decode 的冷启动与稳态相差 10% 至 12%，两者不可互相替代。

上游曾公布的估算档位（自注旧口径、未按环境2 的 PCIe 链路重测，偏差约 ±20%）decode 落在 53 至 80 tok/s；实测稳态中位落在这个区间内，说明其绝对量级可信，但不作为验收基线。单卡基线里最要紧的一条：参考引擎只给一张卡时专家槽位从 11,952 掉到 3,838、会话命中率从 95.2% 掉到 78.0%（见 research/01 §10.3）。

## 4. 验收场景

- 必须包含「262K 上下文 × 高比特量化档」。该组合在上游公开的速度表中为空缺，是本项目唯一可量化、且已知他人未做到的验收点。
- 预取类结论必须在两种内存余量下分别验收：主机内存余量紧张与余量充足。上游同方向机制在紧张条件下为负收益、在充足条件下为正收益，结论会翻号。
- 统计口径：每次配置重复不少于 5 次，报中位数与区间；固定任务集与随机种子；禁用随机 prompt。
- 冷启动与稳态分开验收，不得互相替代。

## 5. 设计约束

约束即设计输入。全部数值按环境 2 口径读取。环境 1 是本机（Windows 宿主 + WSL2），环境 2 是另一台原生 Linux 机器；两套口径不可混用。

| 约束 | 环境 2（285K / 64GB DDR5-4400 / 双卡 / 原生 Ubuntu） | 环境 1（265K / 48GB DDR5-8400 / 单卡 / Windows 宿主 + WSL2） |
|------|------------------------|------------------------|
| 显存 | 2 × 16 GB（单卡 16 GB 为硬下限，可用约 13.5 至 14 GB） | 1 × 16 GB |
| 显存带宽 | 448 GB/s（Blackwell sm_120，无 NVLink） | 同 |
| 主机内存 | 64 GB DDR5-4400 标称，可见 61.0 GiB；实测已用 73% 至 90%，可支配余量仅 6 至 16 GiB | 48 GB DDR5-8400 |
| 内存带宽 | 约 70 GB/s | 约 134 GB/s（为环境 2 的 1.9 倍） |
| PCIe | 5.0 x8 + x8，每卡约 31.5 GB/s 单向 | 5.0 x8，约 31.5 GB/s（该型号显卡电气为 x8 [S-32]） |
| 存储 | NVMe，顺序读约 7 GB/s | 同 |
| CPU 指令集 | 仅 AVX2，无 AVX-512 / AMX | 同 |
| 核显 / NPU | 核显与 CPU 共享内存总线，不增加带宽；NPU 不参与专家计算 | 同 |

平台差异同样计入约束：环境 1 实际跑在 Windows 宿主之上的一台 WSL2 虚拟机内（`.wslconfig` 把虚拟机内存上限定为 16GB，实测可见 15.6 GiB；GPU 经 `/dev/dxg` 直通），环境 2 是原生 Linux。因此环境 1 的**内存容量**与 **PCIe 有效带宽**有两套口径（WSL 内与 Windows 宿主），引用时必须写明测在哪一侧；内存**带宽**经 2026-10-09 实测两侧基本相同，差别在容量。

另外，上游参考引擎在 WSL 下无法使用 KV 流式（上游注明 never under WSL），其 Windows 宿主侧也没有原生构建，因此环境 1 不作为相对参考引擎提速的对照平台；单卡硬下限的验收在环境 2 上以仅启用一张卡的方式进行。

两条推论：

1. 内存余量（6 至 16 GiB）与设计中需要常驻的对象（外挂表 28.8 至 51 GB、专家 pinned 区约 17 GB）量级相近而方向相反，因此主机内存预算是硬门禁。
2. 环境 1 的内存带宽约为环境 2 的 1.9 倍。CPU 侧未命中专家路径的瓶颈强度取决于采用哪套环境，引用该结论时必须写明环境。**该比值已由同一脚本、同一参数实测**：triad 87.2 对 53.7 GB/s（1.62 倍），copy 110.1 对 64.4 GB/s（1.71 倍），厂商规格比值为 1.91。两侧必须同为「引擎未运行」才可比：环境2 在引擎常驻时测量会偏低——该引擎约占 43 GiB 主机内存、系统 swap 已用到 91%，此时 triad 降到 42.9 GB/s，比值被高估到 2.03 倍（见 `hardware.md` 两份实测值表）。因此环境 1 的 CPU 侧专家吞吐上限明显高于环境 2，`G-07`（未命中路径是算力还是带宽瓶颈）在两套环境给出相反结论的可能性是真实存在的。
3. 两套环境的单卡 PCIe 带宽相同（均为 5.0 x8，约 31.5 GB/s）[S-32]：环境 1 只在内存带宽与容量口径上与环境 2 不同，PCIe 上没有优势。因此任何「环境 1 的 PCIe 更快」的推论都不成立。

## 6. 非目标

| 不做 | 原因 |
|------|------|
| 通用多模型、多后端平台 | 只做垂直切片：单模型、单硬件代次 |
| 多机与分布式推理 | 第一版不做；环境2 的上限为双卡 |
| 超出原生窗口的工作区虚拟化 | 原生 262K 已覆盖验收场景；若要做须独立成 ADR |
| 训练、微调、数据管线 | 与推理引擎正交 |
| GPU 稠密内核从零重写 | 复用 ggml 血统，创新在调度与介质 |
| 发明新的量化算法 | 只提供可插拔精度接口，量化方法为外部输入 |
| 服务端式高并发吞吐 | 目标并发 2 至 8，不为上千 QPS 优化 |
| 额外的通用压缩（如 zstd / LZ4 权重） | CPU 成本高、收益不明确 |
| 以命中率作为优化目标 | 该指标与速度不保证同向 |
| 无证据的倍数承诺 | 分母必须是环境2 上的实测 |

### 6.1 应改用其它引擎的场景

以下场景本设计不占优，正确做法是换引擎，而不是修改本引擎。

| 场景 | 占优者 | 原因 |
|------|--------|------|
| 高并发与服务化吞吐 | 服务端派引擎 | 其收益来自大批量把向量乘转为矩阵乘；本设计目标并发仅 2 至 8，且每张卡的 KV 池与状态池随并发同步增长，容量先于调度成为瓶颈 |
| 模型能整份塞进显存 | 服务端派引擎、原生低精度稠密引擎 | 此时分层与预取全部失效 |
| 新模型的首日支持 | 服务端派引擎 | 有官方资源与内核团队跟进；本设计每遇到新架构都要自写内核 |
| 工程存量与内核成熟度 | 成熟开源引擎 | 量化内核、跨平台后端与机器画像是多年积累 |
| KV 分层的服务化深度 | KV 缓存层项目、上下文虚拟化项目 | 已有成熟体系，且同类项目已在本代 16 GB 卡上实现 256K 近无损 |
| 多卡与多机扩展 | 服务端派引擎 | 本设计禁用每层同步的张量并行，代价是放弃这条扩展谱系 |
