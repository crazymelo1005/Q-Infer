# ADR-019：核显不参与未命中专家计算（P3b 不做）

状态：Accepted（2026-10-14）

---

## 背景

[ADR-005](ADR-005-igpu-npu-as-coprocessor.md) 的第二节把「核显分担未命中专家」设为条件性方案，门禁是 G-07；G-07 于 2026-10-09 判定未命中路径是算力瓶颈，该前提成立。据此 [ADR-014](ADR-014-gpu-igpu-serve.md) 的阶段 C 建成了核显侧资产（`src/experts/igpu`：Vulkan 运行时 + Q2_0 GEMV + 融合 silu 量化），P3a 又补齐部署包实际使用的三个 gate/up 档位着色器（IQ2_S、IQ2_XXS、IQ1_M），三者与主机内核逐位一致（bit-same 1.000、L1 相对误差 0）。

剩下的问题是 P3b：把这些着色器接到厂商化引擎的 `PoolFn` 缝上，让核显真的参与一次解码。该阶段自带证伪点——「若核显不显著快于 CPU 池，就地停下、把读数写进 ADR，P3b 不做」。测量已完成，判定为不通过。

测量口径（环境2，2026-10-14，引擎停机，工具 `igpu_gemv_bench`；原始读数 `measure/results/20261014T075400-igpugemv-环境2.json`）：批形状取自部署包 `gsq-rco-iq2_xs` 的真实几何——一个 gate（或 up）矩阵 = 640 行 × 10 个 IQ 块（`expert_feed_forward_length` 640 / 隐藏 2560 / 每块 256 值），一个解码 token 路由到 10 个专家，故一批 = 20 个该形状矩阵 = 12,800 行。四个臂跑同一份字节：`host1` 主机内核单线程、`hostT` 主机内核按行切给 T 线程、`gpu` 权重常驻设备下的纯分派（计算下限）、`gpu_e2e` 每矩阵上传 + 分派 + 收尾下载（P3b 实际会付的代价）。每臂取多轮最小值，下表给当日各轮（同形状 3 至 4 轮）的区间：主机臂跨轮复现到 2% 以内，设备臂波动达 1.4 倍，故判定取对设备最有利的读数。

真实批形状（20 矩阵 = 12,800 行/批）：

| 档 | 批字节 | host1 | host8 | host16 | host24 | gpu（分派） | gpu_e2e |
|------|-----------|--------|-------|--------|--------|-------------|---------|
| IQ2_S | 10.010 MiB | 16.7 至 16.9 ms | 2.18 至 2.19 ms | 1.19 至 1.20 ms | 0.97 ms | 9.5 至 13.3 ms | 15.3 至 19.8 ms |
| IQ2_XXS | 8.057 MiB | 15.1 至 15.2 ms | 1.96 至 2.02 ms | 1.06 至 1.11 ms | 0.87 ms | 11.3 至 15.6 ms | 22.3 至 28.9 ms |
| IQ1_M | 6.836 MiB | 15.5 ms | 2.00 至 2.04 ms | 1.08 至 1.11 ms | 0.87 ms | 10.7 至 15.0 ms | 20.5 至 26.7 ms |

换成吞吐比：纯分派臂为 8 线程池的 0.13 至 0.19 倍，端到端臂为 0.07 至 0.12 倍；端到端臂还慢于单线程主机（耗时 1.09 至 1.69 倍），纯分派臂只略快于单线程主机（耗时 0.69 至 0.91 倍）。

## 对照实验

单看真实批形状不足以定案——它还可能是「形状对设备不友好」或「主机赢在缓存」或「分派开销冒充计算慢」。三项对照分别排除这三条，第四项把设备侧唯一有效的杠杆拉到极限。

一、合批上限（G1）：恒定 12,800 行/批与同样的批字节，只改每次分派的行数。设备吞吐随单次行数上升：640 行 0.86 至 1.00 M 行/秒、1,280 行 1.52 至 1.77 M、3,200 行 2.49 至 2.86 M、6,400 行 2.16 至 3.33 M。这条杠杆由引擎的交活粒度封顶：`PoolFn` 一次给一层一 token 的 k 个专家（k ≤ 10，`third_party/strata/include/strata/core/session.hpp:314`），一次调用最多把 10 个专家的 gate 合成 6,400 行一次下发。**把这条杠杆拉满，设备仍只有 8 线程池的 0.23 至 0.52 倍**（端到端 0.13 至 0.27 倍）。

二、算力上限（C1/C2）：把三档各自的活合成单次 25,600 行大分派、权重常驻、无逐矩阵开销、多次取优——这一形状超出上一条的合批上限，只是排除性对照——设备得 4.99 至 6.21 M 行/秒，为 host8 的 0.64 至 0.94 倍、host24 的 0.23 至 0.34 倍。即设备的原始算力约合 5 至 6 个单核，但那是缝外才够得着的形状。

三、工作集放大（S1）：200 个矩阵、IQ2_S 100.1 MiB，远超 36 MiB L3。host8 6.10 至 6.75 M 行/秒、host16 12.1 至 13.3 M、gpu 1.12 至 2.70 M、gpu_e2e 0.78 至 1.03 M——放大后 CPU 吞吐不降反升，争用点不在带宽，主机不是赢在缓存常驻。

四、逐分派固定开销（O1）：0.09 至 0.14 ms 一次（两次 64 行极小分派合计 0.18 至 0.28 ms）。真实批 20 次分派合计 1.8 至 2.8 ms，只占同臂实测（10.7 至 14.8 ms）的两成以下——分派开销既不是差距的主项，也就不能靠「减少分派次数」把它抹掉。

## 判据

把两边换算到同一量纲（M 行/秒 对 单核）：真实批形状下整块核显约合 **1.1 至 1.5 个单核**；在 `PoolFn` 缝内合批到上限约合 **1.8 至 4.2 个**；只有超出该缝的单次大分派才约合 **5 至 6 个**。这台机器有 24 个逻辑核，主机池 8 线程 5.85 至 6.75 M 行/秒、16 线程 10.7 至 13.3 M、24 线程 13.2 至 18.3 M，加线程近乎线性且未见饱和。**核显在任何可部署形态下都到不了 CPU 池的一半，而 CPU 侧还有比加一组设备更有效的那条杠杆。**

## 补充测量：稠密投影（P1 spike，2026-10-14）

本节结论只针对 MoE 专家的小矩阵（640 行）。为验证「大矩阵是否不同」，同日对 GDN 稠密投影的典型形状做了对照测量（工具 `measure/igpu_dense_spike/`，IQ4_XS × Q8_K，attn_qkv 形状 10240 × 2560，权重 13.28 MiB，激活 2.85 KiB，10 个 IQ 块/行）：

| 臂 | 耗时 | 相对 CPU |
|------|---------|----------|
| CPU（单线程，库函数 `iq4xs_gemv_q8k`） | 6.39 ms | 1.00× |
| iGPU（Intel Arc ARL，160 个 workgroup × 64 线程，权重常驻） | 1.64 ms | 3.9× 加速 |

数值误差：0（逐位一致，max abs/rel error = 0）。

**这条读数与上一节的专家形状形成对比**：同样的 IQ4_XS × Q8_K 内核、同样的 Vulkan 运行时，矩阵从 640 行扩到 10240 行后，iGPU 从「慢 10 倍」翻转为「快 4 倍」。原因在上一节的 G1 对照里已经指出——占用率。640 行只开 10 个 workgroup，填不满 4 个 Xe 核；10240 行开 160 个 workgroup，设备被充分占用。

**该读数不推翻本 ADR 的决策**：P3b 不做，因为 MoE 专家的矩阵形状由 `expert_feed_forward_length` 640 决定，缝内合批上限 6400 行仍只有 8 线程池的 0.23 至 0.52 倍。但该读数**支持核显承担另一类任务**——GDN 稠密投影（attn_qkv 10240×2560、attn_gate 6144×2560、ssm_out 2560×6144），这些任务占 CPU 计算的 28%（见 `../gates.md` G-07 的 CPU 计算分解），且矩阵规模足以填满 iGPU。

读数本身已足够定案，以下是对差距来源的解释，按证据强度分开写。已被本仓库直接复现的部分：着色器只能把 int8 乘加写成标量序列（`src/experts/igpu/shaders/*.comp` 里没有任何 `dot` 调用，`measure/igpu_probe.c` 报告的 192 项扩展里没有 `VK_KHR_shader_integer_dot_product`），而主机侧这些内核是可移植 C++，构建里没有 `-march` 开关（基线 x86-64，本机亦无 AVX-512，见 R-04），却仍跑赢整块核显。G1 那组形状证据进一步指出剩下的差距是占用率：640 行一次分派只开 10 个 workgroup × 64 调用，填不满设备，单次行数增加能回收 2 至 3 倍，但缝把它封顶在 6,400 行。

未被单独证实的部分：「扩展名没列」不等于「指令取不到」——该扩展在 Vulkan 1.3 已进核心，核心版本下驱动可以不列扩展名；一次手写的 pNext 能力位探测曾给出自相矛盾的读数（逐 op 属性全 0 而同结构的能力位读到 1），故本 ADR 不把它当判据。判据只有耗时读数本身。任何重启该方向的工作要先在同一批形状上复测，而不是引用本节对原因的说法。

## 决策

1. 不做 P3b：不把核显着色器接入厂商化引擎的 `PoolFn`，不引入 `--igpu-frac`，不写构建期补丁 `tools/patches/p3-igpu-pool.patch`。
2. P3a 的资产保留在仓库里并继续进 ctest（`igpu_runtime`、`igpu_gemv`、`igpu_iq2s`、`igpu_iq2xxs`、`igpu_iq1m`）。判据是「按真实批形状能不能替 CPU 干活」，答案是不能；资产本身逐位正确、成本只是构建期一次 glslang 生成，留着作为将来非专家用途（[ADR-005](ADR-005-igpu-npu-as-coprocessor.md) 第一节那三处）与跨设备移植的基线，但不接任何执行路径。
3. 核显在 MoE 专家计算上的定位回到 [ADR-005](ADR-005-igpu-npu-as-coprocessor.md) 第一部分的口径：只承担视觉编码器、记忆表 gather、图像/视频预处理这三处，不承担专家 GEMV。该 ADR 第二节的条件分支按本节判为不启用，其「启用后占比如何限制」的后续问题一并关闭（R-08 同步收窄）。
4. 未命中专家路径的算力扩展走 CPU：同一档、同一次运行里从 8 线程加到 16 线程吞吐近乎翻倍（IQ2_S 5.87 至 10.74 M 行/秒），加到 24 线程 13.21 M 且未见饱和——这条杠杆比在缝内合批到极限仍只有半个 CPU 池的设备有效得多。

## 备选方案

1. 做 P3b，按「核显免费、多一组工人」的思路分摊一部分专家。否决：P3b 实际要付的 `gpu_e2e` 臂慢于单线程主机（耗时 1.09 至 1.69 倍）、只有 8 线程池的 0.07 至 0.12 倍——设备执行的 job 在其整个生命周期里占着一个 CPU 线程等结果，净效果是把池的吞吐往下拉而非往上抬。
2. 设备侧合批（一次 `PoolFn` 调用把 10 个专家的 gate/up 各合成 6,400 行一次下发、权重常驻不上传）。这是 P3b 能做到的最佳形态，已按 G1 直接量过：0.23 至 0.52 倍。否决——合批是设备侧唯一有效的杠杆，而它由引擎的交活粒度封顶。
3. 先把着色器优化到能打过 CPU 再决定。否决：要抹平的是相对 8 线程池 5 至 8 倍（真实形状）、2 至 4 倍（缝内合批到极限）的差距，而可用的杠杆都很薄——该机上核显没有可用的整数点积内建（扩展列表未给，见上文的证据强度说明），把码本放进 shared memory 也只是把全局内存延迟换成搬表成本；把余下差距抹平所需的工程量与 P3b 同量级，而收益上界只是「打平 CPU 池」，同时主机还能继续加线程。
4. 把核显资产删除，避免留死代码。否决：资产是被 ctest 钉住的逐位正确实现，删除等于丢掉 ADR-005 第一节那三处用途的既有能力与阶段 C 的交付物；本节要关的是执行路径接线，不是内核本身。

## 后果

正面：

- 省下 P3b 的全部工程与风险：构建期补丁（改 `third_party/strata` 之外的 `build-engine/src`）、设备与引擎之间的字节几何耦合、`--igpu-frac` 与图捕获的互斥逻辑、真机分摊实测。补丁这条路线尤其危险——它每次升引擎都要重验证。
- 决策依据落在可复现的量纲与形状上：不是「没测出收益」，而是「在缝内能合的最大批、权重常驻、多次取优的条件下仍不到 8 线程池的一半」，且主机加线程近乎线性。
- 补充测量（P1 spike）明确了核显的有效适用面：大矩阵稠密投影（10240 行级别）可获得 3.9 倍加速，为后续 iGPU 承担 GDN 投影提供了实测依据。

负面：

- [ADR-014](ADR-014-gpu-igpu-serve.md) 的阶段 C/D 中「核显参与专家主计算」这一条就此关闭，异构分工求解器（其 `--igpu-frac` 输入）没有实现对象，本仓库的 GPU 卸载面只剩 CUDA 侧的稠密段与 KV。
- 判定只在环境2 的这块 Arc 核显 + 这一族 IQ 档上做成立。换到有 `VK_KHR_shader_integer_dot_product` 的设备（有 DP4A 等效指令）时，本节结论不可外推——那条路上「核显是第二组算力」的前提可能重新成立。任何重启该方向的工作必须先在同一批形状上复测，而不是引用本 ADR 后直接开工。
- 计时只覆盖 gate/up 三档；阶段 C 的 down（Q2_0）与融合 silu 量化两枚着色器未单独计时。它们与 gate/up 同形状同量纲，结论应当同样适用，但这是口径提醒，不是独立证据。
- 着色器与主机内核是两套实现，档位布局若变动需同步维护；两者由逐位对拍测试约束，漂移会被 ctest 抓到。
