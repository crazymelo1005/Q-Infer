## 2. 四项架构改动（每一项都是推理引擎的实现约束）

### 2.1 GDN + QSA 混合注意力

- 每 4 层里 3 层 Gated DeltaNet（GDN）：把历史压进固定大小循环状态。
- 第 4 层 Qwen Sparse Attention（QSA）：做精确远程检索。
- 按 48 层推算：36 层线性注意力 + 12 层稀疏注意力。
- QSA 借鉴 DSA 的「轻量索引器打分选片段」，但把索引本身也压缩：连续若干 token 打成 micro-block → 池化成代表 KV → 轻量 MQA 给块打分 → 取 top 块展开回原始 token 做真注意力。索引开销由 O(n²) 降到 O(n²/压缩比)。
- 官方收益（1M 上下文）：prefill 快 10.2× / decode 快 6.6×（attention kernel 口径，[摘要级]）；论文口径为 prefill 7.6× / decode 4.9×。

对引擎的含义：大部分层不存完整 KV（省容量、省带宽），但 GDN 的循环状态随并发序列数增长、QSA 的 KV 仍全量存储（只读得稀疏）。

### 2.2 Gated Residual（GR）

- 残差流从 1 条拓宽为 4 条并行分支。
- 读用低秩瓶颈网络算逐元素门控（四分支加权平均）；写只用每分支一个标量门。
- 去掉了 Hyper-Connections 的 Hres 混合算子（它要多读一遍完整残差状态，在固定参数量推理下是主导性内存搬运）。
- 训练中学出自然分工：1 条跑长途（第 0 层输出被第 15/19 层等全局注意力层大量读），其余 3 条跑相邻层短程。

对引擎的含义：GR 权重属于「每 token 必用」，必须常驻显存。

### 2.3 N-gram Embedding（51B 外挂表）

- 把当前位置前若干 token 拼成 key → 去大表查向量 → 叠加到表示上。加容量不加计算。
- 关键性质：访问稀疏且确定——查哪几行可以提前算出来。
- 模型设计口径：表放在第 2 层，让主存预取与第 1 层计算并行重叠（串行→并行的设计）。

> 引擎侧现实：Strata 把它放在 SSD、每 token 经 OS page cache 只读若干小行，并没有专用预取器。所以「模型自带并行预取」是设计意图，不等于引擎实现。

对引擎的含义：这是一块 28.8–51GB 的显存外记忆。注意：「表行异步预取」并非空白 —— vLLM 官方 recipe 的 `VLLM_PLE_CPU_OFFLOAD=1` 与 Qwen 官方 README 都已实现（[官方]，见 [05-engine-landscape.md](05-engine-landscape.md) §7.2），故它不能单独作为本设计的差异点；§3.2 进一步显示该预取的收益前提（行访问有可利用的局部性）不成立。

### 2.4 MTP（Multi-Token Prediction）

- 自带 4B 多 token 预测头，可直接做投机解码，无需外挂草稿模型。
- 官方/引擎推荐 `num_speculative_tokens: 3`；显存紧时下调。
- 官方提醒：测 MTP 收益要用 SPEED-Bench（`--dataset-name speed_bench`），不要用随机数据——随机 prompt 的接受率与真实任务严重偏离，会把结论做反。

## 3. KV 结构：两条缓存必须分开记账

| 缓存 | 在哪几层 | 随什么增长 | 随上下文增长？ |
|------|---------|------------|----------------|
| GDN 循环状态 | 36 层线性注意力 | 并发序列数 | ❌ 否（固定大小） |
| QSA 的 KV + 索引器 KV | 12 层稀疏注意力 | 上下文长度 × 并发数 | [已确认] 是 |

推论：
- 拉长上下文只吃 QSA 那 12 层的显存。
- 拉高并发则两条一起涨。vLLM 上 `--max-num-seqs` 一调大就报 Mamba-cache capacity error，就是第一种撞墙。
- 索引器的 KV 也可量化：vLLM 官方配置除 `--kv-cache-dtype fp8` 外还要 `--attention-config.indexer_kv_dtype fp8`——即 QSA「挑块打分」用的那份表示单独还有一个精度旋钮。

### 3.1 索引器与稀疏注意力的几何

主注意力与索引器的几何现已直接从 GGUF 元数据取到（无需 HuggingFace 的 `config.json`）[S-33]：

| 项 | 值 | 来源 |
|----|----|------|
| 主注意力 | `head_count` 24、`head_count_kv` 2（GQA 24:2）、`key_length` 256、`value_length` 256（即 head_dim 256）、`embedding_length` 2560 | [环境2实测] |
| RoPE | `dimension_count` 64、`dimension_sections` [11, 11, 10, 0]、`freq_base` 1e7 | [环境2实测] |
| QSA 层与压缩比 | `attention.compress_ratios` 48 项，每 4 层出现一个 4 → 恰好 12 层 QSA、压缩比 4（其余 0，即 GDN 层） | [环境2实测] |
| 索引器 | `head_count` 4、`key_length` 128、`top_k` 2048 | [环境2实测] |
| 块压缩（二手口径） | 4 token → 1 条压缩 key；索引缓存每 4 token 存 1 条 BF16 key；未完成块走 4 槽环形缓冲 | [摘要级] |
| N-gram 表 | 独立分片中的单个张量 `per_layer_token_embd.weight`，dims = [160, 320,001,536]、GGUF 类型码 20 = IQ4_NL → 512 亿参数，4-bit 约 28.8 GB；行宽 160 与 `embedding_length_per_layer_input` 一致 | [环境2实测] |

一处口径待核：二手来源称「选 top-512 块 → 展开到 2048 个 token 位置」，而元数据里的 `indexer.top_k` 是 2048——两者可能分别是「块」与「token 位置」两个口径，也可能二手数字有误。引用时须注明是哪个口径。

由此给 G-12 一个可算的输入（[推算]，几何为实测）：262K 上下文下，索引器的稠密扫描每 token 读字节 ≈ `(262144 ÷ 4) × 128 维 × 字节 × 12 层`：

| 索引器 KV 精度 | 每 token 扫描字节 |
|---|---|
| BF16（上游默认） | ≈ 192 MiB |
| FP8 / int8 | ≈ 96 MiB |

对照每 token 激活权重读（IQ2_XS ≈1.8 GB），索引器扫描约为其 5–11%：不主导、但不可忽略。

但真正决定 A2 成立与否的不是字节量，而是这 192 MiB 从哪里读：全部 12 层的索引键合计约 192 MiB，本可常驻显存；若实现上不常驻、要走 PCIe，则按实测单向带宽 26.6 GB/s 折算约 7.4 ms/token，而实测步长约 11.6 ms（86 tok/s）——那样它就主导了。因此「瓶颈不在带宽」这一条的正确验证方式是索引键的驻留率（读 `kv_resident` 与 `pcie_share`），而不是只算字节量。见 `design/gates.md` 的 G-12。

G-12 已实测（环境2，2026-10-09）：**参考引擎并不做索引器的稠密扫描**，它只按索引器选中的块去读。256K 原生上下文下 KV 块读的显存命中率 90.1%，一个 256K 请求（256,094 提示 + 128 解码）的内存侧 KV 读合计只有 213.3 MiB——约 1.7 MiB/token 且大部分在预填期，比 192 MiB/token 的稠密推算低约两个数量级。故上面这条担忧在参考引擎上不成立；那条推算是上界而非实际行为。见 [`01-strata-engine.md`](01-strata-engine.md) §7.2。

### 3.2 表行访问局部性（G-04，离线重放）

表行的访问序列与机器无关：它由 token 序列与 n-gram 哈希唯一决定。因此可用离线重放测量——用参考引擎自身的哈希实现（`src/kernels/ngram.cpp` 的 `ngram_rows`，常量取自其 `ngram.hpp`）在分词后的语料上重放行索引。重放工具为 [`measure/ple_locality.py`](../../measure/ple_locality.py)，其哈希已与该引擎自带的 6 组 oracle 向量逐位比对通过；原始记录在 [`measure/results/`](../../measure/results/) 的 `*-plelocality-环境2.json` [环境2实测]。

规则 [S-34]：一个 token 读 16 行；头 0 至 7 是 2-gram、8 至 15 是 3-gram；每头一行，落在该头独占的连续区间内（16 个区间首尾相接，各自约 20,000,000 行、约 1.8 GB，合 320,001,536 行）。语料取自参考引擎仓库自身的文档与源码（与它的 needle 基准同一取材），三档上下文 4K / 32K / 262K token，另加 48 条按文件切分的独立请求（约 80K token）。

| 语料 | 行请求 | 不同行 | 行重复率 | 不同 4KiB 页 | 相邻请求同页率 | 去重后同页率 | 行缓存命中率（2^20 行） |
|------|-------|-------|---------|-------------|--------------|-------------|----------------------|
| 4K | 65,536 | 47,009 | 0.283 | 46,835 | 0 | 0 | 0.283 |
| 32K | 524,288 | 303,857 | 0.420 | 297,197 | 0 | 0 | 0.420 |
| 262K | 4,194,304 | 1,704,915 | 0.594 | 1,502,859 | 0 | 0 | 0.578 |
| 48 条独立请求 | 1,283,856 | 653,280 | 0.491 | 622,976 | 0 | 0 | 0.491 |

结论：

1. 去重后无顺序性，且是结构性的。相邻两次请求同页率为 0，去重后仍为 0。原因与语料无关：16 个头把表切成 16 个互不相邻的区间，一个 token 的 16 行必落在 16 个不同区间，而相邻两次请求（同 token 内换头，或跨 token 换头）必然异区间，故必然异页。「按页合并为顺序大块读」因此不可能成立。
2. 有局部性，但只是长距离复现。行级重复率随上下文从 0.283 升到 0.594；262K 档的复用距离 p50 约 10,240 次请求（约 640 token）、p90 约 521,744 次、p99 约 1,938,464 次。重复中落在 16 次请求窗口内的只占 0.14%、64 次内 1.06%、4,096 次内 38.9%。故「提前一步预取」的命中上界约 0.1%，而参考引擎自带的 8 路组相联行缓存（默认 2^20 行、约 90 MB）能吃下可观的长距离重复：三档命中率 0.28 / 0.42 / 0.58。
3. 触达面很小。262K 档全序列只触及约 1,704,915 个不同行（占表 0.53%）、约 1.5M 个 4 KiB 页（约 6.1 GiB）；一个 token 的表行读合计仅 1,440 字节。参考引擎源码注释给出的对照实测是：mmap 路径下这 16 行是 16 次散落页缺页、串行进行，约 2.10 至 2.61 ms/token，折合 0.5 MB/s，属延迟受限而非带宽受限。

对引擎的含义：门禁 G-04 的通过标准是「去重后存在可利用的顺序性或局部性」，实测两项皆无，故不通过；表行预取子系统被砍，退守按需读加有界行缓存（决策见 `design/adr/ADR-007-ngram-table-on-demand-read.md`）。这同时推翻了本节 §8 第 3 条此前把「表行显式预取」列为最值得下注差异点的判断，也说明 §2.3 所述「模型把表放在第 2 层以便预取与计算重叠」在收益上不成立——左移一个 token 的确定性窗口并不带来命中。

### 3.3 表行读的往返延迟与能否藏进一个步长（G-10）

砍掉预取后，剩下的问题是「按需读的往返能不能藏进一个 decode 步长」。两部分都已在环境2 实测。

**往返微基准**（工具 `measure/io_roundtrip.cu`，原始记录 `measure/results/20261009-ioroundtrip-*-环境2.json`）：一轮 = 从 26.8 GB 的表分片里随机取 16 个 4 KiB 页串行读（正对一个 token 的 16 行），再一次 H2D 拷进显存并同步。

| 模式 | lane | 读腿 P50 / P99（us） | 整条往返 P50 / P99（us） | H2D 段 P50 |
|------|------|---------------------|------------------------|-----------|
| direct（O_DIRECT，引擎默认） | 充足 | 1,473 / 1,959 | 1,481 / 1,973 | 8 |
| direct | 紧张（先占 44 GiB） | 1,479 / 2,083 | 1,487 / 2,097 | 9 |
| cached（带页缓存） | 充足 | 943 / 1,083 | 957 / 1,097 | 14 |
| cached | 紧张 | 936 / 1,241 | 951 / 1,329 | 15 |

三点读数：

1. **往返由 16 次随机页读主导**，H2D 段只有 8 至 15 us（16 页 = 64 KiB，过 PCIe 可忽略）。
2. **内存 lane 几乎不改变结果**：direct 的 P50 只差 0.4%、P99 差 6%；cached 的 P99 差 21%。因为 O_DIRECT 绕过页缓存，而读的又是 26.8 GB 文件里的随机页，页缓存在两个 lane 里都帮不上忙。这与设计早先引用的「暂存式预取在紧张 lane 为负收益」（上游 −32.6%）不是同一件事：那条说的是把数据暂存进 RAM 的机制，本次量的是不落缓存的按需读。
3. 旁注：O_DIRECT 比带页缓存的读慢 56%（1,481 对 957 us P50）——引擎的 direct 模式放弃了预读与合并 IO。

**decode 步长分布**（起 serve，4K 提示、512 输出 token，按 5 ms 轮询 `/metrics` 的 `live.tok_s` 取倒数，原始记录 `measure/results/20261009-stepprobe-4k-环境2.json`）：P50 12.74 ms、P90 15.08 ms、P99 50.0 ms、均值 14.26 ms；引擎自报的同一次请求为 12.05 ms/token（82.98 tok/s），两者一致。

**判定**：往返 P99 2.10 ms 远小于步长 P50 12.74 ms（约 6 倍余量），紧张 lane 下同样成立 → 按需读的往返能藏进一个步长。口径两点：步长取自引擎自己的瞬时速率而非其内部逐步计时；紧张 lane 只对微基准做了——引擎自身约占 43 GiB（61 GiB 机器），部署状态本身就是紧张 lane，无法构造「引擎常驻且余量充足」的组合。

|------|-----------|------------------|------|
| BF16 | 2.0 | 约 54GB | 官方含视觉约 55.6GB |

| GGUF 混合低比特 | ≈0.315（全档）、≈0.294（仅专家） | — | 环境2 实际使用档：逐层混 IQ2_S / IQ2_XXS / IQ1_M / Q2_0，等效约 2.35 bpw，见 [S-36] |
| GGUF IQ3_XXS | ≈0.35 | — | 社区常用档（文件 71GB） |

> 徽章：Byte/参数与「27B 级别参考体积」列为 [推算]；第一行「GGUF 混合低比特」为 [环境2实测]（分量表与专家字节合计见 [S-36]）；备注中的官方数字（含视觉 55.6GB、FP8 检查点 172.78 GiB）为 [官方]；`IQ3_XXS` 文件 71GB 为 [他卡实测] 社区。

### 4.1 KV 精度档的输出一致率（G-14，[环境2实测]）

要问的是「KV 降精度会不会改变输出」。用参考引擎自己的 KV 档做回归：同一提示（4K 真实文本）、greedy、512 个输出 token、同一个引擎进程参数，比对输出序列。工具 `measure/kv_quality.py`，原始记录 `measure/results/20261009T23*-kvquality-环境2.json`。

先要解决可复现性，否则一切比对都被跨运行噪声吃掉：

| 配置 | 同配置两次的贪心序列 |
|------|---------------------|
| 默认（只加 `--adapt-every 0`） | 第 40 个 token 首次分歧，一致率 0.078 |
| 加 `--adapt-every 0 --pcie-frac 0` | 逐位相同（512/512） |

即这台机器上该引擎的逐位复现口径是 `--adapt-every 0 --pcie-frac 0`；只关自适应换入不够——`--pcie-frac` 决定未命中专家里哪些被拷到 GPU 算，而 GPU 与 CPU 对同一专家的舍入不同。这与上游文档「要逐位一致需 `--prompt-cache 0 --adapt-swaps 0 --pcie-frac 0`」（§13.5）一致，且在一次性生成里 `--prompt-cache` 不参与。

在该口径下比较 KV 档（相对 fp16）：

| KV 档 | 首次分歧位置 | 序列一致率 | decode tok/s |
|-------|-------------|-----------|--------------|
| int8 | 40 | 0.078 | 77.6 |
| k8v4 | 57 | 0.111 | 76.0 |
| q4_0 | 40 | 0.078 | 75.8 |
| fp16（基线） | — | 1.000 | 76.6 |

三点读数：

1. **KV 降精度会改变贪心轨迹**，但前 40 至 57 个 token 完全一致——扰动小到不足以翻转 argmax，直到某一位翻转后级联。故「序列一致率」这个口径在 KV 上天然很低（7.8% 至 11.1%），不能用它判定质量是否可接受。
2. **四档吞吐几乎相同**（±2%）：在这台机器上 KV 精度买的是显存，不是速度。原因是瓶颈在 CPU 侧专家路径（§5.1、§5.2），与 KV 读带宽无关。
3. 顺带一条方法学结论：不加可复现口径时，同配置两次的 decode 吞吐也能差 6.8%（63.95 对 68.31 tok/s），故吞吐对比要么加这两个开关，要么多轮取中位。

未测的部分：困惑度拿不到——原生（IQ）pack 下 `--dump-logits` 产出 0 字节文件（源码注释亦如此说明：日志头是随第一行一起写的，而原生 pack 永远走不到逐 token 的落盘点）。要补困惑度需非原生 pack，或由 `--dump-residual` 的 R 复算 head。任务集与长文两条阈值同样需要外部评测 harness。

## 6. 引擎支持度

| 引擎 | 支持度 | 关键约束 |
|------|--------|---------|
| vLLM | 官方 recipe + 专用镜像 `vllm/vllm-openai:qwen38-flash-next`（PyPI 安装不支持） | 见下 |
| SGLang | 发布首日 Day-0 支持 | 新架构内核与量化路径跟进最快；QSA + 前缀复用叠加收益明显 |
| llama.cpp | 社区 GGUF 路线 | 4-bit 约 92.9GB（[推算]）；没有命中率概念 → 慢一个数量级 |
| Strata | 以此模型为设计目标 | 专家三级分层 + 热度排序常驻 |

vLLM recipe 要点（[已确认]）：
- KV：`--kv-cache-dtype fp8` + `--attention-config.indexer_kv_dtype fp8`
- 投机：`--speculative-config '{"method":"mtp","num_speculative_tokens":3}'`
- n-gram 卸载：`VLLM_PLE_CPU_OFFLOAD=1`，主存至少 51GB + 余量，且仅 NVIDIA 设备
- GB300：TP2 为 FP8 最小验证配置，推荐 TP4/TEP4；8×H200 用 TEP8 + `--moe-backend triton`（普通 TP8 不兼容 128-wide 量化块）
- `--gpu-memory-utilization` 0.90（GB300）/ 0.85（H200/H100）；`--max-num-seqs 256`
- 实测：4×H100 + PLE CPU 卸载，并发 64、1024-in/256-out，约 1,430 output tok/s（数据中心口径，不可与环境2 直比）

并行硬约束：
- FP8 检查体用 128-wide 量化块 → 8 卡普通 TP8 不兼容，应用 TEP8。
- N-gram Embedding 初始不支持流水线并行（PP），只能单节点 TP/TEP。
- 4×H100（80GB）普通 TP4 启动即 OOM（光 51B 嵌入表就超每卡余量），recipe 自动打开 PLE CPU 卸载。
- XPU/TPU 初始实现不支持。

## 7. 只对推理有意义的副作用（消融实验）

| 现象 | 含义 |
|------|------|
| 全注意力层去掉 RoPE 在预训练损失上几乎无差，但微调后生成易陷入重复循环 | 位置编码不是「可随意简化」的装饰 |
| GR 里「只读 top-2 分支」省显存搬运、预训练无损，但微调后质量明显下滑 → 最终放弃 | 预训练免费 ≠ 推理免费 |

## 8. 对引擎设计的三条结论

1. 容量问题必须先解，才谈速度：125B + 51B 外挂表在 16GB 单卡上，「装得进」永远是第一约束（环境2 2026-10-09 起为双卡 32GB，但相对 172.78 GiB 的 FP8 检查体仍远装不下）。
2. 两条 KV 缓存分开管理：GDN 状态按并发分配，QSA KV 按上下文 × 并发分配；二者要独立配额、独立量化精度旋钮。
3. n-gram 表看似最大的可优化面，实测不是。模型设计给出了「确定性访问」的窗口，但 §3.2 表明行访问在去重后既无顺序性也无近邻复用，提前一步的预取命中上界约 0.1%；能被利用的是长距离重复，一个有界行缓存即可获得（命中率 0.28 至 0.58）。故该表不再作为差异点，退守按需读加行缓存。
