# Strata 引擎深度拆解

> 研究对象：`github.com/Niko1221/Strata`。本文回答一个具体问题：一个 125B 的 MoE 模型，怎么在 12–16GB 显存的消费级卡上跑到可用速度？
> 结论先行：Strata 没有让 125B 装进 12GB，而是让「装不下」不再等于「每层都等 IO」。它的全部设计都围绕这一句话展开。

复核状态标记：[已确认] 已开原文逐位确认 · [摘要级] 仅见标题或摘要 · [存疑] 来源矛盾已降级。环境2 数值标注引擎版本。

## 2. 它要解决的瓶颈

问题不是算力，是容量：

- 主模型 FP8 检查点 172.78 GiB、BF16 335.28 GiB（[官方]口径）——任何单张消费卡都装不下。
- n-gram 外挂表 51B：FP8 约 51GB、4-bit 约 28.8GB（[官方]）
- 于是 llama.cpp 一类「全量常驻」引擎只能退化到层级 offload：每层把权重经 PCIe 搬回 GPU 再算。PCIe 5.0 x8 只有约 31.5GB/s（低于内存带宽），于是每层都在等搬运。

Strata 的攻击点正是「每层都在等搬运」这个 IO 循环。

## 3. 三级分层存储

| 层 | 放什么 | 依据 |
|----|--------|------|
| VRAM | 每个 token 必用的稠密部分：注意力与 DeltaNet mixer、gated-residual 权重、router、共享专家、输出头、MTP 草稿层、KV（≥64K 时只常驻最常读的部分，其余从 RAM 流入）；剩余显存全部用作专家缓存 | [官方] `docs/HOW_IT_WORKS.md` |
| RAM | 全部 24,576 个专家 pinned 锁页常驻；CPU 用 AVX-512 / AVX2 内核就地计算未命中专家 | [官方] |
| SSD | 28.8 GB n-gram 表；每 token 读 16 行、共 1,440 字节，走 OS page cache，无专用预取器 [S-34] | [官方] |

关键设计取向：显存不屯权重，屯「最热的专家」。VRAM 剩余多少决定能常驻多少专家，直接决定命中率，进而决定速度。

## 4. 专家缓存与命中率模型

- 启动时用预制热度排序（24,576 个专家的 profile 文件）装入最热的一批（社区配置里约 4,500 个），会话中持续学习、动态换入换出。
- 官方换算原话："every extra GB holds ~700 more experts"（每多 1GB 显存约多常驻 700 个专家）（[官方]）
- 双向印证：环境2 实测 `11,967 专家 / 16,416 MiB ≈ 729/GB`（2026-10-09 双卡合计；单卡期曾记 `5,269 / 7,235 MiB ≈ 746/GB`）；社区 `11,466 / 16.65GB ≈ 688/GB`。容量比显卡新旧更重要：24GB 卡比 12GB 快约一倍。
- 官方给出「12GB 卡命中率约 72%、双卡合计 44GB 可到 97.7%」的经验值（[他卡实测]）。

命中率是这个引擎的第一性能变量。它决定了每 token 有多少专家要走慢路径。

### 4.1 路由集中度与覆盖曲线（G-09，[环境2实测]）

命中率的上界由路由集中度决定，已在环境2 上实测。方法：用 `--dump-routing` 记录一次生成中解码路径的路由轨迹（记录格式 `layer, k, 专家 id, 权重`，见 [S-34]），统计 (层, 专家) 对的激活频次并按频次排序，得到 top-N 覆盖曲线。语料为参考引擎仓库自身的文档与源码：一条 4K token 提示续写 1024 token，另取四个不同段落各续写 512 token，合计 **1,646,400 次查表**（约 2,100 个解码位置 × 48 层 × top-10）。工具 `measure/expert_coverage.py`，原始记录在 `measure/results/*-expertcoverage-*.json`。

| 口径 | top-1,000 | top-5,000 | top-8,106 | top-10,000 |
|------|-----------|-----------|-----------|------------|
| 五条合并（164.6 万次查表） | 0.286 | 0.680 | 0.835 | 0.896 |
| 单条最长（55.4 万次查表） | 0.328 | 0.743 | 0.884 | 0.934 |

达指定覆盖所需的对数（合并口径）：50% 需 2,721 对、80% 需 7,253、90% 需 10,134、95% 需 12,541、99% 需 16,674 对——即 99% 覆盖要吃下全表 24,576 对的 68%。

三条读数：

1. 集中度远低于引擎代价模型所用的幂律。该模型声称 top-5,805 对覆盖 94.9% 的路由量；实测在 5,000 对处只有 0.680（合并）至 0.743（单条最长）。上游源码已注明这一偏差，并给出自己在另一台机器上的实测对照：5,805 对处 69.2%（IQ3_S 四卡，1,490 万次解码查表）——与本处同量级。引用命中率上界时不得再用幂律。
2. 饱和很慢，没有平台期。单条 512 token 的生成各触及 14,801 至 15,578 个不同对；五条合并触及 21,380 对（87.0%），仍有 3,196 对从未出现。位置越多、覆盖越广，扩大缓存持续有收益但不收敛。
3. 引擎自带的画像 `data/expert-profile.bin` 是排名而非频次，且不可跨任务迁移。把它当频次曲线用，在 5,000 对处只给出 0.410（实测 0.680）、8,106 对处 0.606（实测 0.835）。画像只能用于「先填哪些槽位」的顺序，不能用来估计覆盖。

口径提醒：以上是静态 top-N 覆盖，且只覆盖解码（专家池）路径——批量预填路径不写轨迹。引擎在真实会话里自报的解码命中率 94% 至 97%（8,106 槽位）高于此处的 0.835，差额来自自适应换入（会话内持续装载实际路由到的专家）与跨请求前缀复用；两者是不同的量，引用时不可混用。见 §13.4 的 `hit_rate` 口径。

### 4.2 槽位与命中率到吞吐的斜率（G-05 / G-06，[环境2实测]）

起 serve 实例、读 `/metrics`，并发一个真实提示的 greedy 请求（工具 `measure/engine_cache_probe.py`，原始记录 `measure/results/20261009-cacheprobe-*-环境2.json`）。部署配置为双卡、`--batch 4`、`--kv-resident 32768`。

| `--expert-cache` | 专家槽位（两卡） | 缓存 MiB | 命中率 | PCIe 占比 | decode tok/s |
|------------------|----------------|---------|--------|-----------|--------------|
| 2048 | 7,621 | 10,549 | 85.8% | 9.8% | 54.9 |
| 4096 | 9,806 | 13,499 | 92.1% | 4.7% | 63.2 |
| 8192（被显存上限钳住，与 auto 相同） | 11,967 | 16,416 | 95.6% | 2.2% | 68.5 |
| auto | 11,967 | 16,416 | 95.6% | 2.2% | 66.9 |
| auto，64K 提示 | 11,967 | 16,416 | 95.4% | 2.4% | 85.6 |
| auto，256K 提示（原生上下文） | 11,967 | 16,416 | 96.0% | 1.9% | 70.0 |

读数：

1. `--expert-cache N` 是**主卡口径**：CUDA0 拿 N 附近的数量、CUDA1 固定 5,438（层切分自定）。`auto` 取显存允许的上限，两卡合计 **11,967 槽位（主卡 6,529，8,816 MiB）**。`--batch 4` 的槽位会话另占 CUDA0 2.05 GiB，直接挤占专家缓存。
2. 命中率与 decode 吞吐**同向**：同一提示内斜率约 **+1.4 tok/s 每 +1 点命中率**（85.8%→95.6% 对应 54.9→68.5 tok/s），PCIe 占比同步从 9.8% 降到 2.2%。
3. **跨提示不可比**：64K 提示在命中率 95.4% 时 decode 反而 85.6 tok/s——上下文长度本身强烈影响该指标。这与上游「命中率与解码速度不保证同向」不矛盾，只是说明该斜率必须限定在同一提示与同一任务类型内。
4. 样本很小：每点 1 个请求、128 输出 token，同配置两次为 66.9 与 68.5（约 ±2%），故斜率只作方向与量级使用。
5. 命中率天花板的两层：静态 top-N 覆盖（G-09）在 11,967 对上约 0.90，而会话内实测 95.6%——差额来自自适应换入与跨请求前缀复用。

## 5. 未命中专家就地计算

这是与 llama.cpp 的根本区别：

- 路由选中不在显存的专家时，CPU 直接在内存里算完（AVX2/AVX-512 内核），与 GPU 上命中的专家并行，最后 scatter-add 合并。
- 效果：把 PCIe 从关键路径上摘掉了。代价是 CPU 算力成为新上限——环境2 的 Arrow Lake 无 AVX-512，只能走 AVX2。
- 但并非「完全不碰 PCIe」：`--pcie-frac` 的官方定义是「未命中专家里被拷到 GPU 算、而不交给 CPU 算的那部分比例」。取大=走快链路、取小=省 PCIe 给 CPU 算。`--pcie-frac 0` 会掉 decode 速度；prefill 阶段官方明确「experts streamed to the GPU over PCIe」。这推翻了早期二手文「CPU 就地算 = 完全不碰 PCIe」的说法。

### 5.1 未命中专家路径是算力瓶颈还是带宽瓶颈（G-07，[环境2实测]）

这条 CPU 就地计算的路是「卡在总线」还是「卡在算力」，决定核显能不能帮上忙（核显共享同一条内存总线，只加算力不加带宽）。微基准工具 `measure/cpu_expert_bench.c`（`cc -O2 -mavx2 -mfma -pthread`），在**同一块 512 MiB 缓冲区、同一字节量**上跑三个臂，比较吞吐：

| 线程 | 纯流式读 GB/s | 4 位码本+FMA | 2 位码本+FMA | 4 位/流式读 |
|------|--------------|-------------|-------------|------------|
| 1 | 29.2 | 1.5 | 0.8 | 0.051 |
| 2 | 34.4 | 3.0 | 1.7 | 0.084 |
| 4 | 45.6 | 5.6 | 3.2 | 0.123 |
| 8 | 58.5 | 10.2 | 6.0 | 0.174 |
| 12 | 63.0 | 15.5 | 8.6 | 0.245 |
| 16 | 59.4 | 20.6 | 11.4 | 0.347 |
| 24 | 67.5 | 30.8 | 17.1 | 0.456 |

读法：

1. 纯流式读在 8 线程就到 58.5 GB/s、24 线程 67.5 GB/s 后不再涨——这是该机器的读带宽天花板（高于 G-02 的 triad 53.7 GB/s，因为 triad 还要写）。
2. 两个算力臂都**远低于**天花板，且**随线程数持续上升**（4 位臂 1.5→30.8 GB/s），并没有像流式读那样在 8 线程后触顶。若受限的是总线，两臂应在到达天花板后与流式读重合；实测没有。
3. 因此在环境2 上，未命中专家路径受限的是**算力**（低比特码本查表与乘加的发射率），不是内存带宽。旁证：参考引擎自报其 CPU 专家池「rows phases 36.8 GB/s」，介于本处 16 线程的算力臂（20.6）与天花板（63 至 67）之间，同样没有触顶。

口径与边界：这是**合成内核**，不是引擎的真实张量布局（真实 IQ 内核是手调过的，绝对吞吐会更高），所以上面的 GB/s 是下界；起判定作用的是形状——算力臂随线程上升而未触顶。另：16 线程附近已是引擎专家池的实际规模（`--pool-workers 15` 加宿主线程），此时算力臂只用掉总线的一半左右，总线尚有可分配的余量。

### 5.2 量化内核的按核型吞吐（G-03，[环境2实测]）

同一路 CPU 就地计算的算力，按核型分开量。工具 `measure/cpu_gemm_bench.c`（`cc -O2 -mavx2 -mfma -pthread`）：按**专家真实几何**跑「码本反量化 + 点积」的 GEMV（gate/up [640×2560] 两次、down [2560×640] 一次，每个专家 4,915,200 次乘加），权重按每 32 值一块量化存放；用 `sched_setaffinity` 把线程绑到指定 CPU。本机的核型划分是 `/sys/devices/cpu_core/cpus` = 0-7（P 核）、`/sys/devices/cpu_atom/cpus` = 8-23（E 核），无 SMT。

| 配置 | 4 位档 GMAC/s | 4 位档 GB/s | 2 位档 GMAC/s | 2 位档 GB/s |
|------|--------------|------------|--------------|------------|
| 单 P 核（cpu0） | 2.81 | 1.58 | 2.89 | 0.90 |
| 单 E 核（cpu8） | 2.29 | 1.29 | 2.33 | 0.73 |
| 8 个 P 核（0-7） | 21.1 | 11.9 | — | — |
| 16 个 E 核（8-23） | 33.4 | 18.8 | — | — |
| 15 核（0-14，引擎专家池规模） | 32.6 | 18.3 | 34.7 | 10.9 |

三条读数：

1. **P 核相对 E 核只有 1.23 倍**（4 位档 2.81 对 2.29 GMAC/s；2 位档 2.89 对 2.33）。E 核单核并不「弱很多」，且 16 个 E 核的合计（33.4 GMAC/s）高于 8 个 P 核（21.1）。因此「按核型分池」是策略选择（避免长尾被慢核定），不是达到合计算力的必要条件。
2. **单位值的吞吐在 2 位与 4 位档几乎相同**（P 核 2.81 对 2.89 GMAC/s），只有 GB/s 相差 1.8 倍（1.58 对 0.90）。这与 G-07 一致：限制来自码本查表与乘加的发射率，与位宽无关；降位宽只省字节，不省算力。
3. 聚合随核数近似线性（8 个 P 核达单核的 7.5 倍，16 个 E 核达单核的 14.6 倍），此时聚合 GB/s 只有 18.8，远低于 §5.1 量出的读带宽天花板（58 至 68 GB/s）——再一次说明这条路不是总线受限。

口径：本内核是**保守实现**（标量码本查表），引擎自报其 CPU 专家池在 `rows phases` 达到 36.8 GB/s，约为本内核 15 核（18.3 GB/s）的两倍，故上面的绝对吞吐是下界。起判定作用的是核型之比与跨位宽的平坦性。

对引擎的含义：按专家几何折算，**每 1% 的路由量落到 CPU 就多 23.6 MMAC/token**；在本内核口径下约合 0.7 ms/token。G-09 的覆盖曲线（8,106 槽位覆盖 0.835）意味着约 16.5% 的路由量要走这条路，即约 11.6 ms/token——与引擎自己在运行日志里报的专家池 `pool 11.4 ms/round` 量级一致（口径不同，不作等号）。这条量化了 engine §15 的「未命中专家走 CPU 的慢路径」。

## 6. 投机解码与取权重成本

- MTP 草稿层最多起草 3 个 token，主模型一次 48 层前向并行验证，平均每步产出 2.4–3.2 token，整体 1.6–1.8×（[官方]）
- 另有 prompt lookup / suffix 起草最多 5 token（引擎 0.1.7 起），只在实测划算是启用（代码改写类 6–11%，其它文本基本不变）。
- 本质是把最贵的专家读取摊到 2.4–3.2 个 token 上（近 3× 摊薄），且输出分布不变（草稿只猜、主模型逐 token 定夺）。
- 为什么 llama.cpp 开 MTP 也救不了：它的草稿层同为 MoE、权重同样在显存外，猜词本身就贵，验证一遍仍要逐层读专家。

### 6.1 投机导致的 IO 放大（G-13，[环境2实测]）

放大系数有两个口径，都取自参考引擎自己的输出（工具 `measure/spec_io_amplify.py`，原始记录 `measure/results/*-specio-*.json`）：

| 口径 | 区间 | 中位 |
|------|------|------|
| 接受率取倒数（日志的 `speculation` 行） | 1.064 至 1.272 | 1.223 |
| 每生成 token 实际跑过的位置数（轨迹记录数 ÷ 48 层 ÷ 生成 token 数，含被拒草稿） | 1.047 至 1.250 | 1.133 |

样本为六次解码生成（16 至 1024 新 token，四次不同 4K 提示），实测 MTP 接受率 0.786 至 0.940。

两口径都落在 1.05 至 1.27 倍：草稿被拒带来的额外专家读与表行读只有一到两成。这比本设计早先引用的 1.35 倍（来自旧的线上日志、接受率 72.2% 至 74.1%）低，原因是 MTP 在本模型上的接受率明显更高。两口径的差来自口径本身：位置数把「同一验证窗口内被接受的草稿」也各算一个位置，故略低于 1/p。

对引擎的含义：投机对 IO 的放大只有约一成至两成半，不足以改变预算分配的量级；它按位置计同时作用于专家读与表行读，不区分路径。

## 7. KV 与长上下文

- KV 量化到 int8（环境2 `kv: int8`，[环境2实测]）。
- `--kv-resident 32768`：最热 32K token 段常驻显存，其余从内存流式读（社区实测读命中显存 96.9%，[他卡实测]）。
- `--prefill auto`：每块最多 8,192 token（32,768 需显式开，[官方]文档）→ 这是官方「长文读取 >1,000 tok/s」的来源，也是 prefill 与权重加载重叠的手段。
- WSL 约束：`--kv-streaming on|off` 官方注明 "never under WSL, which cannot stream"——在 WSL 里跑拿不到 `--kv-resident` 这条红利。环境2 实例 `kv_resident 32768` 生效，说明它并非跑在 WSL 内。

### 7.1 上下文复用：并发各自独立，跨轮/跨请求有复用（[官方] DETAILS.md 与 BATCHING.md）

- 并发槽位是独立会话：一个 batch 槽位 = 一份自己的 session（GDN 递推、QSA 的 K/V 与索引器、PLE 历史），并发会话之间不共享活 KV。
- 跨时间/跨请求的复用有三套机制：
  - 检查点（conversation cache）：续聊只读「引擎已持有部分之后」的尾巴。检查点最多 6 个、各约 118 MB，在每个新 assistant 轮开始与每 16K prompt token 处拍；只有 prompt 逐 token（含图片）完全匹配时才用。最老的那个检查点（通常 = system prompt 末尾，同一客户端每个对话都共享）永久保留 → 新对话若共享该前缀，就从它之后开始读，而不是从 token 0。
  - 槽位即对话缓存：跑完的槽位保留其内容；该对话下一轮回到这个槽位，引擎把状态拷回来（短会话约 50–60 ms）而非重读历史。
  - Conversation parking（`--conversation-cache-mib N --conversation-cache-slots K`）：把最多 K 个对话「停」在 RAM，之后在任一 stage 恢复；官方实测 9,276 token 的对话 51 ms 恢复，续写 token 与从未离开一致。默认预算 0（关）。
  - 固定共享前缀（`"strata_prefix"`，0.1.40.2，需 `--prompt-cache 3`+）：把「一长文档 + 多问题」的文档末尾钉成检查点 → 20 个问题只读一遍文档。一次只允许 1 个 pinned prefix。
- 复用直接省时间：环境2 实测 `reused / prompt_tokens ≈ 85%`（例：`reused 1,172,944 / 1,373,844`）→ prefill 只读尾巴（多为 1–2 s，而非十几万 token 的分钟级）。`/metrics` 甚至有 `vllm:prefix_cache_queries_total` / `_hits_total` 口径（沿用 vLLM 的指标命名）。
- 参数：`--prompt-cache N`（0=关）、`--prompt-cache-every N`、`--prompt-cache-root N`（0=无 system-prompt 检查点）、`--turn-token ID`。

### 7.2 KV 驻留与流式读（G-12，[环境2实测]）

`--kv-resident 32768`：每个 QSA 层在显存里常驻 32,768 个 cell，其余在 pinned 主机内存里按块流式读入。相对原生上下文 262,144，名义驻留率即 **12.5%**。

起 serve 实例实测的块读命中与内存读量（同一部署配置，见 §4.2 的记录）：

| 提示长度 | KV 块读的 VRAM 命中率 | 内存侧读量 |
|---------|---------------------|-----------|
| 4K token | 98.9% | 24.6 MiB |
| 64K token | 93.1% | 130.8 MiB |
| **256K token（原生上下文）** | **90.1%** | **213.3 MiB** |

关键点：引擎**不做索引器的稠密扫描**。它按索引器选中的块去读那份表示，因此每 token 的 KV 读量远低于 research/02 §3.1 里那个「262K 下稠密扫描 192 MiB/token」的推算——那条推算是**上界**，不是引擎的实际行为。真正决定 KV 侧带宽的是被选中块的数量与它们的驻留率，而不是 KV 总量。因此 research/02 §3.1 提出的「索引键若不常驻显存就要走 192 MiB 的 PCIe」这一担忧，在参考引擎上不成立：它读的是稀疏块，且 90% 至 99% 的块读命中显存。

一个 256K 请求（256,094 token 提示 + 128 解码）的内存侧 KV 读量合计只有 213.3 MiB——按 128 个解码 token 平摊也只有约 1.7 MiB/token，而且其中大部分发生在预填期。对照 192 MiB/token 的稠密推算，实测量低约两个数量级。同一次请求的 decode 为 70.0 tok/s、解码命中率 96.0%、PCIe 占比 1.9%——即长上下文下 KV 流式读也没有把吞吐压下去。

## 9. 多卡与并发（[官方] MULTI_GPU.md 与 BATCHING.md；[环境2实测] 见 §9.3）

> 这一节同时回答两个问题：Strata 怎么用多张卡，以及为什么多个请求会排队等。

### 9.1 多卡机制：pipeline（按层切分），不是张量并行

- 一张模型跨 2–3 张 NVIDIA 卡：层切成连续区间，每卡跑自己那段；最后一张卡还跑输出头 + MTP 草稿层。每卡只为自己那几层维护专家缓存 → 两卡的显存专家容量约翻倍。
- 是 pipeline（层）并行：一个 token 每个 verify window 跨卡一次（几百 KB，走 pinned RAM），不是每层跨两次 → 不需要 NVLink / P2P，x4 甚至 x1 槽也能用。`--pcie-frac` 若显式给出则是「每卡同一比例」，暂无按卡设置。
- 卡顺序（`auto`）：更快的卡放最后（末段跑 head / 草稿 / verify，prompt chunk 要等它）；等速卡保持你给的顺序。
- 配套开关：`--layer-split K1[,K2..]|auto`、`--split-device`、`--trim-stage-weights`（每卡只加载自己层的稠密权重，省下的 VRAM 归专家缓存）、`--vram-reserve-later-mib`。
- `--pipeline-windows 2`（可选）：第一张卡在末卡还在 verify 本 window 时就开下一个 window；下个 window 是猜的（猜本 window 全接受、且 bonus token 是草稿层预测那个）。命中→下个 window 已做一半；不中→回滚。需要「恰好两卡两段 + `--serve`」，且与 `--batch` 槽位互斥。

### 9.2 并发机制：`--batch N`（默认一次只服务一个请求）

- 默认 Strata 一次只答一个请求，其余在服务端队列里等（[官方] README + BATCHING.md 原话）。
- `"parallel": N` / `--batch N` / `--slots N`（常规 2..8）：最多 N 个会话同时解码，每个 verify window 每个会话带一个 token → 稠密权重、共享专家、head、以及会话间共用的路由专家每 window 只读一次。可选开关（#465，引擎侧 PR #559）。
- 双卡 + `--batch-groups G`：N 个槽位分 G 组在 GPU 间流水（GPU k 跑一组、GPU k+1 跑另一组）。G 必须整除 N。0.1.41 起 `--batch-groups auto` 默认 = 每 GPU 段一组（2 卡 4 槽 = 2 组 ×2）。
- 引擎默认上限 8 槽（一个 window 8 行），受 VRAM 限制；不足 2 槽时退回「一次一个」。
- 槽位的代价：每槽 session 占 VRAM（32K 上下文 + 8-bit KV 约 0.56 GiB），从专家缓存里出。专家多在 CPU 算的卡上，batch 只买到「延迟公平」不买速度：12GB 卡上单请求慢 11–24%。官方 5070 / Q2_0 / 32K 实测：4 并发时第 4 个请求首 token 从 11.2s 降到 1.8s，但总吞吐 70.7 → 63.1（−11%），单请求 79.6 → 16.9。
- 能塞满显存 / 层切分才是槽位真正加总速度的地方：4×16GB 层切分 + `--batch 8 --batch-groups 4 --trim-stage-weights`，并发 1→8 时总吞吐 120 → 360 tok/s（单请求 123 → 45）。
- 默认 batch window 不带 MTP 草稿（一槽一 token/window）；`--batch-mtp`（需单卡、`--mtp`+`--spec`）让每槽每 window 验一个 MTP 提案，不支持层切分 → 双卡用不了。
- server 侧调度（真正决定「为什么会等」）：
  - 请求多于槽位 → 等空槽（`/metrics` 的 `live.slots` 看每槽 idle/reading/decoding；`live.running` 是在飞请求数）。
  - 准入（admission）一次只做一个：「两个新长 prompt 一前一后地读」。
  - 读长 prompt 时，槽位只在每个 chunk 边界解码（默认解码时长 = 该 chunk 读时长 × 0.5），所以一个长 prompt 会拖慢而不是停住其它槽。
  - 长 prompt 遇「半长以下」的短请求会 `BYIELD` 让路（下一 chunk 边界切出）。
  - 请求数在 1↔多 之间变化会有 solo↔slot 的 STOP / 状态恢复 churn（每请求最多 2 回；短会话恢复约 50–60 ms）。
- `--pipeline-windows` 与 `--batch` 槽位互斥（层切分下两个都开不了）。

读数（环境2 口径：2× RTX 5060 Ti，PCIe 5.0 x8，命中率约 0.97，单流 77 至 86 tok/s）：
- decode 已越过「单卡 IQ2_XS@262K ≈ 47」一档，落在上游同类双卡（2×3090 IQ3_S 137、2×Arc B60 58–61）的中段；
- 按官方规律，prefill 是双卡收益最大的一块（+18–20%，两卡各读自己那几层并 chunk 流水），`STRATA_PREFILL_HELP=1` 时短 prompt 还能再快；
- 并发总吞吐在 `--batch` 槽 + 分组流水下可显著上抬（4×16GB 档 1→8 并发 120→360），上限受 8 槽与 VRAM 约束。
- 各机器模型档位/CPU 不同，不可直比；此处仅给「可能的区间」。

### 9.5 结论（引擎设计要点）

多卡用「按层切分（pipeline）+ 各卡各自专家缓存」，不要每层同步的 TP；并发用「可选 N 槽 batch + 按 GPU 分组的流水」，且要正面回答：槽位吃专家缓存、batch 默认无投机、准入串行、长 prompt 拖慢全体。环境2 双卡实测表明：专家高驻留 + 层切分时，槽位同时改善排队与总吞吐。

### 10.1 运行时内存占用与换页（[环境2实测]，引擎运行与停机对照）

| 项 | 引擎运行中 | 引擎停机后 |
|----|-----------|-----------|
| 进程常住（`strata` VmRSS） | 31.25 GiB（峰值 48.13 GiB） | — |
| 进程换出（VmSwap） | 2.61 GiB | — |
| 主机 `shared`（Shmem） | 36.9 GiB | 1.4 GiB |
| 主机 swap 已用 | 7,450 MiB / 8,191 MiB（91%） | 3,524 MiB |
| 主机可用内存 | 17.5 GiB | 55.6 GiB |
| 进程 `VmLck` / `VmPin` | 0 / 0 | — |

读数：

1. 该实例的常驻区在共享内存里，而且可被换出。引擎运行时 `Shmem` 36.9 GiB、停机后降到 1.4 GiB，说明那约 35 GiB 常驻区是 tmpfs 或共享内存；tmpfs 可被换出，实测该进程有 2.61 GiB 落在 swap，系统 swap 已用到 91%。
2. 因此 §3 表中「全部 24,576 个专家 pinned 锁页常驻」这条 [官方] 表述对该实例的实际部署不成立：它没有做到不可换出。
3. `VmLck` 与 `VmPin` 均为 0，但这不能单独证明未使用页锁定内存（CUDA 的 page-locked 分配不走 mlock 记账），只作辅助信号；决定性证据是上面的 `Shmem` 与 swap 计数。
4. 含义：「热专家进 pinned 区以避免换页抖动」是对上游做法的改变，不是复述上游；其代价是 pinned 页不可换出，会加剧内存不足时的整体压力——与上游把 `--vram-reserve-mib` 从 770 压到 0 会触发系统回退属同一类取舍。

推导（公式抄在画像 JSON 的 `formulas` 里）：

| 参数 | 公式 | 结果 |
|------|------|------|
| 每步 PCIe 字节预算 | pcie_h2d × 步长 × io_share（设计输入，取 0.5） | 186.8 MiB |
| 本步必需需求 | 48 × 10 × 专家块字节 ×（1 − 命中）+ 表行 | 106.9 MiB（静态命中）/ 25.9 MiB（会话命中） |
| 预算宽松度 | 预算 ÷ 需求 | 1.75×（静态）/ 7.21×（会话） |
| 专家槽位 | 缓存字节 ÷ 专家块字节 | 12,160（实测 11,967，差 1.6%） |
| KV 满上下文 / 常驻窗 | 上下文 × 1,056 B/cell × 12 层 | 3,168 / 396 MiB（12.5%） |
| §15 的带宽上限 | 显存带宽 ÷ 每 token 权重字节 | IQ2_XS 216 tok/s、FP8 64.8 tok/s |

三条读数：

1. 槽位公式复现实测值到 1.6%，说明「槽位 = 缓存字节 ÷ 专家块字节」这条算术成立，可用它直接换算别的显存或别的量化档能装多少槽位。
2. 每步 PCIe 预算（186.8 MiB）对「本步必需的未命中专家」有 1.75 倍余量（按静态命中 0.835），按会话内命中 0.96 则有 7.2 倍——这台机器上 PCIe 不是把盲塞进一个步长的约束，与 §4.1 至 §4.2 的结论一致。
3. 用实测带宽（398，而非标称 448）算 §15 的上限：IQ2_XS 从 250 降到 216 tok/s、FP8 从 75 降到 64.8。参考引擎实测的双卡 77.2 至 86.3 tok/s 落在两者之间——它用 IQ2_XS 权重，即达到权重口径上限的 36% 至 40%，与「远低于权重口径的上限」一致。

已知缺口：并发分池只给出 QSA 侧的每 cell 字节（1,056 × 12 层）；GDN 侧按并发增长，需要 SSM 几何才能算。起草长度上限按实测位置放大（T=6 窗口下 1.05 至 1.25）取引擎自身的上限 8，实际由接受率门控。

## 11. 约束与风险清单

1. CPU 算力即上限：AVX2（无 AVX-512/AMX）平台未命中部分的吞吐被封顶。
2. 命中率是单点依赖：所有速度结论都挂在命中率上；工作集切换时 `hit_rate` 会波动（单卡期实测 0.655–0.859；双卡常规 0.935–0.975；长 prompt 下可下探至 ~0.79，此时 `pcie_share` 同步升高，见 §9.3 / §13.4）。
3. 专家缓存有自适应淘汰，但不是开放策略面：`--adapt-every` / `--adapt-swaps` / `--adapt-async` / `STRATA_ADAPT_LAG` 控制「跟着会话把专家在 VRAM↔RAM 之间搬」，被换出的专家回写到它在 RAM 的位置，使 RAM 侧恰好保存「GPU 没有的那些」（[官方] `docs/DETAILS.md`）。没有的是「可插拔/可自定义的淘汰策略」与「共现感知的预载」。
4. `conversation_cache` 事实上不可用：门槛「空闲 ≥2,560 MiB」在最需要它的多轮 agent 场景下恒为关。
5. n-gram 表无显式预取器：走 OS page cache 而已；28.8GB 表在 SSD 上时冷启动代价大（首请求约为稳态的 1/18）。
6. WSL 不可用 `--kv-streaming`。
7. 并发槽位有限：默认 1（一次一个请求），环境2 4，引擎上限 8；且 batch 默认无投机、准入串行、长 prompt 会拖慢全体（§9.2）。并发吞吐天花板明确。

## 12. 对引擎设计的可迁移结论

| 结论 | 来自 |
|------|------|
| 显存要屯「最热专家」而不是「整层权重」 | 第 3、4 节 |
| 未命中必须与 GPU 并行算，不能串行搬 | 第 5 节 |
| 投机解码是 MoE-卸载场景的必选项（不是可选项） | 第 6 节 |
| KV 要做「常驻热窗 + 流式冷段」两级 | 第 7 节 |
| 所有参数应按机器自动标定（`--calibrate` 的思路可再进一步） | 第 8 节 |
| 多卡用「按层切 + 各自专家缓存」，别用每层同步的 TP | 第 9 节 |

同时，第 11 节的 7 条约束，即本设计的机会清单。

## 13. 上游文档补充核查（[官方]）

2026-10-09 对上游文档的补充核查，独立成节（本节全部事实源自上游 `docs/DETAILS.md` / `docs/INTEL_ARC.md`）：

### 13.1 `--calibrate` 的确切能力边界

引擎 0.1.19 起自动实测 4 个「随 PC 而非随模型」的参数（`--pcie-frac`、`--spec-min-p`、`--pool-workers`、`--adapt-*`），只保留 >3% 提升的取值，结果按 PC + 模型记忆，耗时 15–30 分钟。→ 「自动标定到机器 profile」不是本项目的差异点，上游已实现。

### 13.2 已实现的「预测预取」与「批量 IO」

- `STRATA_LOOKAHEAD` / `STRATA_LOOKAHEAD_K`：CPU 算一层时，另一线程对下一层应用路由，预测未命中专家并请求其页（只请求页，不改计算结果；`STRATA_LOOKAHEAD=0` 关闭）。
- `STRATA_IO_PREFETCH=1`（0.1.40.2，Linux file-tier）：整块 `pread` 进页缓存，`STRATA_IO_PF_THREADS` 默认 8，`STRATA_IO_PREFETCH_DEPTH` 默认 2；greedy 输出哈希不变（已自证逐位一致）。
- Windows 侧用 `PrefetchVirtualMemory` 一次性批量请求整页集合。
- `STRATA_EXCHANGE_ROTATE=1`：自适应交换改为移交缓冲所有权而非拷贝，宿主拷贝更少。

### 13.3 预取的实测收益与负收益

cgroup 限内存、200-token greedy 中位数、每次跑前丢页缓存：

| 机器 / 内存上限 | 默认 | `STRATA_IO_PF_STAGE=1` |
|---|---|---|
| RTX 3060，32GB，IQ3_XXS | −3.4% | +25.7% |
| RTX 3060，16GB，IQ3_XXS | −1.8% | −32.6% |
| Radeon 780M 核显，16GB，Q2_0（自适应层关） | −0.7% | −19% |

上游结论：页缓存热时文件层已按常驻速度跑，没有可赢的东西；差距只在冷启动与低内存 lane。默认关闭，暂存变体只建议 32GB 级机器尝试。
iGPU 附加警告：Radeon 780M 上「预取 + 自适应层」在内存压力下约 9 次里 7 次 GPU 复位（引擎只打警告照跑）；`--adapt-every 100000` 后约 40 次无复位。原因未知。

### 13.4 `hit_rate` 的口径

`hit_rate` = 查表专家中 residing 在 VRAM 的比例；经 `--pcie-frac` 从 PCIe 搬入的专家不计入 → 「调高 `--pcie-frac` 会让 `hit_rate` 上升，即使解码变慢」。另有 `pcie_share`（0.1.39+，#588）单独统计 PCIe 侧占比。
另：`--vram-reserve-mib` 从 770 降到 0 可多出 333 个槽位（2,782→3,115），但每步剩 0 MiB 空闲会触发系统回退，上游判定「留给整张卡其余部分的余量比多出来的槽位更值钱」（引 issue #781）。

### 13.5 逐位复现的开关组合（本项目对确定性的要求，上游已文档化）

跨请求有两件事会改变舍入：自适应层在 RAM/VRAM 之间搬专家（GPU 与 CPU 对同一专家的舍入不同）与 prompt cache 复用。要逐位一致需 `--prompt-cache 0 --adapt-swaps 0 --pcie-frac 0`（#410）。
